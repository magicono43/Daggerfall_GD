## Delivered interface and ownership

The [formula contract](../../../main_project/scripts/rule/FORMULA_DISPATCH.md)
defines the exact bounded API and supported behavior:

- `integer-formula-v1`, initially only fixture.integer: pure single-integer whole
  replacement, input -1000..1000, output -1000000..1000000, no gameplay mutation,
  no random-source use or session Objects passed to callbacks. Known calculations
  are built-in x*2, A x+100 and B x+200. No production combat/stacking/pricing/spell
  hooks, additive chains, universal rule interpreter or gameplay history exists.
- Standard unbound RefCounted methods validate by actual Godot reflection: one
  TYPE_INT argument, TYPE_INT output, no defaults/varargs/bound/unbound transforms.
  Preflight never probes a callback to discover behavior. Trust/purity/synchronous
  execution are explicit obligations, not a proof about arbitrary executable code.
- MOD's new read-only `formula_provider` attests exact selected enabled package ID /
  version, resolved order and existing hooks_allowed integration eligibility.
  Fixtures associate application-owned methods with real discovered packages; no
  package source is executed. IMP-050/051 still own real executable admission.
- Every prepare retires the old candidate and validates all contributions before
  selection. Missing/disabled/wrong-version providers, unknown hooks, signatures,
  duplicates and empty contributions block entry. Any invalid contribution leaves
  no winners. Selection walks real MOD order; reversing registration arrival does
  not change B as winner. Empty eligible registrations select declared built-in.
- Omission uses the exact failed candidate ticket and MOD/registration fingerprint
  and removes the whole provider formula contribution, including otherwise-valid
  entries. It does not disable its package. Clean rebuilding revalidates MOD
  dependencies, registrations and DATA. MOD revision/staging invalidates omissions;
  dependency failure discards obsolete formula candidates/provenance.
- The existing CORE menu transaction reserves DATA, formulas and MOD mutation
  admission before menu callbacks/profile-history persistence. Menu/profile failure
  publishes neither. After the durable step, only assignment remains: publish DATA
  and formulas, lock MOD and mark actual menu entry. No fallible I/O/callback is
  introduced afterward. Reentrant stage/prepare/Continue requests reject as busy.
  Title/setup, character/load and ordinary preferences preserve the run lock.
- CORE binds explicit ready session consumers to the application's published hook
  set. The invoker checks registry identity, actual consumer Object identity,
  current ready/safe scope, stable CORE admission and the owner's current operation
  predicate. It captures operation values before invocation, then rechecks context.
  Mutation of the caller's Dictionary cannot replace the captured operation.
  Ended scopes, foreign registries and stale owner operations cannot apply values.
- Exactly one selected method is called. Failure identifies hook/provider/session /
  captured operation and observed scalar return/type without exposing Objects.
  CORE enters service-loss recovery; the owner applies no failed value. The winner
  is neither removed nor replaced, blind retry cannot invoke again, and diagnostic
  projections never call any provider. Owners retain application/retry authority.

## Callback-error mechanism and build limits

A scoped `Logger` records non-warning engine errors around synchronous Callable.call,
then is removed. Errors are checked before the returned value's type/domain.
This distinguishes genuine reported execution failure from detectable bad output,
without catching by reinvoking a method or trying another provider.

The initial editor/debug experiment demonstrated a real Dictionary-key callback
abort returning the valid-looking default integer **0**. Windows release templates
compile that VM check out, so the Dictionary-only release test was **incomplete**:
no engine error was observable and the owner could receive 0. That exploratory
report (`export-57e4f6d8ab8547339713aac753e99851/result.json`) is retained and is not
counted as passing thrown-callback evidence.

The final fault fixture uses a native JSON parse failure that remains observable
in both templates, followed by access to the failed result. Editor/debug emits
native parser error kind 0 plus an actual GDScript callback abort kind 2; release
emits the native execution error kind 0. Both return 0 but are classified
`callback_error` before application. An explicitly returned 1000001 produces
`invalid_result` with no engine errors. The distinction is checked separately.
Release native-error handling is not mislabeled proof of a compiled-out VM abort.

The monitor cannot detect silent within-domain semantic mistakes, prove arbitrary
callback purity, undo partial mutations or contain native crashes/late asynchronous
work. Supported callbacks must validate preconditions and remain synchronous/pure.
Actual executable/sandbox contracts remain IMP-050/051. No new template/compiler
or native shim was adopted to disguise the observed release limitation.

The console diagnostics are not suppressed. Fault verification matches the complete
pinned parser source/function/line/code/rationale and log site, plus the paired
script abort in debug builds, with fixed inventories and build-mode evidence.
Missing/unmatched/extra errors remain incomplete. An extra error outside invocation
is deliberately emitted in `formula-extra-error-v1`; its owner assertions finish,
but both editor modes and the release export must remain incomplete/exit 2.
Import errors are always disallowed. No generic allow-script-errors option exists.

An exploratory release `--script` probe did not execute the intended script and
