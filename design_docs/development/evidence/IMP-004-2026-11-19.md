## Implementation and exact manifest

The existing normal startup/provider boundary now uses a real application-owned
DATA registry. It separates source resolution, basic validation, unpublished index
initialization, settings publication, reader activation and per-record access.
Required-reader publication is all-or-nothing. Failed/replaced candidates discard
their indexes/handles before retry; stale initialization tickets cannot activate.
Windows case aliases reuse active indexes. Menu/character lifecycle does not own
the registry. Shutdown disposes DATA before releasing the persistent-storage lease.

The registered foundation capability `classic-containers-v1` requires exactly:

| File | Supported container | Observed records | Encoded index bytes |
| --- | --- | ---: | ---: |
| `ARCH3D.BSA` | BSA numeric (`0x0200`) | 10,251 | 82,008 |
| `BLOCKS.BSA` | BSA named (`0x0100`) | 1,295 | 23,310 |
| `MAPS.BSA` | BSA named (`0x0100`) | 248 | 4,464 |
| `DAGGER.SND` | BSA numeric (`0x0200`) | 459 | 3,672 |

Inventory: **one implemented generic BSA/SND container reader, four mandatory
source instances, raw indexed bytes only**. The startup reader gate is the enabled
consumer. Counts above are fixture observations, never acceptance thresholds.
The manifest composes registered declarations of enabled capabilities and includes
adapter provenance per entry. An enabled undeclared capability fails closed.
Unsupported reader formats and late registrations are rejected.

Checks: readable/nonempty required filenames; complete four-byte little-endian
header; nonnegative signed-16 count; supported directory tag; complete EOF
directory (18-byte named or 8-byte numeric entries); nonempty named identity;
nonnegative signed-32 sizes; cumulative payload extents from byte 4 bounded by
the directory. Duplicate identities retain all physical records; ambiguous
ID-only queries fail explicitly and ordinals remain accessible. Extra files,
zero/changed populations, padding and compatible modified data are accepted.
No original checksum, size, count or content value is required. Payloads are not
eagerly decoded or exhaustively scanned. Supported-format evidence is DFU's
read-only `API/BsaFile.cs` enum/header/directory/record code plus the real checks
below; no DFU implementation/runtime was incorporated.

See [manifest and API contract](../../../main_project/scripts/data/README.md) for
exact layouts, registration, source rules, identities, failures and staged owners.
`ready`, `record_not_found`, `source_unavailable`,
`malformed_or_unsupported` and `before_readiness` are distinct access results.
Failures retain file/path, requested record and reason where available. DATA does
not replace failures with successful defaults or choose a recovery policy for
future consumers. Raw ordinal addresses are not persistent GAD-01 definition keys.

Initial source settings persist before activation. Invalid/canceled selection and
failed source-setting publication preserve the committed selection; source-specific
failure also rolls back the accepted path. Generic accepted-unsaved preference
semantics are retained. Later valid source changes persist pending restart while
active readers/index identities remain unchanged. The UI shows the active source.
Production IMP-005 still rejects package publication. Real DATA success therefore
reaches package recovery, not a fabricated normal menu or gameplay-ready state.
