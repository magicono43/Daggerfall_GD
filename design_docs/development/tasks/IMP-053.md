## Approved quest-debug increments

The user approved this breakdown on 2026-11-18.

1. **Inspector.** Read QUEST's projections for task/clock/binding/global/provider and outcome state. Search and selection do not re-evaluate conditions, draw randomness or execute actions.
2. **Trace.** Keep the approved per-run bounds of 1,000 entries and 4 MiB with aggregation/filtering and explicit sanitized local export. Eviction affects detailed diagnostics only; durable recovery summaries/receipts remain QUEST-owned.
3. **Author tests.** Launch selected stable quest IDs through production validation and execution in the approved isolated in-world workflow. State-changing controls require that context and preserve ordinary player storage/session state.

## Debug fixture and ownership

Use IMP-028's fault/retry quest with retained first-effect receipt and IMP-038's durable recovery facts. DEV consumes them and owns disposable trace/presentation. IMP-052 provides console entry. Each test operation identifies the isolated context and selected quest. Inspector availability never grants mutation permission.

## Constraints and readiness

Planning-ready for the approved three increments. Target Windows first on Godot 4.7.2. Execution waits for IMP-028/038/052 and authorization. Export uses DEV-004's allowed context and sanitization rules.

## Acceptance

- Inspect the fault/retry fixture repeatedly and compare task, RNG, action and recovery state before/after. No query can rerun a condition or action.
- Exceed entry and byte bounds independently. Verify aggregation/eviction and retained durable fault summary/receipts.
- Filter/export the trace and compare selected context and sanitized fields. Export failure reports the actual outcome without mutating the quest.
- Launch the chosen quest by stable ID in the isolated in-world context and compare production owner behavior.
- Attempt state-changing controls in an ordinary session and with stale isolated context. Reject both without player-state or storage mutation.
- Verify the accepted and rejected outcomes specified by the linked feature criteria; record which criteria are covered by owner tests and which require a milestone integration run.
- Confirm that required handoff results reach the expected consumer and that rejected or obsolete input leaves committed state consistent under the approved failure policy.
