## Runner and fixture contract

- Provide two project-owned local commands that invoke the project on Godot 4.7.2, one headless and one rendered. Both take a suite or scenario selection and a stable fixture identity. An optional explicit seed, clock and input sequence are supported by the scenarios that need them. Keep command arguments callable from later CI.
- Allocate a fresh disposable test root for each run through the storage seam from IMP-001. Use isolated synthetic data and clean session state. Report scenario ID, fixture and relevant inputs, engine/build, result and expected/actual on failure. Preserve the result for the invoking process. A pass exits successfully. Failure or an unavailable required check exits unsuccessfully and is identified as failed or incomplete in the report.
- M1 verifies harness invocation, isolation and reporting with one passing case and one explicitly selected failing fixture. Add production scenarios for enemy placement/combat and failed restore to M2, then quest fault/retry to M3. Add rule and classic conversion vectors alongside their owners. Keep render-dependent assertions in the separate rendered suite.

## Constraints and readiness

Planning-ready on 2026-11-18 using project-owned commands. Target Windows first with Godot 4.7.2. Script filenames, report serialization and CI integration are implementation details. IMP-001's startup prerequisite was delivered on 2026-11-19 ([evidence](../evidence/IMP-001-2026-11-19.md)); execution still requires explicit authorization. Adopt its task-local startup cases without treating them as delivery of this shared harness.

## Acceptance

- Run each local command independently, first with a passing fixture and then with an explicitly selected failing fixture that asserts expected 1 against actual 0. Check the exit outcome, expected/actual report and distinct disposable roots. Request a missing required scenario and verify an incomplete result with an unsuccessful exit.
- Verify the accepted and rejected outcomes specified by the linked feature criteria; record which criteria are covered by owner tests and which require a milestone integration run.
- Confirm that required handoff results reach the expected consumer and that rejected or obsolete input leaves committed state consistent under the approved failure policy.

## Automated verification

Assert that a deliberately failed scenario yields a failed suite result with expected and actual values. Confirm that an unavailable required scenario cannot produce a green routine gate. Add the three production scenarios at M2 and M3. Use isolated fixtures under DEV-014 and record the inputs, expected outcomes and actual assertions.

## Manual verification

Invoke each suite locally and check exit status and reproduction output in a clean workspace. Record the fixture, build and observed outcome. Follow the linked feature’s explicit manual or rendered criteria where supplied.
