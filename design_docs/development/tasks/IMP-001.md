## Startup interfaces

1. **Root resolution.** CORE supplies the executable directory, standard per-user directory, launch mode, and explicit fallback choice when applicable. Select from launch inputs once and return either a checked root context with its process-held lease or a failure identifying the operation and path. Distinguish required I/O failure from root-in-use. Root-in-use offers Retry or Quit. Required portable I/O failure offers Retry, explicit standard fallback or Quit. Keep the lease for the lifetime of persistent consumers. Return the same root context to settings, logs, SAVE and MOD.
2. **Platform boundary.** Windows is the first acceptance target, confirmed by the user on 2026-11-18. Keep per-user path discovery, root identity and exclusive locking, and safe file replacement behind a storage adapter. Verify two processes targeting the same Windows directory through supported aliases, concurrent distinct roots, and reacquisition after process termination. Future platforms implement and verify the same behavioral contract.
3. **Settings.** Read packaged defaults, active settings, the last validated backup and damaged-input recovery through the selected root where applicable. Use the approved versioned human-readable settings.ini and preserve unknown keys. Return separate results for normal initialization/load, successful recovery with reset details, incompatible format, invalid packaged defaults, and failed required publication. Stage and validate writes before publication. Preserve the last usable version on failure. Report runtime application independently of persistence. Consumer settings and compatible groups join through owner-declared defaults and validation. The startup slice verifies the classic source path and setup-at-startup preference plus controlled single-value and grouped recovery inputs.
4. **Setup routing.** The shell consumes checked classic-source and package outcomes. Missing or invalid required data routes to mandatory setup; valid classic data permits the package step. A rejected package candidate stays in recovery with its reported source and reason. Reach main-menu readiness only after the mandatory checks and configuration publication. Exercise this with controlled result providers first and replace them with IMP-004/005 in the M1 integration run.

## Acceptance

- Launch without a marker and verify standard storage. With Portable.txt beside the executable, verify PortableAppdata beside the executable and exclusive root access. Compare the test and ordinary player roots.
- Make required portable storage unavailable. Assert that Retry, explicit standard fallback and Quit are offered, and that fallback leaves the marker and portable files intact. Verify the next launch tries portable again. A logging-only failure warns and permits startup.
- Compare quiet first-run settings initialization, corrupt-input recovery with a valid backup, and rejected publication. Check that failed publication preserves the existing usable version and prevents startup success. Verify preference activation separately from persistence.
- Across two launches verify Player.log and Player-prev.log. Verify a session change leaves rotation intact. Exercise setup routing with controlled provider outcomes, then run the same routing against the real DATA and MOD results at M1.
- Verify the accepted and rejected outcomes specified by the linked feature criteria; record which criteria are covered by owner tests and which require a milestone integration run.
- Confirm that required handoff results reach the expected consumer and that rejected or obsolete input leaves committed state consistent under the approved failure policy.
