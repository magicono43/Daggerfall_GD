## Approved runtime and activation handoff

The user explicitly approved Luau restricted scripting and GDScript trusted scripting on 2026-11-18. The [runtime contract](../MOD_RUNTIME_REVIEW.md) defines package module loading, host capabilities, budget/allocator failure, executable approval identity, scope retirement and exported verification.

1. Implement restricted multi-file source loading in a package-isolated VM with checked value/ID owner bindings.
2. Bind trusted approval to the executable snapshot and load GDScript only after consent and revalidation. Demonstrate a substantial provider replacement.
3. Prepare registrations in validated order before dependent content validation, publish through IMP-005 and retain MOD-005's verified cleanup/restart recovery.

## Constraints and readiness

Planning-ready under the approved runtime selection and executable-content contract. Target Windows first on Godot 4.7.2. Execution waits for IMP-005/028 and authorization. Actual versions, build options and measured quotas are pinned with dependency integration. Exported isolation, multi-file performance and substantial replacement are acceptance requirements.

## Acceptance

- Run restricted ZIP and unpacked multi-file fixtures through the selected VM and owner bridge in a Windows export. Verify declared behavior and report startup/first-use measurements.
- Probe prohibited filesystem/network/OS/object/native access, path escape and imported bytecode; exercise loop, allocation and bounded host-operation limits.
- Verify no trusted execution before consent. Alter executable inputs after discovery and assert renewed approval is required; a data-only edit with identical executable identity retains it.
- Demonstrate a substantial trusted gameplay-provider replacement and explicit resolution of competing replacements.
- Decline approval and verify inactive installation, dependent diagnostics and explicitly selected validated data-only fallback.
- Inject activation/session setup failure and stale callbacks. Retry only after verified cleanup; unsafe cleanup requires restart under MOD-005.
- Verify the accepted and rejected outcomes specified by the linked feature criteria; record which criteria are covered by owner tests and which require a milestone integration run.
- Confirm that required handoff results reach the expected consumer and that rejected or obsolete input leaves committed state consistent under the approved failure policy.

## Automated verification

Inspect a mod without executing it. In an exported build, validate a restricted sample, probe disallowed capabilities, and change executable content after discovery to verify that permission is tied to the activated version. Use isolated fixtures under DEV-014 and record the inputs, expected outcomes and actual assertions.

Require exported evidence for the supported boundaries before enabling dependent scripting and extension capabilities.

## Manual verification

Use a packaged build on each supported target to exercise approval, tamper detection and denied restricted capabilities. Record the fixture, build and observed outcome. Follow the linked feature’s explicit manual or rendered criteria where supplied.
