## Approved definition-reader increments

The user approved these groups on 2026-11-18. Deliver and verify each independently.

1. **Actor and character inputs.** Resolve encounter and flat definitions, class records and biography sources under DATA-007/008. Preserve field values, stable definition keys and classic mappings. NPC and CHAR own actor construction, eligibility and biography application.
2. **Items and spells.** Decode templates and classic spell inputs and apply declared patches under DATA-010/011. Preserve template identity separately from mutable instances. Reject ambiguous classic mappings and invalid required references. ITEM and MAGIC own item construction, effect conversion and execution.
3. **Faction and quest inputs.** Supply faction records, relationships, quest sources, lists and shared tables under DATA-009/012. DATA resolves sources and provenance. FACT validates faction semantics and QUEST supplies grammar, command and semantic validation. Source access cannot execute a quest or change standing.

## Reader and publication handoff

Each adapter accepts the selected source and declared definition identity and returns a typed immutable record/source with provenance or a checked missing, unavailable, malformed or unsupported result. Required-reference validation returns the referring key, target and reason. Publish complete candidate contributions only after applicable structural and owner validation. Preserve all DATA-003 operation and collision rules.

Source adapters may first verify their output with controlled validation providers. IMP-028 closes actual QUEST grammar and command validation, IMP-032 faction semantics, IMP-015/016 character construction, IMP-017 item construction and IMP-033 spell conversion. Before any corresponding production definition becomes usable, that owner's real validation must pass. Unknown executable commands cannot become valid through a fixture validator. Adapter availability in M1 alone does not certify later semantic readiness.

## Constraints and readiness

## Acceptance

- For each group, pin one valid source record and compare all supported decoded fields, its stable key, classic mapping and provenance with the source fixture.
- Remove a required referenced definition and verify referring/target IDs and rejected readiness. Truncate a source or provide an unsupported record and verify the appropriate error rather than an empty record.
- Publish a valid contribution, then attempt a patch whose later entry is invalid. Assert zero partial changes from the rejected contribution and unchanged earlier committed definitions.
- Exercise duplicate classic spell mappings and duplicate quest list entries under their approved explicit collision rules. Read and validate twice and assert no live RNG draws, new instances, quest starts or standing changes.
- Replace controlled semantic validators with production owners at the named integration checkpoints and verify an unknown required quest command blocks usability.
- Verify the accepted and rejected outcomes specified by the linked feature criteria; record which criteria are covered by owner tests and which require a milestone integration run.
- Confirm that required handoff results reach the expected consumer and that rejected or obsolete input leaves committed state consistent under the approved failure policy.
