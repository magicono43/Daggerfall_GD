# NPC architecture review

Scope covers NPC-001 through NPC-024 in the [feature catalog](../systems/NPC_FEATURE_CATALOG.md). This is a static review of the local DFU 1.1.1 Release snapshot. The exact commit is unavailable in the [repository record](../00_REPOSITORY_OVERVIEW.md). Source paths are relative to Assets/Scripts. Runtime reachability, performance and classic parity remain open.

## Existing architecture

### Population, identity and encounters · NPC-001–007

- **Outdoor civilians (001–003).** Game/Utility/PopulationManager.cs schedules enable and recycle through distance, time, visibility/activation checks and navigation progress. It reuses motor objects and reinitializes their civilian data using MobilePersonNPC.RandomiseNPC or MobileNPCGenerator. UpdateMobiles activates the object before generating identity and calling InitMotor, then emits OnMobileNPCEnable. Consumers of the custom event see initialized data. Unity enable callbacks on the object can run earlier. The practical consequence depends on component wiring. MobilePersonMotor owns local seek/move/idle behavior and handles floating-origin changes, using CityNavigation and clearance probes. Pooling and local navigation fit transient crowds. Pool handles should have an explicit lifetime if quests or saves ever reference them.
- **Placed actors (004).** Game/StaticNPC.cs keeps layout data separate from runtime data and attaches QuestResourceBehaviour when a questor matches. GetPositionHash uses XOR and shifts over layout coordinates. It is a compact position fingerprint, with no uniqueness guarantee. Keep a location-scoped authored identity for placed actors if relationships must survive layout edits. Verify the surrounding key scope before attributing a collision to shipped data.
- **Enemies and spawning (005–007).** EnemyEntity sets career, equipment and spells from enemy data. PlayerEntity.IntermittentEnemySpawn, FormulaHelper and RandomEncounters handle ambient eligibility and selection. FoeSpawner.PlaceFoeFreely performs placement and FinalizeFoe activates objects. Encounter and spawn hooks allow consumers to observe distinct phases. The separation between choosing an archetype and placing a live object is worth retaining. Global player context, shared random calls and Unity placement checks couple the phases in practice. Validate bounds, unavailable geometry and a spawn deferred during scene transition. See Game/Entities/EnemyEntity.cs, Game/Entities/PlayerEntity.cs, Utility/EnemyBasics.cs, Utility/RandomEncounters.cs and Game/Utility/FoeSpawner.cs.

### Enemy perception, pursuit and tactics · NPC-008–016

Game/EnemySenses.cs GetTargets ranks candidates from ActiveGameObjectDatabase plus the player. It checks teams, pacification, hostility and infighting settings. FixedUpdate and sight/hearing helpers manage detection, stealth, concealment, memory, prediction and alert. Language pacification reaches character skills and FormulaHelper. The distinction between a candidate, a detected target and a remembered position is useful. Some decisions use live team/state reads and shared classic cadence. Keep those dependencies explicit so tests can control who is eligible, what was observed and when it expires.

Target scans can enumerate all active enemies per deciding enemy. Aggregate candidate evaluation could approach quadratic growth if many enemies scan a common population. Actual frequency and physics-query costs are unmeasured. Some sight checks already reuse a nonallocating raycast buffer that grows when filled. Its static ownership assumes compatible call scheduling. Preserve reuse if profiling justifies it and measure before adding a spatial index.

Game/EnemyMotor.cs reads perception and movement state to choose destinations, detours, falling/water/flying behavior and combat spacing. OpenDoors and HandleBashing coordinate fixture access with EnemyAttack. Ranged and touch spell choices consider clear projectile paths and EffectsAlreadyOnTarget. Paralysis and knockback can interrupt ordinary steering. The senses/motor/attack split is a useful starting point, but the motor also chooses tactics and checks spell state. The simulation depends on Unity physics queries and animation/attack timing. Preserve the distinction between a request to attack and COMBAT commitment. The source does not establish that a general navigation mesh would reproduce classic detours or work for all dungeon geometry.

### Dialogue, knowledge and quests · NPC-017–023

Game/TalkManager.cs accepts mobile and static actors, sets target context and starts the conversation. It handles reaction, greetings, player tone, knowledge and topic assembly, directions and map marks. It also selects weighted rumors, builds bulletin board output, keeps quest information and post-quest responses, and tracks NPCs offering work. Sharing reply logic across actor types and keeping quest topic cleanup explicit are strengths. Responsibilities span session state, localized answers, content lookup and durable progression. Transition and load callbacks rebuild building/topic context. As content grows, invalidation and side effects become hard to follow through one manager.

SetRandomQuestor picks from the work dictionary keys using a newly constructed System.Random and materializes the keys into a list. GetQuestorName reseeds DFRandom before rendering a name. The rendering call changes shared RNG state, independently of the selection roll. GetQuestorName, GetQuestorGender and GetQuestorLocation index the selected key directly. Removing the selected entry before reading it would make that lookup fail. Normal UI sequencing needs verification. The source uses a name seed as a work dictionary key at removal. Keep name generation and stable actor references separate so actor lookup and quest assignment do not depend on display generation.

### Save and restore · NPC-024

TalkManager.GetConversationSaveData exports quest information, rumors, post-quest replies, work candidates and castle conversation state. RestoreConversationData initializes missing data, removes orphaned quest information and reconciles active quests. Topic and building context is rebuilt on transitions and load. This is a useful split between durable data and derived lists. The save DTO receives the live dictionaries and lists by reference, so it is a view of mutable state until serialization. Whether that matters depends on the serialization schedule.

Game/Serialization/SerializableEnemy.cs registers and restores enemies by LoadID, with a collision workaround that increments conflicting RDB IDs. This resolves duplicates during registration, but the association can depend on registration order when the same base ID collides. Restoring modified layouts or reordered actors requires a fixture. Preserve compatibility with dead actor and quest resource state. Avoid persisting disposable presentation or transient perception state unless continuity requires it.

## Comparison

| Concern | DFU | Proposed Godot design |
| --- | --- | --- |
| Population and encounters | Pooled civilians, layout hashes and activation helpers | Separate pool leases and persistent IDs, with explicit spawn placement results |
| Enemy AI | Senses, motor and attack components driven by engine clocks and shared context | Explicit observations, pursuit state and intent handoffs with local physics adapters |
| Dialogue | One manager owns topics, rumors, offers and map effects | Conversation state and structured replies backed by explicit domain operations |
| Persistence | Enemy LoadIDs and dialogue data reconciled on load | Stable actor and offer references with defined restore order |

Verify pool reuse and enable order, collision identity under reordered layouts, spawn failures, stealth/illusion and allegiance changes, door and hazard traversal, projectile clearance, questor removal and dialogue restore. Profile active-enemy candidate scans and physics queries before optimizing. No runtime, profiling or classic parity tests were performed.
