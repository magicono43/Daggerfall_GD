# UI architecture review

Covers UI-001 through UI-021 in the [feature catalog](../systems/UI_FEATURE_CATALOG.md). Static evidence is from the local DFU 1.1.1 Release snapshot. See the [repository overview](../00_REPOSITORY_OVERVIEW.md) for revision limits. Paths are relative to Assets/Scripts.

## Existing architecture

### Shell, input and extension · UI-001–005

Game/UserInterface/UserInterfaceManager.cs owns the IUserInterfaceWindow stack, lifecycle callbacks and a bounded string message queue. PushWindow calls OnPush, applies pause policy, clears gameplay input and clears an active fade before raising OnWindowChange. ChangeWindow uses the lower-level add/remove paths, so it does not run the same input/fade clearing steps. RemoveWindow calls OnPop and OnReturn, then may resume gameplay and set an activation delay based on stack depth and HUD mode. These are useful centralized lifecycle hooks, but navigation, pause ownership and presentation effects are coupled. PopToHUD in Game/DaggerfallUI.cs repeatedly pops until the current window is the HUD instance. Its guard checks whether HUD is enabled and allocated. If that instance is absent from the stack and popping stops making progress, the loop has no local exit. The normal path depends on the HUD anchoring invariant.

PostMessage clears all pending entries on overflow and keeps the new entry. This is confirmed behavior. DaggerfallUI.Update gives the top window a chance to process messages before the central ProcessMessages switch consumes a message. Preserve routing precedence where it matters, but distinguish commands that require delivery from disposable UI refreshes. Game/DaggerfallUIMessages.cs centralizes names, while string parameters and global routing make invalid payloads and ownership harder to trace.

DaggerfallUI updates the top window and draws through Unity OnGUI. Panel and BaseScreenComponent provide reusable component layout, input and drawing. DaggerfallMessageBox and DaggerfallInputMessageBox reuse modal controls, text tokens and callbacks. The text input window saves/restores IME state around its lifecycle. Verify keyboard/controller focus and cancellation with nested prompts. UIWindowFactory maps window kinds to replaceable classes and calls Activator with caller-specific argument arrays. This supports mods, but incompatible constructor or type errors can surface at creation. Persistent window instances avoid repeated construction and require draft, focus and subscription cleanup on reuse. Rendering and retained resource costs are unmeasured.

### HUD and session navigation · UI-006–010

DaggerfallHUD composes vitals, breath, active spells, compass, mode indicators and temporary notices. HUDVitals, HUDBreathBar and HUDActiveSpells separate views into reusable components. DaggerfallUI supplies shared notice entry points. Preserve the HUD as a reader of gameplay state, with separate persistent indicators and transient messages. Frame updates and texture/layout costs should be measured before introducing event-driven refresh everywhere.

DaggerfallUI.ProcessMessages routes setup, title and cinematic flows. DaggerfallUnitySetupGameWizard, DaggerfallStartWindow and DaggerfallVidPlayerWindow bridge CORE session operations to presentation. Pause options, controls, advanced settings and effect configuration share menu navigation but apply different settings. Keep configuration storage and application in their respective owners, with UI holding an editable draft where cancellation is offered. The save window enumerates saves, updates selection metadata and can call SAVE directly. The classic load window follows a separate entry flow. Retain format-specific selection UI and let CORE/SAVE report operation outcomes. See the [CORE review](CORE_ARCHITECTURE_REVIEW.md) for native load sequencing.

### Character, inventory and reading · UI-011–014

DaggerfallStartNewGameWizard and CreateCharSummary stage and review character creation before handoff. DaggerfallCharacterSheetWindow.UpdatePlayerValues and CheckIfDoneLeveling divide a level reward across entity writes and a window-owned allocation. This confirms a split ownership boundary, with interruption risk addressed in the [CHAR review](CHAR_ARCHITECTURE_REVIEW.md). History and character data are useful separate views.

DaggerfallInventoryWindow selects panes and contextual action modes, maps paper-doll hits, and initiates transfers and item use. The book reader, spellbook and magic item windows offer specialized browsing and selection. These distinct interactions need stable selected identities and explicit cancellation. Eligibility and mutation currently also live in some UI paths, so callers outside the window can bypass policy. Keep sorting, layout, navigation and previews local. Move authoritative transfer, equip, cast and use decisions to their owners. See the [ITEM review](ITEM_ARCHITECTURE_REVIEW.md).

### Dialogue, journal, services and crafting · UI-015–018

DaggerfallTalkWindow presents TalkManager context and topics. Guild and merchant popups route service IDs to focused windows. Quest offer and popup windows handle authored prompts, while DaggerfallQuestJournalWindow builds active-quest and notebook views and can disclose places through FindPlace_OnButtonClick. Preserve the dedicated view models and explicit prompt responses. Topic selection, offer validity and map disclosure need separate owner outcomes so refreshing a view cannot repeat an action.

Trade, banking and property windows present prices and accept confirmation. DaggerfallTradeWindow.ConfirmTrade_OnButtonClick also charges and delivers goods/services. SpellMaker, PotionMaker and ItemMaker build choices and perform crafting operations. Shared editing and confirmation controls are useful. An accepted prompt should commit an explicit owner operation once, with a failure or changed-terms result for the UI. For confirmed settlement and lifecycle evidence see the [ECON review](ECON_ARCHITECTURE_REVIEW.md) and [MAGIC review](MAGIC_ARCHITECTURE_REVIEW.md).

### Maps, paced actions and court · UI-019–021

Dungeon and exterior automap windows present reconstructed location data. TravelMapWindow selects destinations, and TravelPopUp handles options and settlement. RestWindow uses a real-time paced UI loop to advance calendar time, while the transport window offers mode choices. CourtWindow combines verdict decisions, prison presentation, time advancement and release. Keep the pacing and visual feedback in UI, with TIME and LAW owning completion, interruption and recovery. These flows need distinct simulation and view state for save compatibility. Whether saving is supported in an active modal flow should be explicit before defining resumable state. See the [TIME review](TIME_ARCHITECTURE_REVIEW.md) and [LAW review](LAW_ARCHITECTURE_REVIEW.md).

## Comparison

| Concern | DFU | Proposed Godot design |
| --- | --- | --- |
| Navigation and input | Window stack, string queue and shared pause side effects | Explicit modal lifecycle, focus and CORE pause requests |
| Rendering and extension | OnGUI components and reflective replacement | Control views with validated replacement points |
| Player operations | Windows own parts of gameplay decisions and commit | Views submit typed requests and display owner outcomes |
| Prompts and maps | Callback-driven windows and derived map views | Stable choices and explicit refresh/restore boundaries |

Verify nested modals, missing HUD and queue overflow, focus and IME restoration, controller navigation, replacement validation and reuse. Exercise cancelled creation, failed saves, stale selections, changed trade terms, interruption of rest/travel and court release. Profile HUD and map rendering with representative scenes. No runtime, profiling or classic parity tests were performed.
