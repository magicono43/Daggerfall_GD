# Proposed system boundaries

All boundaries are Proposed under [GAD-01 through GAD-12](ARCHITECTURAL_DECISIONS.md). Stable catalog IDs remain intact. A catalog system is a documentation boundary and can contain a few cohesive modules. It does not require a separate process, assembly or manager.

## Ownership and public responsibilities

| System | Authoritative responsibility | Conceptual public contract | Persistence and derived state |
| --- | --- | --- | --- |
| CORE | Application configuration lifecycle, active session, pause reasons and operation admission | Begin/replace/end session, acquire/release owned pause, expose committed phase and readiness | App settings and input profile references. Rebuild service wiring and pause handles on session replacement. |
| DATA | Definition resolution, classic adapters, localization resources and provenance | Resolve a namespaced key from the committed content plan, validate format/references, provide read-only definitions | Definitions live in content packages. Save records refer to keys and versions, with legacy mappings when needed. |
| RULE | Shared arithmetic conventions and random-source contracts | Evaluate calculations with explicit values, units and draws | Owning domains retain gameplay rules. Persist required RNG continuation via the session save projection. RULE owns no character, item or regional state. |
| CHAR | Base actor identity/capabilities, permanent attributes/skills, practice, vitals and pending progression rewards | Query base/live values, apply vital changes, tally practice, validate and commit allocation | Persist base state and pending earned rewards. Derive live modifiers from active MAGIC effects and equipment. |
| ITEM | Item instances, collection ownership, quantities, slot state, condition and physical credit instruments | Transfer/split/merge, equip/unequip, use eligibility and committed item results | Persist instance and source keys plus ownership and slots. Repair condition belongs here, while ECON owns the paid service job and due time. |
| COMBAT | Attack commitment, ordered contact resolution, projectiles and death finalization coordination | Accept attack intent, resolve ordered consequences, report committed hit/death with stable source context | Define explicitly whether pending attacks/projectiles survive save. CHAR owns health, ITEM owns corpse inventory, NPC owns actor lifetime. |
| MAGIC | Learned spell entries, live effect instances, stacking, admission, duration, illness and transformation lifecycle | Ready/commit cast, deliver effect, query capability modifiers, advance/cure/remove effects | Persist effect keys, sources, remaining state and exceptional payload versions. Learned spell membership is exposed through actor identity. Rebuild movement and presentation consequences. |
| NPC | Actor spawning/leases, AI observations and intent, conversation state and durable knowledge | Place/activate actor, query allegiance/threat, submit attack intent, produce structured replies | Persist durable actors and knowledge. Discard pool lease handles. QUEST owns offer validity and resource relationships. |
| QUEST | Quest definitions after validation, instances, tasks, clocks, resource links, globals and quest journal facts | Select/start/advance/end quest, consume resource signals, execute owner requests, provide prompt/journal data | Persist stable action/resource keys and task progress. Relink world representations after relevant identities exist. |
| FACT | Faction graph, standings, political state, memberships and guild entitlements | Change standing under explicit propagation policy, evaluate rank and service entitlement | Persist mutable standings, relationships and memberships separately from content definitions. LAW retains regional legal standing. |
| LAW | Charges, jurisdiction, warrants, trial decisions and sentence state | Report incident, decide pursuit/arrest, resolve plea, complete sentence/release | Persist required regional legal state and permitted pending cases. FACT applies faction spillover through its own operation. |
| ECON | Accounts, debt, regional prices, quotes, paid service jobs, deeds and rentals | Quote/revalidate/settle trade or service, grant entitlement, advance deadlines | Persist balances, obligations and entitlement IDs. ITEM supplies physical coin/credit and inventory operations. LOC consumes property access. |
| WORLD | World coordinates, region/location context, tile residency, world variant selections and exterior discovery | Query context/candidates, request residency, report geometry readiness, apply rebase, mark discovery | Persist durable exploration, variants and world context. Regenerate terrain from versioned source inputs where possible. |
| LOC | Buildings/interiors/dungeons, marker graph, doors/actions, local discovery and map notes | Resolve scoped record/marker, assemble layout, operate fixture, provide local state/readiness | Persist local deltas and discovery by stable scoped keys. WORLD controls residency, while MOVE places actors. |
| MOVE | Input intent interpretation for movement, actor physics modes, interaction targeting and placement | Consume intent, query collision/probes, resolve placement, route typed interaction | Persist required pose, posture and valid traversal context. Rebuild transient contacts. Route law, loot and dialogue actions to their owners. |
| TIME | Calendar, crossed-boundary policy, weather state, rest and travel orchestration | Advance time with reason, expose ordered boundaries, quote trip time, stop/complete paced activity | Persist clock/weather and supported pending activities. Owners update their deadlines and recovery under the ordered contract. |
| UI | Navigation, focus/input capture, editable drafts, prompts and read-only gameplay views | Submit owner requests, display outcomes, return choice/cancel, invalidate views | Persist user preferences and intentional notebook edits through their owner. Pending simulation rewards or sentences belong to gameplay owners. |
| AV | Engine meshes/materials, render passes, audio/video backends and feedback resource lifetime | Render committed world/actor context, consume cues, report playback outcome | Rebuild graphics/audio state. Persist preferences or playback progress only when explicitly required. |
| SAVE | Capture/publication protocol, schema envelope, operation errors and restore coordination | Capture owner projections, migrate/validate, publish generation, coordinate phased restore | Own stored generations and manifests. Owners define payload meaning and compatibility. SAVE does not become the owner of every captured field. |
| MOD | Package metadata, enabled plan, dependency order, registration and provider identity | Resolve package plan, validate hooks, activate extensions, report conflicts | Persist package identity/version plan as compatibility metadata. DATA resolves content and owners hold mod-created gameplay state. |
| DEV | Inspection, diagnostics, fixture control, validation and export tools | Query diagnostic views and invoke production operations with explicit context | Optional evidence and fixture records. Development tools do not bypass invariants required by ordinary entry points. |

This reallocates responsibilities currently colocated in PlayerEntity, PlayerActivate, FormulaHelper and UI windows. It is a proposal for the new RPG, with traceability in [the global review](GLOBAL_ARCHITECTURE_REVIEW.md). Coherent ownership costs additional handoffs but permits local tests and prevents multiple writers to the same field.

## Identity and lifetime contract

A definition key identifies authored content under a package/domain namespace. A durable instance ID identifies a character, persistent actor, item, quest or live effect. A layout reference includes location, variant/version and record/marker key. A transient handle identifies a currently resident engine object or pool lease and must be rejected after release. Display names, name seeds, current transforms and engine node paths are presentation or lookup inputs rather than durable identity.

CORE creates and retires the session. Each owner creates and retires its instances. A lightweight shared resolution contract locates registered instances after hydration. Registration is scoped to session and object category, rejects ambiguous IDs and releases subscriptions on teardown. ITEM transfer changes ownership while retaining instance identity unless stacking deliberately merges records, in which case the result reports the surviving ID. QUEST keeps its resource identity when its scene representation unloads. NPC recycle expires the lease without implicitly deleting a quest actor. These contracts follow GAD-01/02. A generic entity component system is an optional implementation choice.

## Requests, results and notifications

Queries return read-only values or projections. Requests carry source, target IDs, relevant context and any expected version/quote. The owner validates and returns committed, rejected, deferred or failed with a reason and resulting identities. An asynchronous request additionally exposes cancellation policy and a completion outcome. A success notification follows committed state, so observers can query a consistent snapshot. Notifications must not serve as a substitute for required payment, inventory transfer or reference linking.

Use ordered direct calls for required consequences. Defer notifications that would otherwise reenter an active mutation. Subscription lifetime belongs to the session or view. Define ordering only where observable behavior requires it. A global event bus or event-sourced state store would add replay and tooling obligations and is not required by these proposals. This contract resolves the partial-state callback and duplicate-notification risks documented in CORE-015, QUEST-008 and COMBAT-011.

## Shared operations

| Operation | Conceptual handoff and commit condition | Rationale and trade-off |
| --- | --- | --- |
| Attack | NPC/MOVE intent → COMBAT acceptance → contact and RULE evaluation → ordered ITEM/MAGIC consequences → CHAR vital outcome → NPC/QUEST death association → AV/UI cue | One source context and commit marker prevent repeated effects. Preserve explicit phases where callbacks need updated state, rather than assuming a fully precomputed effect list. |
| Equip | ITEM validates ownership, restrictions and conflicts → commits slot delta → MAGIC rebuilds held effects → CHAR derives armor/capabilities → AV/UI refresh | A single slot owner avoids repeated unequip dispatch. Required effect cleanup needs a result/recovery policy, while cosmetic failures can be reported independently. |
| Purchase/crafting | ECON or MAGIC validates quote/recipe → ITEM validates quantities and capacity → payment and output changes commit → observers receive result | Retain the source and funds on validation failure. A short local coordinated operation is sufficient until recoverable multi-stage services require receipts. |
| Quest offer | FACT/CHAR/NPC eligibility context → QUEST selects validated definition and captures giver/resource IDs → world binding accepted/deferred → registration committed → NPC/UI notification | Makes source and binding failure visible. Prevalidating every possible site is expensive, so permit deferred placement with an explicit state. |
| Rest/time jump | TIME accepts mode and interval → ordered interruption boundaries and owner updates → CHAR recovery and MAGIC/QUEST consequences → TIME stop/complete result | UI only paces display. Bulk advancement is allowed for equivalent policies, with stepping for order-sensitive interruptions. |
| Travel/recall/release | TIME/MAGIC/LAW submits destination and actor context → ECON validates any payment → WORLD/LOC prepare destination → MOVE places actor → operation publishes placement completion | Separate settlement from readiness. Full world rollback is costly, so define preflight and safe fallback after replacement. |
| Save/load | CORE admits operation → SAVE captures or validates → owners hydrate under a gate → identity resolution and world readiness → derived state and UI refresh → CORE resumes eligible play | Avoid effect replay and stale callbacks during restore. Optional previews or diagnostics must not determine core validity. |

## Engine and extension boundaries

Godot scene references belong in composition and physics/render adapters. Format conversion, pricing, progression, calendar arithmetic and quest validation should accept data without a live scene where practical. A scene can still own a cohesive controller. Pass small explicit domain access to collaborators instead of turning CORE into a universal mutable locator.

MOD validates the package plan before DATA resolves definitions and before owner registration becomes active. Content lookup reports provider and conflict policy. Owners expose a limited set of typed extension hooks, with signatures and replacement/additive/notification semantics checked before use. Supporting arbitrary executable code requires an explicit trust and lifecycle choice under GAD-10. Data-only content can precede that choice without forcing a scripting runtime.
