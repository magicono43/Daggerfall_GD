# Global architecture review

Prompt_4 synthesis, reviewed on 2026-11-05. Scope includes all 21 catalogs and architecture assessments. The source baseline remains the local DFU 1.1.1 Release snapshot with unresolved exact commit and patch provenance. Targeted source checks reconfirmed lifecycle notification order, native restore order and enemy/corpse/item linking. This is static analysis. A code path establishes ordering or a reachable branch under its prerequisites, while player-visible frequency, parity and performance need runtime evidence. [Repository baseline](../00_REPOSITORY_OVERVIEW.md)

The highest rework risks concern identity and ownership, session and restore phases, time and random sequencing, and atomic gameplay operations. The proposed architecture is a modular game in one process, with explicit domain state and small contracts. Godot scenes supply composition, physics and presentation adapters. The proposal requires no universal entity framework, global command bus or workflow engine. Such infrastructure would add lifecycle and debugging costs before requirements justify it.

The [decision register](ARCHITECTURAL_DECISIONS.md) separates Proposed from Approved entries. No architecture approvals were found. The [boundary document](PROPOSED_SYSTEM_BOUNDARIES.md) assigns responsibilities and conceptual contracts. The [dependency analysis](../04_DETAILED_DEPENDENCIES.md) defines arrow direction, typed graphs, evidence and conditional parallel domains.

## Persistent ownership and shared records

In DFU the object holding a field, the serializer writing it and the feature determining its meaning are often different. The proposed owners below distinguish those roles. A record in SerializablePlayer does not make CHAR the correct semantic owner of every field.

| Durable data | Observed DFU storage and shared use | Proposed authority and trade-off |
| --- | --- | --- |
| Character identity, career, stats, skills, practice and vitals | DaggerfallEntity/PlayerEntity, CharacterDocument and SerializablePlayer. Movement, combat, magic, guilds and UI read or mutate values. | CHAR owns base state and pending rewards. Domains submit validated changes. More calls are needed, but UI allocation and restoration can share rules. CHAR-011–023, CHAR-AR-02/03/05. |
| Items, quantities, slots and condition | DaggerfallUnityItem UID, ItemCollection and ItemEquipTable. Quest links, enchantments, credit and expiry travel with items. | ITEM owns instances and physical collection changes. ECON owns balances and paid jobs, MAGIC owns live effects, QUEST owns resource links. Cross-owner references require staged relinking. ITEM-001, 005–014, 023–025. |
| Effects, illness, transformation and learned spells | EntityEffectManager live bundles and effect payloads, actor spell lists and SerializablePlayer. Teleport also saves anchor state already mapped on the player. | MAGIC owns effect lifecycle and actor spell entries, CHAR owns base identity, MOVE owns one durable recall/placement context. Existing anchor data needs a migration if adopted. MAGIC-010/011/024/028/029, MAGIC-AR-03/05. |
| Actors and conversation knowledge | Enemy records and LoadIDs, placed NPC position hashes, pooled civilians, TalkManager dictionaries and work keys | NPC owns durable actors and knowledge. Separate transient leases from persistent actor keys. More identity validation is needed than using a transform or name seed. NPC-001–004/023/024, NPC-AR-01/05. |
| Quests, tasks, clocks, resources, globals and journal | QuestMachine, Quest, Task, Place and resource records, plus PlayerEntity.GlobalVars and TalkManager links | QUEST owns quest facts and globals. | Faction standing, political relationships and membership | PersistentFactionData, PlayerEntity regional records and GuildManager ordinary/vampire membership dictionaries | FACT owns mutable political and membership state. | Position, residency and discovery | StreamingWorld/GPS, world compensation, variants, building discovery, Automap dictionaries and local serializers | WORLD owns global context/variants/exterior discovery, LOC local state/discovery, MOVE actor pose. DATA definitions stay content. UI/AV caches and active callbacks are reconstructed. CORE-001–006, MOD-014/015, SAVE-001–018. |

Shared mutable structures include entity records, item references, equipment UID arrays, faction graphs, quest site links, conversation dictionaries and discovery dictionaries. Some save getters return live collections, and discovery capture also prunes them. Direct modification crosses boundaries in UI level rewards and trade, FormulaHelper attack effects and regional prices, PlayerActivate legal consequences, and special effects that change equipment or world state. These observations support explicit owners and snapshot contracts, rather than proving a need to replace every shared value type. ## Identity and propagation

| Identity domain | Current identity and risk | Proposed contract |
| --- | --- | --- |
| Content | Classic indexes, filenames, effect keys, spell indexes and package GUID/filename. Resolution and saved payload keys differ. | Namespaced definition key and provider/version, with classic mappings. |
| Item | UID distinguishes an instance. Stack merge retains one instance and split creates another record. Custom className participates in restore. | Stable instance ID, explicit merge result and registered behavior key. |
| Actor | Player/entity behavior references, enemy LoadID, layout position hashes, pool objects and name seeds | Durable actor ID where continuity matters, transient lease handle for disposable population. |
| Quest | Instance UID, resource Symbol, action runtime types and site links | Quest instance plus scoped resource/action identity and versioned definition reference. |
| Location and fixture | Map pixel/map ID, packed building key, scene name and LoadID derived from layout | Explicit global location, variant and scoped record identity, separate from local engine coordinates. |

Identity proposals require decisions on allocation, collision rejection, migration and lifetime. Fixed classic indexes can remain inside adapters. New content does not need a globally allocated numeric range if domain/package scope is explicit. GAD-01/07/10 balance additional validation against compatibility with content changes.

DFU propagates behavior through direct calls, C# events, Unity messages, polled flags, queued UI strings, animation markers and registry lookup. Examples include item slot callbacks into MAGIC, state events into MOD, quest completion into guild policy, and death flags consumed by EnemyDeath. A notification may precede full mutation, as StateManager publishes before updating GameInProgress. A successful scheduled quest emits its started notification twice. These are source observations. Their consequences depend on subscriber behavior. [CORE-015](../systems/CORE_FEATURE_CATALOG.md), [QUEST-008](../systems/QUEST_FEATURE_CATALOG.md)

GAD-09 proposes required owner operations followed by committed notifications with explicit subscription lifetime. Queries and notifications can carry stable IDs and small values. Asynchronous placement and prompts carry a request/continuation identity and cancellation policy. This adds state where a bare callback was sufficient, but makes retries, load and stale targets reviewable. Notification delivery is not assumed to provide exactly-once execution across crashes. Durable receipts are warranted only for effects that require retry across persisted operations.

## Save and lifecycle integration

DFU's native load resets current state before some file decoding, then restores time and contextual records, quests and dialogue, world variants and placement, waits for respawn/registration, applies registered object state, restores auxiliary data and publishes OnLoad. Early missing-component branches can retain the busy flag. Full save writes several files sequentially, while the transition cache persists a smaller subset of object categories. A scene cache and a complete save therefore have different continuity policies. [SAVE-006–017 and SAVE-AR-01/02/03](SAVE_ARCHITECTURE_REVIEW.md)

The proposed restore contract has six stages. First validate package/definition compatibility, schema and required data. Second admit session replacement and hydrate clock, world variant and entitlement context under a simulation gate. Third construct base actors, inventory, quests and layouts without ordinary gameplay side effects. Fourth register identities and resolve caster, item, quest-resource and fixture references after dependencies exist. Fifth rebuild effects, capabilities, visual state and derived indexes, with explicit reconciliation for optional missing data. Finally publish one completion outcome and resume eligible play. The exact order within a stage follows real dependencies, rather than one global order for all fields. Deferred site binding is permitted for unloaded locations.

Capture similarly requires a coherent state boundary and one publication outcome for a generation. A single file or staged directory can satisfy this, subject to platform testing. Required payload failure invalidates publication. Optional preview or diagnostic failure can produce a usable save with a warning. Optional mod data requires an explicit policy for preservation, discard or incompatibility. These choices increase format discipline but prevent old sidecars silently appearing current. GAD-03/04/10 record these as proposals.

## Consistent patterns and decisions before implementation

Preserve the recurring strengths of format adapters, keyed definitions, separate instances, per-domain serializers, staged task removal, reusable scalar formulas, specialized motors and owner-specific extension hooks. Incompatible contracts concern source precedence, replacement versus additive hooks, notifications before versus after mutation, live save references versus snapshots, and different restore failure policies. Consistency is needed at boundaries while domain rules retain their differences.

The critical early decisions are GAD-01 through GAD-10, with GAD-11's render composition and input lifecycle established before their consumers depend on them. GAD-12 supplies evidence for those contracts. Late changes to IDs, save versions, coordinate units, clock/RNG ordering, resource ownership or content precedence can invalidate authored content and saved state. Rendering polish, spatial indexing, broad executable extension APIs and advanced authoring tools have lower deferral cost when their boundaries are explicit.

Potentially parallel domains include content/translation validation, character and inventory rules, world/layout generation, presentation views, political/legal/economic calculations, quest/dialogue interpretation and save publication diagnostics. Their independence depends on shared identity, time and outcome contracts. Full combat/effects/AI, world placement/quest binding, and save reconstruction remain integration clusters. The dependency document specifies the prerequisites and trade-offs for each domain.

Further evidence is needed from representative classic archives and saves, scene/prefab wiring, long time jumps, interruption/failure traces, mod combinations, audio/render output and performance measurements. Gameplay test coverage and external CI remain unverified. The recommendations are conceptual proposals for a similar RPG and do not establish exact classic parity or approved implementation specifications.
