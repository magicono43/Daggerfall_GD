# CHAR architecture review

This review covers CHAR-001 through CHAR-023 in the [character and progression feature catalog](../systems/CHAR_FEATURE_CATALOG.md). Evidence comes from static inspection of the local DFU 1.1.1 Release snapshot. Source paths are relative to Assets/Scripts. The [repository overview](../00_REPOSITORY_OVERVIEW.md) records the limits of revision identification. Classic data fidelity, runtime sequencing and mod combinations remain open.

## Existing architecture

### Creation and handoff · CHAR-001–010

- **Flow and identity (001–002, 007, 010).** DaggerfallStartNewGameWizard owns the window sequence. Close handlers copy race, gender, name, face and reflex choices into CharacterDocument. TriggerGame passes the document to StartGameBehaviour and requests new-character entry. The document is a useful handoff that keeps partially completed UI state out of the live character. PlayerEntity.AssignCharacter owns initial assignment. FacePicker is presentation. Reflex selection has simulation consequences through PlayerEntity.RaiseSkills, so its effective meaning needs to remain visible beyond the wizard.
- **Career and biography (003–006).** The wizard gets preset careers from ClassFile and uses the questionnaire or explicit selection. Custom creation reads the edited DFCareer and reputation selections, then uses BiogFile.GetClassAffinityIndex for biography selection. CreateCharCustomClass and CreateCharSpecialAdvantageWindow carry hit-point and special-trait decisions. Biography selection returns effects and backstory, and BiogFile.ApplyEffects can act directly on PlayerEntity. The legacy career record and biography input are reusable. Rule evaluation, localized labels, and draft mutation are spread across windows and import code. This makes validation outside the original UI more expensive.
- **Rolls and allocation (008–009).** CreateCharAddBonusStats and CreateCharAddBonusSkills use StatsRollout and SkillsRollout. The wizard copies starting and working values and restores them when revisiting steps. Keeping the starting values separate is useful for showing what an allocation changes. Several UI objects carry copies of the draft, so backtracking and rerolls require sequence tests to establish when points and rolls are retained.

Evidence includes Game/UserInterfaceWindows/DaggerfallStartNewGameWizard.cs close handlers and TriggerGame, the CreateChar windows, Game/Player/CharacterDocument.cs, API/ClassFile.cs, API/DFCareer.cs and API/BiogFile.cs.

### Stats, advancement and persistence · CHAR-011–017

- **Base and live values (011).** DaggerfallStats and DaggerfallSkills distinguish permanent values from live values with effect adjustments. DaggerfallEntity.ClearConstantEffects provides a reset point for transient modifiers. This is a useful boundary for progression, which reads permanent skill values. SAVE and MAGIC need an explicit order for restoring base data and reconstructing effects.
- **Practice and mastery (012–014).** Weapon, spell and movement paths report skill use through PlayerEntity.TallySkill. RaiseSkills checks the death guard and a strict elapsed threshold above 360 classic minutes, then applies FormulaHelper thresholds, reflex scaling, and mastery rules. Rest and travel UI invoke it at defined completion points. A qualifying tally resets before the cap/mastery check, so the use balance can clear even if the skill cannot rise. The code sums selected skills against a starting baseline and latches readiness in CheckForLevelUp. FormulaHelper provides reusable calculations. RaiseSkills also performs mutation, popups, fanfare, and sheet opening, which makes it hard to exercise as a simulation step. TallySkill uses compound addition into a short before clamping. A sufficiently large positive amount can wrap and clamp to zero instead of saturating at 20,000. The arithmetic path is confirmed. Reachability through ordinary callers is unmeasured.
- **Rewards (015).** DaggerfallCharacterSheetWindow.UpdatePlayerValues consumes ReadyToLevelUp and OghmaLevelUp. For a normal reward it increments Level and MaxHealth and generates the point pool. For Oghma it uses a fixed pool. The UI holds the pool and working stats until CheckIfDoneLeveling commits them. OghmaInfiniumEffect writes the same two flags. This confirms a split commit across entity state and window state. Coexisting rewards and interrupted allocation are risks. The reviewed SerializablePlayer mapping has no pending reward or point-pool field. Normal UI save gating may constrain exposure and needs runtime verification.
- **Training (016).** DaggerfallGuildServiceTraining checks the cooldown, offers a guild price, and builds a list from the guild or temple. At selection it rebuilds the list and indexes it by picker position, tests the permanent skill against the guild limit, deducts gold, then updates last training time, advances three hours and tallies skill use. The initial affordability check and later deduction are separate. The deduction result is ignored at the commit call site. This creates a potential stale-quote or partial-purchase path if money or the offer changes while the picker is open. Retain guild ownership of offers and the distinction between paid practice and immediate skill increase.
- **Restore (017).** PlayerEntity.AssignCharacter and Reset establish initial/live state. SerializablePlayer stores skill-use counters and progression sums, recomputes a zero current sum, estimates a missing or nonpositive starting baseline, and supplies a default array for null SkillUses. These fallbacks preserve older data. The array assignment and null fallback do not validate a non-null array against the current skill count at those call sites. Compatibility across reordered skills or malformed save data needs fixtures.

Evidence includes Game/Entities/PlayerEntity.cs (TallySkill, RaiseSkills, SetCurrentLevelUpSkillSum, CheckForLevelUp and EstimateStartingLevelUpSkillSum), Game/Entities/DaggerfallStats.cs, Game/Entities/DaggerfallSkills.cs, Game/Formulas/FormulaHelper.cs, Game/Serialization/SerializablePlayer.cs and the windows/effect named above.

### Vitals, transformations and survival · CHAR-018–023

- **Pools and transformation (018–019).** DaggerfallEntity centralizes setters for health, fatigue, magicka and breath. Setters support restore behavior and entity events can be quiesced. PlayerEntity adds player-specific rules, including guild death avoidance and cheat overrides. GetLiveRaceTemplate separates effective race from character creation identity. Transformation grants have dedicated PlayerEntity methods, and classic import reconstructs transformation state through effects. Keep the distinction between saved identity and active effect, and verify that granting/restoring spells is repeatable without duplication.
- **Activity and recovery (020–021).** PlayerEntity.Update and FixedUpdate combine motor state, elapsed game minutes, fixed-step practice and activity-specific fatigue costs. DaggerfallRestWindow uses FormulaHelper recovery rates. PlayerEntity's exhaustion path repeats the health/fatigue/spell-point rate calculation and application sequence. The shared formulas are worth keeping. Separate callers can legitimately advance different amounts of time or trigger different side effects, so verify behavior before consolidating. Runtime fatigue rates and rest interruption remain fixture-dependent.
- **Collapse and death (022–023).** Fatigue exhaustion notifies PlayerEntity_OnExhausted, which checks threats through GameManager and drives either a recovery/collapse path or lethal outcome. The handler guards against repeated popup and already-dead cases. SetHealth can invoke guild prevention before emitting death. PlayerDeath coordinates presentation, exposes OnPlayerDeath, and requests title return through StartGameBehaviour. Preserve that simulation-to-presentation handoff. Ensure repeat writes at zero and restore-time writes cannot replay consequences unexpectedly. There is no measurement of these paths under overlapping damage, exhaustion, rest and load.

Evidence includes Game/Entities/DaggerfallEntity.cs (SetHealth, SetFatigue, SetMagicka and event raisers), Game/Entities/PlayerEntity.cs (GetLiveRaceTemplate, FixedUpdate and PlayerEntity_OnExhausted), Game/UserInterfaceWindows/DaggerfallRestWindow.cs, Game/PlayerDeath.cs and Game/Utility/StartGameBehaviour.cs.

## Comparison

| Concern | DFU | Proposed Godot design |
| --- | --- | --- |
| Character creation | Window sequence builds CharacterDocument | UI edits one draft and hands off validated initialization |
| Progression | Entity methods calculate, mutate and present | Progression owner returns results for UI and other consumers |
| Rewards and training | Windows own parts of the transaction | Character and service owners validate and commit changes |
| Restore and survival | Field mapping, entity events and UI-driven flows | Explicit base state, restore order and committed vital outcomes |

Verify preset and custom backtracking, roll replay, strict skill-check thresholds, large counters and cap/mastery cases. Exercise simultaneous normal and Oghma rewards, allocation interruption, stale training offers, old-save baselines and transformation restoration. Compare rest, travel, exhaustion and lethal damage sequencing with representative fixtures. No runtime or classic parity tests were performed.
