# QUEST architecture review

Covers QUEST-001 through QUEST-023 in the [feature catalog](../systems/QUEST_FEATURE_CATALOG.md). Evidence comes from static inspection of the local DFU 1.1.1 Release snapshot. The exact commit is unavailable in the [repository overview](../00_REPOSITORY_OVERVIEW.md). Paths below are relative to Assets/Scripts/Game/Questing unless specified.

## Existing architecture

### Discovery, eligibility and compilation · QUEST-001–007

QuestListsManager discovers packs and parses lists, builds guild/social pools using membership, faction, reputation and rank, and dispatches automatic starts. SelectQuest draws one candidate and returns null on load failure. This preserves a simple selection policy, but a broken entry can suppress an otherwise available offer. A fallback draw would change probabilities and random consumption. LoadQuest checks loose files before consulting ModManager by filename. Keep selection, eligibility and source precedence independently observable.

Parser separates QRC messages from QBN resources and tasks. Task.ReadTaskLines matches source against registered IQuestAction templates and instantiates actions through CreateNew. QuestMachine.GetActionTemplate uses the first matching pattern, scanning in registration order. An unmatched line is logged and ignored. This helps tolerate unsupported legacy scripts, but a required modded action can be skipped and leave a quest that starts yet cannot progress. Overlapping grammar patterns are resolved implicitly by ordering. Compile cost grows with lines and tested patterns. It has not been profiled.

QuestMachine.ParseQuest reseeds Unity random before parsing. Site choice and other generation can therefore depend on parse order and affect other consumers of the global generator. Parser.ParseLocalized, RestoreLocalizedQuestMessages and Utility/QuestMacroHelper.cs provide separate localization and expansion paths. Keep message identity and dynamic resource context distinct from the rendered string.

### Execution, clocks and termination · QUEST-008–011, 023

QuestMachine accepts immediate starts and queues starts for Tick. StartQuest(Quest) starts the instance, adds dialogue data, registers the quest, emits OnQuestStarted and attempts to bind the last clicked NPC. Tick calls that method for queued quests and emits OnQuestStarted again after it returns. This is a confirmed duplicate notification on successful scheduled starts. Subscriber impact, including one-time tracking in QuestListsManager, depends on idempotence. Binding through LastNPCClicked makes the giver context implicit. Start mutates several owners before reporting completion, so an exception can leave partial startup work.

Quest.Update ticks resources, traverses tasks, flushes task messages and clears pending click rearms after each task. The comments explicitly describe first-come ownership of a click. Preserve this sequencing, including dropped tasks, rising-edge or rearm behavior and early exits, in compatibility fixtures. Task.GetTriggerValue and SetTriggerValue can read/write PlayerEntity.GlobalVars, so task state can have an external owner. Clock saves a world-time sample and remaining duration. Travel-derived deadlines use a travel estimate and a minimum duration. Test large time jumps, recurring tasks and reload at a deadline before changing the time model.

Tick stages tombstones and removals after quest updates. Completed quests can retain dialogue links for a week. Unprotected failures are logged and scheduled for removal, while protected quest failures are recorded and the quest can be ticked again. The latter preserves protected content but can repeat failure or earlier side effects. StoreQuestException and Game/UserInterface/HUDQuestDebugger.cs provide diagnostics. Keep quest identity in failure reports and make retry policy explicit.

### Sites and resource binding · QUEST-012–017

Place resolves local, fixed, remote town, dungeon and exterior sites. Remote town search bounds attempts and relaxes some house requirements before failing. GetSiteMarker chooses compatible markers, and AssignQuestResource links a resource symbol to a concrete site through the quest machine. Location predicates and reveal actions consume those references. This distinction between a logical place and a physical marker supports procedural offers and streamed geometry. Candidate scans and retries can require repeated data access. Profile representative archives before indexing.

Person, Item and Foe carry quest-owned state. PlaceNpc, PlaceItem and PlaceFoe connect that state to the world. QuestResourceBehaviour.DoClick bridges interaction, while enemy death and quest foe conditions synchronize through resource state. Ownership crosses NPC, ITEM, COMBAT and WORLD. Culling or rebinding needs to distinguish a destroyed scene representation from removal of the underlying quest resource. Keep placement identity independent of localized names and transient scene objects. Verify missing markers, multiple resources competing for a site, and repeated scene assembly.

### Player-facing actions and domain side effects · QUEST-018–021

Quest owns messages and log steps, while Prompt, PromptMulti and JournalNote handle authored presentation. Rewards and reputation changes reach gameplay owners through actions such as PayMoney, GivePc, ChangeReputeWith and LegalRepute, plus GuildManager's completion subscriber. StartQuest and RunQuest chain instances, and global-linked tasks coordinate through PersistentGlobalVars. Weather, TeleportPc, CastSpellDo, SetPlayerCrime and TrainPc cross feature boundaries. Per-action classes are readable extension points. Their direct use of live services makes failure, retry and testing behavior action-specific. Preserve explicit source order and distinguish irreversible changes from repeatable queries or notifications.

### Persistence and recovery · QUEST-022–023

QuestMachine.GetSaveData and RestoreSaveData preserve quest state and site links. Quest and Task restore their own records. Task.RestoreSaveData reflects over the serialized action type and invokes its Quest constructor before restoring state. A missing type or incompatible constructor can fail restoration of that quest. The machine logs per-quest failures, reassigns legacy markers and removes stale links. It adds the restored quest to the dictionary before reassigning markers, within the same try block. A marker reassignment exception can therefore be logged as a failed load while the already-added quest remains registered. This is a confirmed ordering risk. Recovery behavior in representative saves remains untested. World components restore separate quest resource links, so quest availability, site resolution and object binding require a defined order.

## Comparison

| Concern | DFU | Proposed Godot design |
| --- | --- | --- |
| Offers and parsing | Ordered pack lookup and parse-on-selection | Validated definitions with explicit offer and source policies |
| Runtime | Tick-driven quests, task order and cross-system actions | Explicit lifecycle and ordering with owner operations |
| Resource placement | Site links and scene resource components | Stable resource references with readiness-aware binding |
| Restore | Serialized action types and per-quest exception recovery | Versioned action keys, staged restoration and visible recovery states |

Verify a story quest and repeatable offer end to end. Exercise conflicting action patterns, invalid pool entries, immediate/scheduled starts, shared clicks, clock jumps, protected faults and interrupted effects. Test missing packages and failed marker reassignment across save/load. Profile parsing and site searches before optimizing. No runtime, profiling or classic parity tests were performed.
