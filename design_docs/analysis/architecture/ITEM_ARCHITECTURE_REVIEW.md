# ITEM architecture review

This review covers ITEM-001 through ITEM-025 in the [feature catalog](../systems/ITEM_FEATURE_CATALOG.md), using static inspection of the local DFU 1.1.1 Release snapshot. The exact commit is unavailable in the [repository overview](../00_REPOSITORY_OVERVIEW.md). Source paths are relative to Assets/Scripts. Runtime frequency, performance and classic compatibility require fixtures.

## Existing architecture

### Templates, instances and construction · ITEM-001–004

Game/Items/ItemBuilder.cs constructs item instances from template and group data, with specialized construction for weapon materials, armor and clothing variants, potions, magic items and filled soul traps. Game/Items/ItemHelper.cs loads templates and registers mod types and use hooks. DaggerfallUnityItem carries the instance UID, mutable item data and behavior. This supports a shared definition with distinct physical instances and keeps construction rules in one place. Legacy numeric identifiers and material mappings are useful compatibility inputs. The factory also embeds category-specific selection rules, so adding content can require code changes. Keep stable legacy mappings and move editable weights or definitions into validated data when a content need warrants it.

ItemCollection.DeserializeItems can recreate a registered custom class using the saved className and Activator. If the class is unavailable, it constructs a base DaggerfallUnityItem from the same data. This preserves an item where a mod type is absent, while its custom behavior may disappear. Runtime type registration and the save contract are coupled. The missing-type policy should be explicit for behavior-critical items. See Game/Items/ItemCollection.cs and Game/Items/ItemHelper.cs.

### Collections, capacity and currency · ITEM-005–009

ItemCollection distinguishes UID membership from stack equivalence. FindExistingStack checks group, index, message, potion recipe and expiry, plus stack eligibility from FormulaHelper.IsItemStackable. These distinctions protect several important cases, especially potion variants and separately expiring stacks. Other state is outside the equality test. Mod-enabled stacking needs a contract for which mutable fields and quest links can safely merge. AddItem merges before the duplicate UID check and returns void. When no merge occurs, it logs and refuses a duplicate UID. Transfer calls source.RemoveItem and then AddItem without observing either outcome. A destination rejection after source removal can therefore lose the source entry. This path is confirmed for a duplicate UID that cannot merge. Ordinary reachability is unmeasured.

SplitStack returns the original for a full split and constructs a base item copy for a partial split, then inserts it with noStack and reduces the original quantity. Test custom subclass behavior and reference preservation when split/merge changes UIDs. RemoveOne, TransferAll and selective GetItem support common inventory flows. Linear stack search and weight summation are simple for small inventories. Repeated insertion during large loot transfers may be costly, and no measurement establishes a need for an index.

DaggerfallInventoryWindow checks player and wagon capacity and wagon access around transfers. A caller using ItemCollection directly does not automatically inherit UI checks. This flexibility matters for system grants and restores, but inventory commands need an explicit capacity policy. PlayerEntity.GetGoldAmount and DeductGoldAmount combine coin balance and credit items, while physical gold items can appear in a collection. Preserve the distinction between physical transfers and service settlement. See Game/UserInterfaceWindows/DaggerfallInventoryWindow.cs and Game/Entities/PlayerEntity.cs.

### Equipment, condition and repair · ITEM-010–014

ItemEquipTable selects slots, resolves hand conflicts, updates item slot state and invokes StartEquippedItem and StopEquippedItem through EntityEffectManager. DaggerfallInventoryWindow applies player restrictions and renders paper doll/accessory state. DaggerfallEntity derives armor values from equipment. The table provides a useful single location for slot conflict logic. Player-facing checks in the window still need an owner-level policy for callers outside the UI.

The list-taking UnequipItem overload calls the slot overload, which already calls StopEquippedItem on a removed item. The wrapper then calls StopEquippedItem again. Both calls reach the effect manager when its prerequisites hold. This is a confirmed duplicate dispatch. Whether it changes a particular enchantment depends on its unequip behavior. DeserializeEquipTable links saved UIDs to inventory items and sets EquipSlot without executing normal equip callbacks. That distinction is useful for restoration. Invalid array length returns before clearing the table, so callers need a policy for invalid restore input.

DaggerfallUnityItem.LowerCondition and ItemBreaks coordinate item wear, unequip and optional removal. COMBAT provides hit-driven wear and MAGIC supplies break/held effects. Preserve the ordering between condition reaching zero, enchantment cleanup and ownership changes. ItemRepairData stores scene name and world time on LeaveForRepair, exposes completion and persists an ItemRepairData_v1 record. Its GetDaysLeftUntil subtracts unsigned timestamps before converting to float. A past completion time can underflow if a caller requests remaining days without first checking completion. The arithmetic is visible. UI exposure needs verification. See Game/Items/ItemEquipTable.cs, Game/Items/DaggerfallUnityItem.cs and Game/Items/ItemRepairData.cs.

### Use, identification and presentation · ITEM-015–019

DaggerfallInventoryWindow.UseItem first lets the item's virtual method handle use, then checks quest behavior, then a registered template handler, then built-in actions. Quest handling can consume the interaction or show a message before continuing. A linked quest that cannot be found throws in this path. This explicit extension order is valuable, but combining it with book and map presentation, spellbooks, consumable effects, torch/fuel control and UI transitions makes additions harder to audit. ItemHelper resolves long names and inventory images, while IdentifyItem updates the instance. Preserve item state and use precedence, with results that UI can render. Books and maps call into DATA and WORLD, potions and drugs into MAGIC, and light state into player/AV systems. See DaggerfallInventoryWindow.UseItem, Game/LocalizedBook.cs and Game/EnablePlayerTorch.cs.

### Loot, provenance and persistence · ITEM-020–025

Game/Items/LootTables.cs and Internal/DaggerfallLoot.cs use loot matrices, random additions and location/time context to generate containers and stock. DaggerfallLoot also represents shop shelves, household containers, corpses and drops. Its stocked date gives restocking a time reference. Generation policy and runtime container behavior share an engine component, making offline distribution tests harder. Keep distinct stock policies and measure large collection generation before adding caching.

PlayerActivate and inventory windows handle access, transfers and property prompts. EnemyDeath transfers the actor's inventory to a corpse with quest context. Quest-linked items carry a quest UID and symbol, can be exported or made permanent, and have orphan cleanup. Summoned items carry an expiry and can be preferred by selective retrieval, including arrow use. Cleanup depends on who owns the collection and when it is checked. Explicit provenance and expiry policies need to survive movement between player, wagon, corpse and world containers. Confirm whether every supported destination participates in cleanup. See Game/PlayerActivate.cs, Game/EnemyDeath.cs, ItemCollection.RemoveExpiredItems, DaggerfallUnityItem.LinkQuestItem and MakePermanent.

SerializablePlayer and SerializableLootContainer save collections through item records. DeserializeItems inserts without stacking, which preserves distinct UIDs for subsequent equipment relinking. Equipment is represented by slot UID references, while enchantment state is restored separately. Restore ordering, missing UIDs, custom type fallback and quest reconciliation are important compatibility boundaries. No corruption or migration tests were performed.

## Comparison

| Concern | DFU | Proposed Godot design |
| --- | --- | --- |
| Identity | Template indexes, instance UIDs and saved type names | Stable definition and instance keys with explicit behavior fallback |
| Ownership changes | Collection operations plus UI policy | Validated transfers with typed outcomes and defined stack identity |
| Equipment and use | Slot and window callbacks into other systems | Committed slot transitions and ordered use handling |
| Loot and persistence | Engine container components and UID relinking | Explicit generation context and owner-directed reconstruction |

Verify stack equality and identity under split, merge and duplicate UID rejection. Exercise hand conflicts and enchantment teardown, save restoration with missing mods or equipment UIDs, repair completion, quest-link cleanup and summoned expiry across containers. Measure generation and transfer costs before optimizing. No runtime, profiling or classic parity tests were performed.
