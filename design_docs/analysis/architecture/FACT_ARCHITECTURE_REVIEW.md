# FACT architecture review

Scope covers FACT-001 through FACT-018 in the [feature catalog](../systems/FACT_FEATURE_CATALOG.md). This is a static review of the local DFU 1.1.1 Release snapshot. The exact commit is unavailable in the [repository record](../00_REPOSITORY_OVERVIEW.md). Paths are relative to Assets/Scripts. Runtime exposure, classic parity and balance remain open.

## Existing architecture

### Faction identity, reputation and reactions · FACT-001–005

API/FactionFile.cs loads faction records and relinks child relationships. Game/Player/PersistentFactionData.cs keeps session faction records keyed by numeric ID and provides hierarchy queries and reputation changes. SetReputation and direct ChangeReputation clamp the value. The propagated path adjusts allies and enemies first, follows the parent chain, and recursively changes descendant standings. It gives selected nodes full changes and others half changes, with special routing for knightly orders, deity factions and the Dark Brotherhood. Centralizing this legacy policy is useful. The parent walk and descendant recursion have no local cycle detection. A malformed hierarchy could fail to terminate if it reaches these paths. Overlapping affiliations can also receive multiple adjustments. Preserve order, repeated contributions and integer division in fixtures before simplifying.

PlayerEntity owns a separate social-group reaction modifier and exposes normalization and legal reputation operations. TalkManager.GetReactionToPlayer consumes reaction inputs, while quest actions read and mutate faction standings. Keep faction reputation, social reactions and regional legal reputation distinct. Their current co-location with character state makes it easy for a caller to conflate them. See Game/Entities/PlayerEntity.cs, Game/TalkManager.cs and Game/Questing/Actions/ChangeReputeWith.cs and WhenReputeWith.cs.

### Alliances, political state and markets · FACT-006–008

PersistentFactionData owns fixed ally/enemy slots, power and ruler updates. StartFactionAllies writes the requested slot on the first record and attempts to write the reciprocal relationship into the first empty slot of the second. If the second has no empty slot and does not already list the first, the method can still return true after writing a one-sided alliance. The write and success behavior are confirmed. Intentional asymmetry and actual reachability need verification. Relationship capacity and permanent war rules warrant explicit policy.

PlayerEntity.RegionPowerAndConditionsUpdate coordinates power, war and conditions. PlayerEntity.Update calls FormulaHelper.UpdateRegionalPrices at day changes and then scans elapsed minutes for periodic work. The source uses 112-day normalization, seven-day power updates and 38-day regional condition updates, with comments identifying a departure from classic's combined schedule. Price updates precede the historical minute loop at that call site, so a long jump and the same time advanced in smaller steps may order price and political updates differently. Runtime impact is unmeasured. The minute scan scales with elapsed time even if few boundaries are crossed. Existing regional flags and power values provide a useful handoff to ECON, but their update order and ownership should be explicit. See Game/Entities/PlayerEntity.cs and Game/Formulas/FormulaHelper.cs.

### Guild membership, rank and offers · FACT-009–013

Game/Guilds/GuildManager.cs resolves guild groups, creates IGuild implementations, stores memberships and returns nonmember behavior for unavailable memberships or mismatched deity/order variants. This lets callers query services without constructing their own membership checks. CreateGuildObj supports registered custom Types through reflection. Variant constructors depend on the group, and GetGuild casts the stored holy and knightly implementations to Temple or KnightlyOrder. A type satisfying only IGuild would still need to meet that subtype contract for those paths. Verify validation and package compatibility at registration.

Guild implements eligibility, join and rank policy. UpdateRank gates reevaluation on a 28-day interval since the last rank change, calculates thresholds from reputation and permanent guild skills, updates membership on expulsion and returns localized tokens. That method couples rule evaluation, clock, mutation and presentation. Preserve the gate and the distinction between initial eligibility and rank. PlayerEntity tracks crime-guild recruitment, GuildManager listens to quest completion, and ThievesGuild/DarkBrotherhood handle specialized joins. QuestListsManager.GetGuildQuestPool consumes membership, faction, reputation and rank. These seams support distinct guild policies, but which owner records invitation, acceptance and one-time effects needs to be clear across save and quest completion.

### Services and specialized benefits · FACT-014–017

Game/Guilds/Services.cs maps NPC service identifiers to service kinds, labels, shortcuts and custom registrations. Guild.CanAccessService and overrides apply gates. FightersGuild adjusts rest, repair and rewards. MagesGuild can grant recharge. Temple has deity-specific blessings, healing and death avoidance. KnightlyOrder grants armor, housing and travel perks. GuildManager aggregates cross-guild capability queries such as FreeShipTravel and AvoidDeath. These focused hooks are useful. A service ID, UI route, entitlement, price and fulfillment are separate concerns even when one guild implementation coordinates them. Keep exceptional behaviors in code and use authored tables for routine thresholds and discounts when content needs them. Verify stacking or precedence when multiple benefits apply, and ensure one-time claims survive reload. See Game/Guilds/Guild.cs, FightersGuild.cs, MagesGuild.cs, Temple.cs and KnightlyOrder.cs.

### Restore and classic import · FACT-018

PersistentFactionData merges classic reputation and adds custom factions. GuildManager exports ordinary and vampirism-related memberships as group-keyed records, recreates guilds using saved variant data, and restores rank and last-change values. Classic import uses separate conversion paths, including Guild.ImportLastRankChange. Persisting compact membership state separately from live objects is a strength. RestoreMembershipData clears the selected dictionary before recreating its members. An exception during construction or restore can therefore leave a partial dictionary at that boundary. No runtime failure was reproduced. Stable definition references, compatibility for missing custom guilds and an ordered rebuild of relationships and benefits need a defined policy.

## Comparison

| Concern | DFU | Proposed Godot design |
| --- | --- | --- |
| Faction graph and standing | Legacy records combine hierarchy, relationships and mutable standing | Validated relationships with explicit ordered standing changes |
| Politics and markets | Player update coordinates periodic work and price changes | TIME boundaries feed FACT, LAW and ECON under a defined order |
| Guild membership and services | Group-specific objects combine rank, service policy and presentation hooks | Explicit membership state, validated policy and owner-specific fulfillment |
| Restore | Rebuild memberships after clearing the current dictionary | Validate a replacement and publish with explicit compatibility outcomes |

Verify hierarchy and ally-slot boundaries, overlapping propagation, long time jumps, exact rank gates, variant-specific services, invitation completion and one-time claims. Exercise malformed or missing custom definitions and classic imports. No runtime, profiling or classic parity tests were performed.
