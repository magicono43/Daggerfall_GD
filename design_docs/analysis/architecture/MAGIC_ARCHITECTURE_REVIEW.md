# MAGIC architecture review

Scope covers MAGIC-001 through MAGIC-030 in the [feature catalog](../systems/MAGIC_FEATURE_CATALOG.md). Evidence comes from static inspection of the local DFU 1.1.1 Release snapshot. The exact commit is unavailable in the [repository overview](../00_REPOSITORY_OVERVIEW.md). Paths under Effects and references to the broker and manager are relative to Assets/Scripts/Game/MagicAndEffects. Runtime behavior, effective mod combinations and classic parity require fixtures.

## Existing architecture

### Definitions, spellbook and cast delivery · MAGIC-001–005, 011

EntityEffectBroker discovers effects through assembly reflection, registers keyed templates and creates instances with Activator. RegisterEffectTemplate supports controlled replacement. Classic spell conversion maps legacy effect keys and translates record settings into bundle entries, with AllEffectsImplemented available as a coverage check. Stable keys, an import boundary and separate live instances are worth preserving. Reflection and template construction make registration sensitive to the concrete types present at startup. Startup and cast allocation costs are unmeasured. Spell lists are owned by DaggerfallEntity, while the spellbook window presents them and the broker registers custom offers. Keep ownership of learned spells separate from offered definitions.

EntityEffectManager.SetReadySpell checks silence, version and cast progress and computes a ready-time cost. It has distinct player and enemy affordability policies. CastReadySpell, CastNoAnimSpell and the FPSSpellCasting release callback distinguish immediate, animated and enemy execution, then use direct assignment or DaggerfallMissile for contact. The manager also owns history, practice and UI notifications. Preserve the explicit release boundary and legitimate differences across routes. Shared ready fields and multiple commit paths increase the work needed to verify charge, abort and history semantics. The ready event fires before the no-cost flag and caster-only instant state are assigned. Whether subscribers depend on those fields needs a caller audit. Projectile target collection and attribution are covered in the [COMBAT review](COMBAT_ARCHITECTURE_REVIEW.md).

### Admission, scheduling and persistence · MAGIC-006–010

EntityEffectBundle carries source settings and caster/item context. EntityEffectManager.AssignBundle creates a LiveEffectBundle with separate IEntityEffect instances. The loop handles missing keys, hard immunities, absorption, reflection and resistance, starts the effect, then evaluates the on-cast chance result. It supports explicit bypass flags. Preserve the ordering in fixtures before changing it. Because Start precedes the failed-chance branch, a custom effect that mutates during Start can leave a consequence even when the instance is skipped. The visibility of such effects depends on their implementation.

TryReflection is called inside the effect loop, increments ReflectedCount on the source bundle and recursively assigns that entire bundle to the caster. The original loop can continue after that effect. This is a confirmed mismatch in granularity between admission and redirection. The shared reflection counter also couples recipients if the same source bundle is reused across deliveries. The one-reflection limit is useful protection against recursion. Actual partial application and target-order effects need tests with multi-effect and multi-target spells.

EntityEffectBroker.Update converts elapsed game minutes into magic rounds, including paused gameplay with advancing game time, and caps catch-up at two game days. On a positive catch-up it advances the cursor to the current time, skipping rounds above the cap. Some disease and poison effects implement their own catch-up. EntityEffectManager.DoMagicRound, DoConstantEffects, UpdateEntityMods and RemoveBundle coordinate duration, recurring effects, modifier rebuild and removal. IncumbentEffect permits a new application to merge with an existing instance. Only the flagged incumbent continues ticking and persists. This is a useful explicit stacking model. It needs defined merge, expiry and cleanup order so a cure or repeated restore cannot leave modifiers behind. Global round fan-out, per-manager iteration and reflection-created instances merit profiling before optimization.

GetInstancedBundlesSaveData and RestoreInstancedBundleSaveData use effect keys, settings, caster load IDs, item IDs and effect-specific payloads. Restore calls Resume and RestoreSaveData, migrates old icon data, skips held effects with missing source items, and logs and skips unknown effect keys. Empty restored bundles are discarded. This is a useful tolerant boundary. The code documents potential caster relinking order problems. Missing content behavior is currently lossy for skipped entries, and custom payload compatibility depends on each effect. HUD icons and removal events are coupled to the manager, although the UI can derive icons from live state.

### Crafting, consumables and enchanted items · MAGIC-012–016

DaggerfallSpellMakerWindow uses broker template queries and FormulaHelper.CalculateTotalEffectCosts to assemble spell entries. DaggerfallPotionMakerWindow.MixCauldron resolves a PotionRecipe and removes ingredients from inventory or wagon. EntityEffectManager.DrinkPotion turns the consumable into effect delivery. DaggerfallItemMakerWindow builds forced and selected enchantments, evaluates capacity and commits item changes and gold in the window handler. These are distinct authored workflows with reusable inputs, but rule validation, resource charging and UI are interleaved. Confirm behavior if inventory or price changes before commit. See Assets/Scripts/Game/UserInterfaceWindows for the three crafting windows.

EntityEffectManager.DoItemEnchantmentPayloads and held item start, unequip and break hooks route CastWhenHeld, CastWhenUsed and CastWhenStrikes behavior. This preserves distinct trigger policy and allows strike effects to alter damage. Effect lifetime is tied to source item identity and event ordering across ITEM and COMBAT. Re-equip, broken equipment, missing items on restore and reentrant strike callbacks are useful regression fixtures. The existing code does not establish failure atomicity across crafting payment, output creation and inventory mutation.

### Effect families and cross-system ownership · MAGIC-017–030

- **Vitals and timed status (017–022).** DamageHealth, ContinuousDamageHealth, HealEffect, FortifyEffect, DrainEffect and TransferEffect use effect instances for immediate or recurring changes. PoisonEffect and DiseaseEffect carry effect-specific saved state and lifecycle behavior. Paralyze, Silence, FreeAction, Shield and ElementalResistance participate in admission or modify actor capabilities. Keep individual effect behavior independently testable and preserve distinct immunity, resistance and cure policies. Test damage/transfer attribution, cap changes, cure matching and removal after restore. A data-only interpreter would have to encode these differences as well as ordinary stat modifiers.
- **Traversal, perception and NPC behavior (023–026).** Levitate, WaterWalking, WaterBreathing, Slowfall, Jumping and Climbing influence MOVE and CHAR. ConcealmentEffect and the manager expose break-on-action handling, while DetectEffect and light effects reach perception or presentation. Charm, Pacify and ComprehendLanguages touch AI and dialogue. Teleport reads and writes PlayerEntity.AnchorPosition, calls world and scene-cache operations, and provides its own save/restore state. SerializablePlayer also maps AnchorPosition. The confirmed overlap makes restore order and which value wins important. Follow the [MOVE placement proposal](MOVE_ARCHITECTURE_REVIEW.md) for traversal ownership.
- **Object utility and special effects (027–030).** Open and Lock reach interaction and doors, while Identify, CreateItem, SoulTrap and DispelMagic touch inventory, death or live effect removal. Vampirism and lycanthropy combine infection, ongoing curse state, race overrides, rest/weapon hooks and character grants. Their effects call global services for equipment, spells, quests and presentation, and persist specialized fields. PassiveSpecialsEffect and artifact implementations reuse the effect lifecycle, including the Ring of Namira combat callback and Oghma's level reward flags. This is flexible, but effects with several owners have more restore and cleanup cases. Keep exceptional behavior in code and use data for tuning and referenceable definitions.

## Comparison

| Concern | DFU | Proposed Godot design |
| --- | --- | --- |
| Definitions and mods | Reflection-discovered templates and classic conversion in the broker | Validated keyed definitions and explicit compatibility adapters |
| Cast and defenses | Shared ready fields, animation callbacks and bundle admission with mixed scopes | One cast commit and documented defense scope per delivery |
| Effect time and persistence | Global minute events, live instances and per-effect save data | Actor-owned live state with explicit time, restore and missing-source policies |
| Crafting and exceptional effects | Windows and effect classes coordinate multiple owners | Owner operations for resource commit, traversal and exceptional consequences |

Verify cast interruption and payment, mixed absorption/reflection/resistance, multi-target delivery, tick caps and cure/expiry order. Test missing mods and item sources, caster restore order, anchor migration, crafting failures and transformation cleanup. Profile active bundles and long time jumps before optimizing. No runtime, profiling or classic parity tests were performed.
