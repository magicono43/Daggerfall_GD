# LOC architecture review

Covers LOC-001 through LOC-020 in the [feature catalog](../systems/LOC_FEATURE_CATALOG.md). Evidence is from static inspection of the local DFU 1.1.1 Release snapshot. The exact commit is unavailable in the [repository overview](../00_REPOSITORY_OVERVIEW.md). Source paths are relative to Assets/Scripts.

## Existing architecture

### Exterior layout and identity · LOC-001–004

Internal/DaggerfallLocation.cs assembles exterior blocks with Utility/RMBLayout.cs, which constructs geometry and attaches static door and building metadata. Game/BuildingDirectory.cs indexes building summaries and supports faction queries. MakeBuildingKey packs layout X, layout Y and record index and remaps zero. This is compact and reproducible for an unchanged layout. Reordering blocks or records can change a building's key without changing its intended identity. Keep the directory as a query surface, and distinguish authored identity from legacy layout indices where mods can reorder records. Static doors carry hit metadata used by PlayerActivate, while DaggerfallCityGate owns gate state. Start markers provide arrival candidates to StreamingWorld. Geometry creation, interaction binding and arrival share the same block data, which supports consistency but requires fixture coverage when a replacement changes only one layer.

### Interior construction and occupants · LOC-005–008

Internal/DaggerfallInterior.cs DoLayout reconstructs an interior from StaticDoor metadata. AssignBlockData reads the RMB block and selects the interior record, throwing on a missing block or empty interior model set. GetSceneName derives the scene identifier from map ID and building key. DoLayoutAutomap also reads the block, while the live layout places people and furniture, assigns actions and makes household containers. Shared source data is a strength. It needs a consistency check across gameplay, marker and map representations. Closest/lowest door and marker helpers provide geometric matching where explicit links are absent. Ambiguous or missing markers need documented fallback. AddPeople and UpdateNpcPresence connect authored placement to NPC state. Keep occupant scheduling and ownership of household stock with NPC and ITEM while LOC supplies placement and property context.

### Dungeon assembly, environment and population · LOC-009–014

Internal/DaggerfallDungeon.cs LayoutDungeon assembles RDB blocks, resolves start and enter markers, reads block water and special flags, and removes overlapping doors. Utility/RDBLayout.cs builds individual block objects and adds fixed and random enemies, treasure, flats and water. Per-block assembly is a useful boundary for fixtures and eventual loading budgets. Story-specific texture choices, classic seeded texture tables and optional randomization are handled separately in DaggerfallDungeon and DungeonTextureTables. Preserve the authored exceptions and record the effective seed or variant when continuity matters. Avoid assuming visual texture changes alter gameplay identity.

FindMarkers and GetPlayerBlockIndex feed placement and water context to PlayerEnterExit. Quest Place enumerates dungeon markers and binds resources. Preserve the distinction between marker roles, block-level environmental data and instantiated effects. Enemy/treasure generation and object assembly share builder code, so repeated reconstruction needs a clear rule for generating fresh state versus restoring existing state. Verify overlapping doors, special blocks, missing markers and modded layouts against actual archive fixtures. Assembly allocations and overlap checks have not been profiled.

### Actions, traps and doors · LOC-015–017

Utility/RDBLayout.cs LinkActionNodes resolves next and previous keys to GameObject references. Internal/DaggerfallAction.cs Receive gates triggers and checks whether its chain is playing. ActivateNext forwards to the next component. IsPlaying follows NextObject recursively when the current node is idle, with no visited check. LinkActionNodes likewise shows no cycle validation. A cycle of idle action nodes can therefore cause unbounded recursion if admitted by the layout. Whether shipped layouts include such a cycle remains unverified. Preserve authored ordering and trigger acceptance, including collision triggers.

DaggerfallAction also handles text input, teleport, casting, health and poison. Movement uses iTween. Internal/DaggerfallActionDoor.cs owns lockpick, bash and toggle behavior with action callbacks and tween restart. These components provide understandable authoring units, but gameplay state and animation progress are coupled to engine objects. Separate committed action and lock state from transform playback. Keep explicit owner handoffs for damage, spells and traversal. Verify blocked doors, interrupted motion and action chains that wait for animation completion.

### Automap and reconstruction · LOC-018–020

Game/Automap.cs saves and restores dungeon discovery, handles interior discovery, and maintains user notes and teleporter markers. GetState calls SaveStateAutomapDungeon before returning its state, so capture includes updating the active map's discovery. Preserve discovery independently of map UI and geometry visibility. Use stable segment identity where players can revisit a changed layout.

Game/Serialization/SerializableActionDoor.cs and SerializableActionObject.cs relink by LoadID and restart tweening from saved progress. SerializableActionDoor increments a conflicting registered LoadID until it finds a free one. If colliding objects register in a different order, the resulting identities can differ. SerializableLootContainer and SaveLoadManager restore local state against reconstructed objects. Scene names and layout-derived keys are useful for deterministic reconstruction when content is unchanged. Define restore behavior for deleted records, changed variants and interrupted motion. See the [WORLD review](WORLD_ARCHITECTURE_REVIEW.md) for readiness and the [DATA review](DATA_ARCHITECTURE_REVIEW.md) for variant resolution.

## Comparison

| Concern | DFU | Proposed Godot design |
| --- | --- | --- |
| Assembly | Classic block builders construct Unity geometry and runtime components | Validated layout records with engine assembly and owner-specific population |
| Arrival | Door metadata and geometric marker selection | Explicit destination keys with validated placement and fallback |
| Actions | Scene references, recursive chain checks and tween state | Validated links, bounded dispatch and explicit action phase |
| Persistence | Scene names, LoadIDs and separate automap capture | Stable scoped keys and ordered reconstruction of durable state |

Verify one exterior, one interior and one multi-block dungeon with doors, water, treasure, enemies and quest markers. Test cyclic links, missing or ambiguous markers, changed variants, ID collisions, interrupted door motion and automap notes after reload. Profile assembly before changing job or streaming granularity. No runtime, profiling or classic parity tests were performed.
