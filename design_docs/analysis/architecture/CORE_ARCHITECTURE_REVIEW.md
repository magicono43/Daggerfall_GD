# CORE architecture review

CORE coordinates bootstrap, configuration, session entry and play gating. This review covers all 21 features in the [CORE feature catalog](../systems/CORE_FEATURE_CATALOG.md). It uses static inspection of the local DFU 1.1.1 Release snapshot. The exact source commit is unavailable in the [repository record](../00_REPOSITORY_OVERVIEW.md). Source paths below are relative to the snapshot's Assets/Scripts directory unless specified. Confirmed findings describe code paths and ordering. Player-visible frequency and consequences remain unmeasured.

## Existing architecture

### Bootstrap and configuration · CORE-001–006, CORE-021

- **Storage and logging (001–002).** [DaggerfallUnityApplication.cs](../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/DaggerfallUnityApplication.cs) caches portable-mode detection and path selection at subsystem initialization. A Unity log handler rotates one previous log and auto-flushes the current log. A single root and bounded retention are useful. Directory and log-file creation can throw outside rotation recovery. Auto-flush adds I/O per write. Its cost and simultaneous-launch behavior are unmeasured.
- **Settings and preferences (003, 006).** [SettingsManager.cs](../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/SettingsManager.cs) separates packaged defaults from the user INI, backs up parseable input, synchronizes keys, and falls back for typed values. The backup occurs before key synchronization and typed validation. This preserves the original shape but a parseable backup can still contain bad values. Write failures log a message without returning a status. StartGameBehaviour.ApplyStartSettings and GameManager shadow helpers apply engine and feature settings. Scene-dependent guards allow partial application. The frame-cap branch only assigns a cap when VSync is disabled and the configured cap is at least 30. Live reapplication could retain a previous cap.
- **Scenes and app actions (004–005, 021).** SceneControl.Start owns the initial ARENA2/settings/input check. Build settings confirm startup and game at indexes 0 and 1. The setup wizard also changes scenes, while title, setup and DaggerfallUI have quit paths. A GUID search found no direct ExitGame script references in scene or prefab YAML. GameManager.SetupSingleton persists the manager and the typed properties cache component, name and tag lookups. That avoids repeated discovery after binding and gives consumers a consistent entry point. Consumers still depend on global availability and scene naming. Startup failure and scene replacement require checking reference lifetime and serialized wiring.

### Session entry · CORE-007–014

[StartGameBehaviour.cs](../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/Utility/StartGameBehaviour.cs) provides one deferred dispatcher for most entry modes. Update consumes mutable StartMethod and SaveIndex fields. It pauses and disables world parents before mode-specific validation. Cleanup of request fields occurs on normal return. Title, death and void paths repeat quest/UI/world/weapon cleanup with meaningful differences in the messages and notifications. OnNewGame also reaches reset consumers such as PlayerEntity, PlayerMotor, TalkManager and magic effects on menu/void entry. Death entry writes a TitleMenu request which Update subsequently clears. Void mode sets NoWorld without clearing it in that path. These are code observations. They do not establish which follow-up behavior was intended.

New and classic entry reuse NewCharacterCleanup. New entry takes a CharacterDocument, chooses dungeon or exterior, delegates starting gear and spells, and initializes owner systems. Reusable grants and a visible sequence are strengths. Core also embeds opening quest keys, resumes before launching quests in source order and writes directly across many owners. Classic import combines reading SaveGames, CharacterRecord and SaveVars, translating legacy values such as weather flags/codes, and mutating the running session. An invalid index throws after shared cleanup. Failure to open a valid slot posts a message and returns after that cleanup. Classic fixture coverage is unknown.

[SaveLoadManager.cs](../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/Serialization/SaveLoadManager.cs) owns native reconstruction. DaggerfallUnitySaveGameWindow also calls it directly. Load(int) sets loadInProgress, releases GameManager pause and starts the coroutine. The success popup is posted at initiation. LoadGame resets player/quest state before file reads, waits for respawn and registration, restores data and mod sidecars, then clears the flag and emits OnLoad. Missing SerializablePlayer or PlayerEnterExit exits the coroutine before that clear. This is a confirmed unbalanced branch. The gameplay gate observes the flag and later load requests are rejected while it stays set. Actual reachability in shipped scenes is unverified. SaveData_v1 and mod save hooks already establish persistence boundaries. CORE's concern is operation sequencing and failure. SAVE owns schema migrations and restore semantics.

### Play gating and input · CORE-015–018

[StateManager.cs](../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/StateManager.cs) is a small C# class lazily created by GameManager. It subscribes to UI changes and static start, load and death events. It separates lifecycle observations from scene reconstruction. Its ChangeState publishes after changing CurrentState and before changing GameInProgress. Start and load share OnStartNewGame, which fires before the transition to Game. No unsubscribe lifecycle is visible in StateManager. Replacement or repeated construction could retain old observers. Window state shares a single previous-state slot with lifecycle transitions.

[GameManager.cs](../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/GameManager.cs) owns pause, time-scale restoration, gameplay input and optional HUD hiding, with an IME recovery step. UI window push/pop can request pause/resume. PauseGame has one bit of ownership. An overlapping pause is ignored and a resume releases the existing pause regardless of caller. IsPlayingGame separately checks pause, save readiness/load and window policy. This is convenient for callers but two systems can infer different notions of playability. The UI still needs its own input and presentation policy.

FixedUpdate exposes ClassicUpdate as a sampled flag and discards overshoot. At the serialized 0.02-second fixed step, with steady active updates and unchanged timing, 0.0625 seconds crosses on the fourth step, giving an approximately 0.08-second interval. That is a source-derived estimate. EnemyAttack, EnemyMotor, EnemySenses, PlayerEntity and DaggerfallAudioSource consume the flag, so changing timing can change random draw order and behavior. Update dispatches shortcut UI messages and SAVE actions behind the gameplay gate. Preserve ordered shortcut precedence and quickload confirmation while making dispatch independent of timing.

### Shared gameplay hooks · CORE-019–020

GameManager exposes rest veto callbacks, threat checks, encounter/spawn events and bulk enemy operations. [ActiveGameObjectDatabase.cs](../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/ActiveGameObjectDatabase.cs) maintains categorized weak-reference caches with active queries and prunes destroyed entries on additions. The shared registry avoids redundant world searches. Threat policy combines sight, hostility, spawn eligibility and separate spawner checks, including a hardcoded distance condition during rest. Keeping this logic centralized helps consumers agree. Each scan scales with candidate count and can perform perception checks. No profiling establishes a bottleneck. FoeSpawner and CreateFoe raise encounter events. GameObjectHelper, RDBLayout and SerializableStateManager publish enemy spawns, including on restore. Mod subscribers therefore need context if they distinguish reconstruction from fresh gameplay. Rest veto delegates are lightweight extension points. Their lifetime, precedence and failure behavior need an explicit contract if exposed publicly.

## Comparison

| Concern | DFU | Proposed Godot design |
| --- | --- | --- |
| Startup | Static root/settings and cached scene discovery | Application root with validated session bindings and recoverable storage setup |
| Session entry | Mutable request slot plus direct native SAVE calls | One operation contract with preflight, ordered apply and completion |
| State and pause | Static events, window history and global pause flag | Committed lifecycle snapshot and independently owned pause reasons |
| Runtime hooks | Manager owns tick, shortcuts and enemy operations | Clock, input adapter and feature owners retain their own responsibilities |
| Extensibility | Delegates, events and mod save hooks | Preserve small hooks with lifecycle and failure contracts. Keep persistence versioning in SAVE. |

Verify malformed settings, unavailable storage, repeated setup/game entry, invalid native and classic selections, missing restore components, overlapping UI/load/death states and callback-visible snapshots. Then measure cadence and actor-query costs with representative gameplay. Scene and prefab lifetime, original content behavior, classic import fidelity and mod combinations remain open. No runtime or Godot implementation was exercised.
