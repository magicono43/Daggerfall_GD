# NPC-006 — Ambient encounter selection

Approval status **Approved — finalized v1**

The user approved Draft v1 on 2026-11-11 with “I approve”. See NPC-006-A01 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#npc-006-interview-decisions).

## Gameplay purpose and intended player experience

Create intermittent danger in the wilderness, at night in location areas, and when resting in an alerted dungeon. The setting and player level influence which foe may appear. The encounter can interrupt rest when activation actually commits.

## Confirmed requirements

NPC-006-D01–D03 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#npc-006-interview-decisions) confirm the DFU timing and context defaults, moddable scheduling and selection, and bounded placement retries for a single retained foe.

## Existing Daggerfall Unity behavior

`Assets/Scripts/Game/Entities/PlayerEntity.cs` iterates elapsed minutes and calls `IntermittentEnemySpawn`, skipping ambient checks while swimming or aboard ship. The method uses `((Minutes / 12) % 12) == 0` with integer division. Outdoor checks distinguish a location rectangle at night and wilderness by day or night. Dungeon checks require resting, and `Assets/Scripts/Game/Formulas/FormulaHelper.cs#RollRandomSpawn_Dungeon` checks enemy alert. The elapsed-minute loop stops when a spawner is requested. `Assets/Scripts/Utility/RandomEncounters.cs#ChooseRandomEnemy` uses climate and day/night or dungeon type, then selects within a table using level-dependent bounds. The gate uses the opportunity minute, while the selector reads current world time. These findings come from the local 1.1.1 source snapshot.

## Detailed rules and behaviors

- TIME delivers committed game-minute boundaries during eligible play and supported rest or loitering. Evaluate each eligible minute at most once. Suppressed advancement, including supported fast-travel and jail time skips, advances the encounter cursor without building a backlog.
- Resolve one context for the opportunity. Default outdoor contexts are location-area night and wilderness day or night. Ordinary interiors and outdoor location areas by day have no default check. Dungeon checks require active alert and rest. Swimming, ship travel, explicit suppression and a full pending budget prevent checks. Respect current session and area scope.
- Use the same context snapshot for the gate and table selection, so a boundary crossing cannot roll one context's odds and choose another context's foe. Evaluate the approved RULE-020 gate once. A pass selects one foe from the applicable stock table using the captured player level and stock table policy. Retain the result and selected archetype through placement retries.
- Maintain at most one pending ambient request in the current area by default. Pass it to the placement owner. Retry placement within a bounded budget while the request remains eligible. If exhausted or stale, close the request and wait for a new eligible minute. A failed placement consumes no additional encounter-gate or selection draws.
- During catch-up, stop ambient checks for the current elapsed-time batch when a request is accepted and consume the remainder of that batch for scheduling. TIME remains responsible for how far calendar advancement commits. A qualifying encounter activation is checked by the rest owner before the next segment advances.

## Formulas and parameters

For nonnegative integer game minute `M`, the default schedule permits checks when `floor(M / 12) mod 12 = 0`. Eligible minute offsets are 0–11 in each 144-minute period. Under RULE-020, the odds per eligible check are 1/24 for location-area night or wilderness night, and 1/36 for wilderness day or alerted dungeon rest. Placement eligibility and retries affect actual encounter frequency. The default request is one foe, with one pending request in the current area.

## Required data, inputs, outputs and events

Inputs include committed minute and advancement reason, session and area IDs, outdoor location classification or dungeon type, climate and day/night context, rest and alert state, swimming, ship and suppression state, player level, pending budget and validated tables. Outputs distinguish ineligible, failed gate, invalid data, selected request, placement retry, abandonment and committed activation. Track each opportunity and request independently. CORE-020 governs activation and actor availability notifications.

## Edge cases and failure conditions

- A replayed minute, pause, reload, or repeated placement callback cannot create another check for the same opportunity. A genuinely new minute can authorize a new opportunity.
- A missing or malformed table is a configuration failure. Close a passed opportunity without placement when its resolved table has no eligible foe.
- If the area or session changes, or the original eligibility expires before placement commits, discard the pending request. A callback from that request cannot spawn into the new scope.
- Track pending requests separately from living actors. Rest may continue while a request awaits placement. A committed relevant activation or another established blocker prevents further rest advancement.

## Configuration and balancing

Expose schedule windows, supported advancement reasons, context eligibility, table mappings and supported selection policies, pending cap and placement retry limits. RULE-020 independently exposes exact odds and alert eligibility. Keep placement distances, active actor caps and exact retry timing with the placement owner. Stock table mappings and level bounds require content verification.

## Save/load considerations

Restore the scheduler cursor so elapsed time is not checked again. Restore any supported pending request with its original context, selected foe, retained gate result and remaining placement budget, or close it under declared recovery policy. Preserve settled activation and actor state. A load cannot create a fresh encounter notification or duplicate an actor already placed.

## Technical constraints

Target Godot 4.7.2. Use scope-bound opportunity and request IDs. Keep scheduling, probability, selection, placement and actor availability explicit. Diagnostics expose eligibility and outcome without drawing or mutating state. Exact APIs, rest boundary ordering and save schema remain owner integration work.

## Acceptance criteria

1. The stock scheduler permits checks at offsets 0–11 of each 144-minute period. Repeat delivery and suppressed skips produce no additional checks.
2. Each default context uses its approved RULE-020 odds. Swimming, ship travel, ordinary interiors, location-area daylight and ineligible dungeon states skip the stock check.
3. A passed gate chooses at most one foe from the matching context table and preserves it through bounded retries. A full pending budget prevents another request. Stale or exhausted requests close safely.
4. A placement failure produces no committed activation. A relevant committed activation is processed before further rest advancement.
5. Save/load neither repeats completed opportunities nor duplicates committed actors. Mods can change supported timing, tables and eligibility.
