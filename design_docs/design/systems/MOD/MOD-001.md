# MOD-001 — Mod package discovery

**Approved — finalized v3.** The user approved Draft v3 on 2026-11-17.

## Gameplay purpose and intended player experience

Players can install a mod by placing a single archive or an unpacked mod folder in the active `Mods` directory. The same pre-menu configuration applies to both forms. Players can identify which copy they are about to use and recover from a broken installation.

## Daggerfall Unity reference

DFU 1.1.1 recursively scans for `.dfmod` Unity AssetBundles under `StreamingAssets/Mods` by default. Its Unity Editor path separately scans `Assets/Game/Mods` for `.dfmod.json` manifests and constructs virtual mods directly. An already-discovered matching GUID suppresses a virtual copy. See [ModManager.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/ModManager.cs#L555).

## Confirmed rules

1. Discover both ZIP archives and unpacked folder packages in normal play. Use one `Mods` directory under the active storage root selected by CORE-001. Standard and portable modes expose their own installed libraries.
2. Present discovered candidates in pre-menu configuration. When eligible copies share a stable package ID, show their source paths and require the player to choose one copy or skip that ID before continuing. The same rule applies across and within formats.
3. Report an unreadable or invalid package with its path and reason. Exclude it from the eligible candidates. Allow the player to proceed with the remaining selection if it passes dependency and pre-menu data validation.
4. Hand eligible candidates and duplicate choices to the mod selection and dependency features. DATA-003 governs publication of validated definitions and locks the enabled selection and order at main-menu entry.
5. Recursively scan ordinary subdirectories of `Mods` so players can group packages by author or category. Skip directory links. A folder containing a root mod manifest is a package boundary even if manifest validation fails. Stop searching that folder's descendants for independent packages. Grouping folders carry no load priority.

6. Require a shared `mod.json` manifest at the package root with four required fields. `manifest_version` identifies the manifest format, `id` is the stable package ID, `name` is the player-facing label and `version` is the mod release version. If a ZIP puts its manifest under a wrapper folder, report that it belongs at the ZIP root.
7. Provide **Rescan Mods** on the pre-menu mod screen. Rerun discovery and refresh candidates and diagnostics after package installs, repairs or removals. The updated selection remains subject to dependency validation and DATA-003's configuration lock.
8. Remember the player's explicit duplicate choice across launches, including a choice to skip the ID, while the eligible copies for that ID retain the same paths, IDs and versions. Compare the eligible copies on launch and manual rescan. If the set changes and a duplicate remains, ask again. If only one eligible copy remains, it is available for ordinary mod selection.
9. Treat a missing `Mods` root as an empty library. If the root exists but cannot be read, show the path and offer **Retry**, **Continue without mods for this run**, or **Quit**. Retry reruns discovery. Continuing without mods supplies an empty installed-package set for this run and still runs DATA-003 validation and SAVE-017 compatibility checks. The choice applies to package discovery within the selected storage mode. Required writable storage follows CORE-001 recovery.

10. Keep installed package file access within the package boundary. Reject ZIP entries that escape the package root and filesystem links inside unpacked installed packages. Mods can share one installed copy of an asset through a declared dependency and an explicit export, identified by provider package ID and asset key. A dedicated asset pack or an existing mod can provide the export. Before activation, report an unavailable or incompatible required provider or missing required export through dependency or content validation.

See MOD-001-D01 through D12 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Parameters, data, inputs and outputs

There are no gameplay formulas or balance settings. The discovery root is the active storage root plus `Mods`. Inputs are the selected root, installed candidates, package metadata, saved duplicate choices and player actions. Results are candidate records with stable package ID, version, display name, format and source path where available, plus validation issues, root recovery outcomes and the resolved set of eligible copies. Pre-menu consumers receive discovery results and any decisions still needed before validating the active selection. These are conceptual results. API and event names remain implementation details.

## Edge cases and failure conditions

- An archive and its extracted folder can claim the same ID. Display both, even when their names and versions match.
- A broken candidate can lack a usable ID. Its path and diagnostic still appear. If another mod requires a provider that cannot be selected, dependency validation governs whether the player can proceed.
- A package can be discoverable and still fail dependency checks or content validation. Surface the failure at the stage that detects it.
- Backup copies under ordinary grouping folders are discoverable. If a backup shares an ID with another eligible copy, apply the duplicate choice.

## Cross-system interactions and save/load

- [CORE-001](../CORE/CORE-001.md) supplies the storage root for the run, including an explicitly selected fallback. [CORE-002](../CORE/CORE-002.md) records available mod startup metadata when established.
- MOD-002 and MOD-003 own enabled selection, priority and dependency validation. [DATA-003](../DATA/DATA-003.md) owns application of the resolved plan and the configuration lock.
- MOD-003 owns dependency declarations and version compatibility. Asset export and lookup contracts belong to the MOD content features. Moving a provider between grouping folders preserves references when the selected package ID and exported key remain the same.
- [SAVE-017](../SAVE/SAVE-017.md) governs compatibility and recovery for mod payloads. File renames preserve identity when the package ID matches. A character load still applies the approved required and optional content rules. Discovery results and package selection are application state.

## Recommendations and technical constraints

Apply the same manifest requirements and containment policy to both forms. Discovery produces candidate metadata and diagnostics. Executable activation follows its own MOD lifecycle contract.

## Acceptance criteria

1. A valid archive and a valid unpacked folder with distinct IDs both appear in normal pre-menu configuration.
2. Each storage mode discovers packages under its selected root, including the root used after explicit startup fallback.
3. Two eligible copies with one ID display both paths and require an explicit choice. Selecting one yields one candidate for that ID. Skipping yields none.
4. An unreadable archive or invalid manifest produces a path and reason. A valid remaining selection can continue. A remaining selection with unsatisfied required dependencies cannot activate.
5. The discovered selection follows DATA-003's validation and lock. Loading a character follows SAVE-017 compatibility rules.
6. A ZIP in an author folder and an unpacked package in a nested category folder are both discovered. A ZIP inside the unpacked package is excluded from independent discovery, even when the package manifest is invalid. Directory links are skipped.
7. Both package forms report invalid required manifest fields. A ZIP with a wrapper folder over its manifest reports the required manifest location.
8. Rescanning before main-menu entry shows newly installed or repaired packages and removes deleted candidates. The action is unavailable after main-menu entry.
9. A later launch reuses a duplicate choice for an equivalent candidate set. A path or version change, or an added or removed copy, prompts again if multiple eligible copies remain. An equivalent pre-menu rescan preserves the choice.
10. A missing root yields an empty library. An unreadable root shows its path and offers all three recovery actions. Retry can recover once the root becomes readable. Continuing without mods still checks save compatibility and a subsequent launch attempts discovery again.
11. A ZIP entry that escapes the package root and a filesystem link in an unpacked installed package fail validation with a source path and reason.
12. Two mods can reference the same exported asset from one installed provider. Moving the provider within `Mods` preserves the reference when the package ID and export key stay the same and the selected version is compatible. An unavailable required provider or export is reported before activation.

## Outstanding questions and approval

Remaining implementation contracts include exact manifest field validation and encoding, dependency and export declaration syntax, and package path normalization. MOD-016 owns authoring and packaging, including any support for local workspace links. These contracts must preserve the approved discovery and sharing behavior.

The specification was checked against the approved storage, pre-menu configuration and mod save policies listed above. The recorded decisions fit those policies. See MOD-001-A01 in the gameplay decision log for approval.
