# MOD-002 — Enabled mods and load priority

**Approved — finalized v2.** The user approved Draft v2 on 2026-11-17.

## Gameplay purpose and intended player experience

Players can keep named mod setups for different campaigns or tests and switch among them before entering the main menu. Each setup controls which installed mods participate and the order in which their content is considered.

## Daggerfall Unity reference

DFU 1.1.1 exposes enablement and priority in its mod loader window. ModManager restores these choices by mod title, sorts by priority and unloads disabled mods during initialization. See [ModManager.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/ModManager.cs#L831).

## Confirmed requirements and detailed behavior

1. Provide named profiles within each CORE-001 storage root and a ready-to-use Default profile. Each profile stores enabled package IDs and their intended order over that root's shared installed library.
2. Present profile selection, enablement and ordering in pre-menu configuration. Newly discovered IDs start disabled. Rescan updates availability without enabling new IDs.
3. Match profile entries by stable package ID. A missing enabled mod remains visible with its saved position. The player can explicitly skip it for the current run if the resulting configuration validates, or remove it from the profile permanently. If the ID returns, reuse its saved enablement and position, subject to discovery and validation.
4. Provide **Save Profile** to persist an unfinished configuration, including one with missing prerequisites. **Continue** validates the candidate selection and rebuilds definitions under DATA-003. A saved profile can still need work before it can launch.
5. Entering the main menu locks the validated profile selection and resolved active order for the rest of the run.
6. Provide **Create**, **Rename**, **Duplicate**, and **Delete**, with confirmation before deletion. At launch, preselect the last profile that successfully entered the main menu within the active storage root. If that profile is unavailable or there is no successful history, preselect Default.
7. If **Continue** has unsaved profile edits, offer **Save and Continue** or **Continue for This Run**. Both paths must validate before main-menu entry. Save and Continue validates and saves the edited profile before entry. Continue for This Run uses the validated edits for the active run and preserves the saved profile. Run-only omissions stay scoped to the run.

See MOD-002-D01 through D06 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Parameters, configuration and required data

Profiles need identity, display name, enabled package IDs and their ordered positions. Persist the last successfully used profile ID per storage root. Runtime configuration also needs the saved and edited profile values, discovered eligible copies, missing IDs, explicit current-run omissions and the resolved active order. There are no gameplay formulas or balancing settings. DATA-003 applies later enabled contributions where their declared operation permits overrides.

## Inputs, outputs and events

Inputs include storage-root selection, discovery and rescan results, profile management and edits, Save Profile, Continue, the unsaved-edit choice, and explicit missing-mod recovery choices. Outputs include the persisted profile, validation results and the locked active set and order. UI feedback distinguishes successful profile save from successful configuration activation. Concrete API and event names remain open.

## Cross-system interactions and save/load

- [CORE-001](../CORE/CORE-001.md) supplies the active root. [CORE-003](../CORE/CORE-003.md) supplies settings persistence and recovery rules.
- [MOD-001](MOD-001.md) supplies eligible copies and handles duplicate choices. MOD-003 owns dependency validation and auto-sort behavior. [DATA-003](../DATA/DATA-003.md) applies the resolved order and locks it after pre-menu validation.
- Profiles share installed packages and the root's character saves. [SAVE-017](../SAVE/SAVE-017.md) checks the actual locked content selection when loading a character. A save load cannot switch the active profile.

## Edge cases and technical constraints

- A filename or folder move preserves profile identity. Duplicate copies still follow MOD-001's resolution rules.
- A package update under the same ID can leave a profile with an incompatible dependency. Surface the validation result before activation.
- A current-run skip preserves saved intent. Permanent removal requires a profile edit. A package returning after a skip still follows the approved configuration lock if the main menu has already been entered.
- Preserve the saved profile if a write fails and report the failure. Use committed settings recovery under CORE-003.
- A failed validation or profile write on Save and Continue leaves the player in configuration with their pending edits available for recovery.

## Acceptance criteria

1. The same installed library supports two profiles with different enabled sets or orders. Standard and portable roots expose their own profiles.
2. A newly installed ID appears disabled after launch or rescan.
3. Removing an enabled package shows a missing entry in its original position. An explicit eligible run-only skip permits validated activation. Reinstalling the same ID restores the saved position.
4. Save Profile can persist a setup with an unmet dependency. Continue blocks entry while the candidate fails required validation.
5. A character load checks compatibility under the active configuration. Returning to the main menu retains the run's lock.
6. A player can create, rename, duplicate and delete profiles. Canceling deletion preserves the profile. A later launch preselects the last successfully used profile or Default when it is unavailable.
7. With unsaved edits, both Continue choices validate. On success, Save and Continue retains the edits for future launches. Continue for This Run applies the edits to the active run and the persisted profile retains its prior values.

## Outstanding questions and approval

The UI needs to keep Default available as a fallback and define name validation and navigation with pending edits. Persistence encoding and dependency solver behavior remain follow-on contracts. The confirmed rules fit the approved storage, discovery, data activation and save compatibility policies above. See MOD-002-A01 in the gameplay decision log for approval.
