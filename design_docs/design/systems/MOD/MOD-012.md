# MOD-012 — Quest packs and custom verbs

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-18.

## Purpose and intended player experience

Authors can distribute quests and dialogue as data, reuse custom commands from other packages, and test a specific quest in the running game. Players receive validated quests through their authored eligibility and offer rules.

## Daggerfall Unity reference

DFU 1.1.1 discovers quest pack lists and registers action templates. Quest parsing selects the first template whose pattern matches a line. See [QuestListsManager.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/Questing/QuestListsManager.cs#L107) and [QuestMachine.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/Questing/QuestMachine.cs#L751).

## Confirmed rules

1. A data-only pack can add quests, dialogue and eligible quest-list entries. It can use built-in commands or package-qualified commands supplied by declared dependencies. A pack that supplies its own executable behavior follows MOD-004 and MOD-005.
2. Resolve command providers before validating dependent quests. Follow QUEST-006 for stable command IDs, typed arguments, condition or operation roles, reference validation and compatibility versions. Reject unknown or duplicate IDs and unresolved ambiguous legacy syntax. Perform validation without changing gameplay state.
3. Apply DATA-003 and DATA-012 contribution operations, precedence, provenance and explicit recovery. Published lists follow normal quest eligibility and duplicate rules. The application content plan locks at main-menu entry.
4. Provide an in-game author tool to select a quest by stable ID within an isolated test session. Offer the normal offer path and an explicit direct-start path. The offer path uses normal offer rules. Direct start skips waiting for an offer and still validates required world resources and bindings through the supported quest runtime.
5. Report whether a test failure arose during definition validation, world setup or execution. Show resolved command IDs, versions and providers under QUEST-006. Test actions and history are isolated from ordinary character saves and history.

See MOD-012-D01 and D02 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Required data, inputs and outputs

Inputs include quest, dialogue and list definitions, stable quest and command IDs, provider dependencies and versions, argument and reference schemas, and the selected test session and entry path. Outputs include validated contributions, eligible quests and command bindings, test execution outcomes and actionable diagnostics. Quest owners supply selection and gameplay parameters. Concrete API and event names remain open.

## Interactions and save/load

- [DATA-012](../DATA/DATA-012.md) governs quest sources, validation and explicit recovery. [QUEST-005](../QUEST/QUEST-005.md) governs quest preparation and author testing. [QUEST-006](../QUEST/QUEST-006.md) governs command validation and execution contracts.
- [MOD-003](MOD-003.md) validates provider dependencies. [MOD-004](MOD-004.md) and [MOD-005](MOD-005.md) govern executable eligibility and registration.
- [QUEST-022](../QUEST/QUEST-022.md) and SAVE own persistent quest state and compatibility. Restore required commands by stable ID and compatible version or supported migration. A missing required provider follows save recovery. Restoration preserves committed quest progress and effects.

## Edge cases and technical constraints

- A data-only pack can depend on a trusted provider. The provider still requires its own approval before execution.
- A quest can validate and still fail to find suitable world resources in the chosen test context. Report that as a world setup failure.
- Rebuilding the candidate cannot accumulate list entries or stale registrations. Testing uses normal validation and runtime rules with isolated mutable state.

## Acceptance criteria

1. A data-only pack adds a quest, dialogue and a list entry using built-in commands. A second pack uses a declared dependency's custom command.
2. Unknown, duplicate or ambiguous commands produce actionable diagnostics. Validation does not start quests or grant rewards.
3. The author can select the same quest by ID and exercise both the normal offer path and direct start in an isolated test session. Direct start fails clearly when required bindings are unavailable.
4. Diagnostics distinguish validation, setup and execution failures and identify the resolved command provider. Test actions preserve ordinary character history.
5. Loading a quest with an unavailable required command follows approved compatibility and recovery rules.

## Outstanding questions and approval

Exact pack schemas, command interfaces, test session setup and navigation, and migration formats remain technical design. The specification follows approved quest validation, command registration, testing, and save compatibility policies. See MOD-012-A01 in the gameplay decision log for approval.
