# MOD-005 — State-based entry points

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-17.

## Purpose and intended experience

Mods can register application behavior once per successful activation and prepare separate state for each character. Players receive actionable recovery when a mod fails to initialize. Starting or loading another character uses a fresh session scope.

## Daggerfall Unity reference

DFU 1.1.1 invokes attributed entry points at Start and on the first Game transition, then unsubscribes. It catches and logs entry-point invocation exceptions and continues. The inspected callback path does not roll back partial registration. See [ModManager.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/ModManager.cs#L716).

## Confirmed rules and lifecycle

1. During pre-menu activation, run application-wide mod registration after required trust consent and in the validated mod order. Register behaviors such as custom quest commands and system replacements in time for dependent validation. Publish the result through the approved DATA-003 activation flow. Main-menu entry locks the active plan for the run.
2. Prepare character-specific mod state and listeners for each new or loaded session. On load, restore required payloads or apply the eligible migration, initialization or recovery policy from SAVE-017. Required setup and restoration complete before CORE announces readiness.
3. Deliver CORE-015's committed new-session and restored-session notifications distinctly, once per actual milestone. A restored character does not receive the new-session milestone. Reuse the active application scope across sessions. Clean up session-owned listeners, registrations and resources at session end and reject late work from that scope.
4. Block the affected activation step when setup fails. Identify the mod and phase. After verified cleanup, offer retry or revision of the pre-menu plan where it is still editable. For failures during character entry, follow CORE's session recovery while preserving the run's locked plan. If safe cleanup cannot be established, require restart before another activation attempt. Existing CORE cleanup and quit options still apply.
5. Offer explicit continuation with a failed optional capability disabled only when the author declares a fallback, cleanup is verified and the resulting configuration passes applicable dependency, content and save checks. Disclose which capability is affected. A required failure blocks readiness.

See MOD-005-D01 through D04 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Required data, inputs and outputs

Inputs include the candidate or locked mod plan, trust decisions, phase, owning mod and scope, session and operation identities, requested registrations, fallback declarations, saved payloads and player recovery actions. Outputs include prepared registrations or session state, readiness results, owned cleanup outcomes and diagnostics. CORE owns committed lifecycle notifications. There are no numeric gameplay formulas or balancing parameters.

## Interactions and save/load

- [MOD-003](MOD-003.md) validates dependencies and resolved ordering. [MOD-004](MOD-004.md) governs permission to run trusted code and replacement selection. [DATA-003](../DATA/DATA-003.md) governs pre-menu publication and the configuration lock.
- [CORE-005](../CORE/CORE-005.md) governs service lifetimes and safe recovery. [CORE-015](../CORE/CORE-015.md) governs committed lifecycle notifications and scope ownership.
- [SAVE-017](../SAVE/SAVE-017.md) supplies mod payload restoration, migration and optional recovery rules. A launcher fallback cannot waive a required reference in a save. Missing or incompatible prior state follows its applicable save policy.

## Edge cases and technical constraints

- Retry after a partial registration only once affected state is verified clean. Cleanup and stale-callback rejection must preserve unrelated active scopes.
- Returning to the main menu after a session does not repeat application registration. New sessions receive fresh session setup, even for the same character.
- Trusted code may create effects outside the registration APIs. A caught exception is insufficient evidence of cleanup.
- Finalize the fallback and required readiness checks before publishing readiness. Post-readiness notifications observe the committed result.

## Acceptance criteria

1. Trusted mod registration begins only after consent. A custom registration can satisfy dependent content validation before main-menu entry.
2. Starting a character and loading a save each prepare a fresh mod session. Restore required mod payloads before the restored-session notification. Deliver each applicable milestone once.
3. Ending a session removes its mod subscriptions and registrations. Delayed work from that session cannot affect another. Application scope survives a safe menu return.
4. Failed activation identifies the mod and phase, blocks the affected milestone and allows another attempt only after verified cleanup or restart.
5. An author-declared optional fallback can proceed after explicit choice and successful revalidation. A required dependency or save reference that the fallback cannot satisfy still blocks entry.

Callback signatures, how candidate registrations are staged and cleaned up, and how each subsystem declares and verifies its fallback remain technical contracts.
