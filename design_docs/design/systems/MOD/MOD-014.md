# MOD-014 — Mod settings and localization

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-18.

## Purpose and intended player experience

Players can edit mod preferences, preview presets and restore a mod's authored defaults. They can tell which changes are staged, effective or pending, and use localized controls and explanations.

## Daggerfall Unity reference

DFU 1.1.1 provides typed mod settings, a dedicated window and a preset picker. Mods can opt into a settings callback and look up localized strings by key. See [Mod.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/Mod.cs#L491) and [PresetPicker.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/ModSettings/PresetPicker.cs).

## Confirmed rules

1. Store one preference set per stable mod ID under the selected storage root. Profiles within a root share those values. Standard and portable roots keep separate values. MOD-002 profile management governs enabled packages and order.
2. A preset stages only the settings it declares. Show which values change and their activation timing. Apply validates and accepts eligible changes under CORE-006. Cancel discards unapplied edits.
3. Every mod that exposes editable settings provides a **Reset to Defaults** action. Ask for confirmation before proceeding. Scope the reset to the selected mod and use the defaults from its active settings definition.
4. Under CORE-006, classify settings as live, next session or location, or restart-required. Apply interdependent values at a boundary safe for the whole group. Preserve CORE-003 write recovery and distinguish staged edits, pending requests and effective values. Live settings changes respect the locked mod plan.
5. Resolve localized setting names, descriptions and preset labels through approved DATA-013/014 fallback and diagnostics. Display strings are separate from stable setting and preset identities.

See MOD-014-D01 through D04 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Confirmed reset behavior

Confirming **Reset to Defaults** stages the complete set of editable defaults for that mod. Show the changes and timing in the settings view. **Apply** uses the same validation, activation and persistence flow as other edits. Canceling the confirmation preserves existing staged edits. Canceling the settings view after a confirmed reset discards that unapplied reset.

## Parameters, required data, inputs and outputs

Settings need stable keys, value types and constraints, declared defaults, preset values, activation boundaries and group membership, and localized string references. Inputs include saved values, the active mod settings definition, locale and player edits. Outputs include staged changes, validated requests, effective values, diagnostics and persistence status. Numerical balance remains with the setting's owner. Concrete API and event names remain open.

## Cross-system interactions and save/load

- [CORE-001](../CORE/CORE-001.md) selects storage. [CORE-003](../CORE/CORE-003.md) and [CORE-006](../CORE/CORE-006.md) govern validation, application and settings recovery.
- [MOD-002](MOD-002.md) owns profile selection. [DATA-003](../DATA/DATA-003.md) governs the resolved content plan and its lock. [DATA-013](../DATA/DATA-013.md) and [DATA-014](../DATA/DATA-014.md) govern localized text and fallback.
- Mod preferences belong to the application. Character-specific mod state follows [SAVE-017](../SAVE/SAVE-017.md). Loading a character does not implicitly restore earlier preferences or change the active profile.

## Edge cases and technical constraints

- A partial preset preserves omitted values in the pending editor state. Validate each changed group before accepting it.
- Malformed stored values and incompatible settings schema changes follow settings validation and recovery. Exact migration rules remain open.
- A reset can include both live and deferred groups. Show their effective timing and report failed application or persistence through the existing recovery flow.
- A missing translation uses the approved fallback. Locale or label changes preserve setting identity and value.

## Acceptance criteria

1. Two profiles in one root see the same preferences for the same mod ID. Switching storage roots exposes the other root's values.
2. Selecting a partial preset stages its declared values and timing. Apply validates it and Cancel discards unapplied changes.
3. Every mod with editable settings offers Reset to Defaults and confirmation. Confirming stages defaults for the selected mod and Apply follows each group's activation timing. Canceling the confirmation leaves edits intact.
4. A restart-required group remains pending until its owner boundary. A write failure leaves application and persistence status distinguishable. A missing localized label follows the approved fallback.
