# MOD-006 — Asset lookup, cloning and caching

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-18.

## Gameplay purpose and intended experience

Mods can deliberately replace game assets and reuse exported assets from other mods. Two placed objects can look alike and share underlying art while retaining independent gameplay state and local visual changes.

## Daggerfall Unity reference

DFU 1.1.1 queries enabled mods in reverse order and returns the first asset it can load as the requested type. Its lookup can return a shared asset, instantiate a clone or bypass the mod cache. It also supports bulk loading and unloading bundle resources. See [ModManager.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/ModManager.cs#L394) and [Mod.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/Mod.cs#L306).

## Confirmed rules

1. A reference to a provider package ID and exported asset key resolves through that selected package and its export. Check availability and the expected asset type. Report a missing or wrong-type export through applicable dependency and content validation. A matching key in a different package cannot satisfy this reference.
2. A request for a logical game asset uses DATA-003's resource identity and approved precedence. Later valid replacements win where the asset type permits that operation. Invalid contributions follow DATA-003 recovery and validation.
3. Share read-only assets by default. Each runtime instance owns its mutable state. When a caller needs to edit an asset such as a material, give it an independent editable resource so the edit stays local. Retain shared read-only dependencies where feasible.

See MOD-006-D01 and D02 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Parameters, required data and configuration

There are no gameplay formulas or balancing parameters. Lookups need the logical domain and resource path or the provider ID and export key, the expected type, the validated configuration, the resolved source, and the required shared or editable access. Preserve source provenance for diagnostics. Cache sizes and eviction thresholds remain technical parameters.

## Inputs, outputs and events

Inputs include asset requests, the validated override or export definitions, candidate rebuilds and owner lifecycle changes. Outputs include a shared resource or independently editable instance, source provenance, and actionable validation or loading failures. Public API and event names remain open.

## Cross-system interactions and save/load

- [MOD-001](MOD-001.md) defines exported asset references. [MOD-003](MOD-003.md) validates provider availability and compatibility.
- [DATA-003](../DATA/DATA-003.md) owns override operations, provenance, invalid contribution recovery and the run-long configuration lock. AV and other asset consumers define the required types and mutable instance state.
- [MOD-005](MOD-005.md) and [CORE-005](../CORE/CORE-005.md) define ownership boundaries. Save validation under [SAVE-017](../SAVE/SAVE-017.md) still applies to required mod references. Runtime cache contents are disposable. Save owners persist gameplay state and stable references where their schemas require it.

## Edge cases and technical constraints

- Two packages can export the same key. Each direct reference resolves within its named provider.
- A missing or wrong-type required export stays a validation failure even if another package contains a plausible replacement.
- An independently editable resource must isolate any nested state the caller can mutate. Read-only meshes, textures or other dependencies may still be shared.
- Pre-menu candidate changes must not retain stale winners or provenance from earlier configurations. Discarding a candidate must preserve resources still owned by another live scope.

## Recommended caching approach

Load on demand and reuse read-only data while consumers still need it. Keep cached lookup results scoped to the relevant resolved configuration. Release unused resources at safe ownership boundaries. Profile representative mod lists before adding bulk preloading, memory budgets or manual cache controls.

## Acceptance criteria

1. Two providers export the same key and each direct reference selects its named provider. A missing or wrong-type export produces a diagnostic without substituting the other package.
2. A logical game asset with multiple valid replacements follows DATA-003 precedence and reports the winning source.
3. Two runtime instances share read-only art while retaining independent state. An edit to one instance's editable material leaves the other instance and original resource unchanged.
4. Rebuilding a candidate under a different order changes the resolved winner where required. Cleanup preserves resources still in use by another owner.
