# MOD-010 — Formula and custom activation overrides

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-18.

## Purpose and intended player experience

Mods can replace individual gameplay calculations and object interactions. Players can inspect which providers will run and resolve cases where a system overhaul makes another mod's required hook unavailable.

## Daggerfall Unity reference

DFU 1.1.1 registers formula delegates by name, selects by provider priority and removes an incompatible delegate when lookup detects a signature mismatch. Object activation can call both a registered model or flat callback and an object component callback on the same hit. See [FormulaHelper.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/Formulas/FormulaHelper.cs#L3135) and [PlayerActivate.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/PlayerActivate.cs#L433).

## Confirmed rules

1. Competing whole-system replacements require explicit provider selection under MOD-004. Individual formula replacements and same-scope interaction replacements use the last valid provider in resolved enabled-mod order under RULE-004 and MOVE-025. Valid individual conflicts expose candidates and the winner in diagnostics.
2. A whole-system replacement declares the existing hooks it supports. Resolve hook availability against the selected provider. Show contributed hooks that are unavailable as inactive in pre-menu diagnostics. If an enabled mod explicitly requires an unavailable hook, block Continue and identify the requiring mod, hook and selected system provider. Revalidate after the player changes the candidate configuration.
3. Validate hook identities, eligibility and owner-defined signatures before activation. Formula replacement and additive behavior follow RULE-004. Additive hooks compose only under their declared ordering and combination contract.
4. Follow MOVE-018 and MOVE-025 for activation routing. Instance-specific primary handlers precede broad primary matches under those rules. Run at most one primary effect. Observers receive the result under their declared contract. Only an explicit effect-free Not applicable allows routing fallback.
5. Lock application-level hook providers with the validated configuration at main-menu entry. A failing or out-of-contract callback stops the affected operation and follows owner recovery. Do not retry a second provider or replay effects after possible mutation.

See MOD-010-D01 and D02 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Parameters, required data, inputs and outputs

Inputs include stable system and hook IDs, provider ID, execution eligibility, resolved order, selected whole-system provider, supported and required hooks, and owner-defined contracts. Activation also takes validated target, actor, reach, mode and operation context. Outputs include the selected or inactive hook, source provenance and actionable diagnostics, plus owner-defined invocation results and observations. There are no shared formulas or balance parameters. RULE and gameplay owners define calculation inputs, output bounds and side effects.

## Interactions and save/load

- [MOD-004](MOD-004.md) governs trust and whole-system provider choice. [MOD-005](MOD-005.md) governs registration and cleanup. [MOD-003](MOD-003.md) governs package dependency validation.
- [RULE-004](../RULE/RULE-004.md) owns formula contracts and [MOVE-025](../MOVE/MOVE-025.md) and [MOVE-018](../MOVE/MOVE-018.md) own activation routing. [MOD-007](MOD-007.md) supplies the pre-menu diagnostics view.
- Save compatibility uses the locked providers and applicable SAVE and domain contracts. Restore saved gameplay facts through their owners. Loading cannot change hook providers, replay committed effects or reroll retained results.

## Edge cases and technical constraints

- A losing whole-system provider's hook support cannot satisfy a requirement against the selected provider.
- A registered interaction component and a broad hook matching the same target still follow one primary dispatch. Respect normal eligibility and effect-free preview rules.
- Validate ownership and lifetime. Session-bound targets and callbacks cannot mutate later sessions. Keep diagnostics independent of invocation.

## Acceptance criteria

1. Competing whole-system providers require a choice. Valid competing individual hooks select the last eligible provider under owner rules and show its provenance.
2. Selecting a system that omits a contributed hook marks that hook inactive. An explicit requirement for that hook blocks entry and identifies the incompatibility.
3. An incompatible hook registration fails validation. A matching instance handler and broad activation do not produce two primary effects.
4. A failing callback follows owner recovery without invoking a second provider. Menu return or character load preserves the locked application providers.

## Outstanding questions and approval

The hook inventory and versioning, declaration syntax for required and supported hooks, and concrete signatures and recovery mechanics remain owner contracts. The specification follows the approved MOD-004 whole-system policy and the RULE-004 and MOVE-025 policies for individual hooks. See MOD-010-A01 in the gameplay decision log for approval.
