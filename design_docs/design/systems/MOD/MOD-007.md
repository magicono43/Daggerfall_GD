# MOD-007 — Loose text and record patches

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-18.

## Purpose and intended player experience

Players can apply local text and data changes across their profiles and inspect which mod or loose file supplied a resolved value.

## Daggerfall Unity reference

DFU 1.1.1 checks a loose relative path first for a single text read and then looks in mod bundles by basename. Bulk reads and record merges have separate code paths. See [TextAssetReader.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Utility/AssetInjection/TextAssetReader.cs#L35).

## Confirmed rules

1. Use one `Overrides` folder beside `Mods` under the storage root selected by CORE-001. All profiles in that root use the same loose source. External changes to loose content require an application restart. Pre-menu mod rescans and reordering use the run's loose source under DATA-003.
2. Apply shipped definitions, then enabled mods in their resolved order, then loose overrides. Identify logical resources by domain and relative path and records by stable ID. Within a source, use normalized relative path and declared entry order.
3. Use explicit, domain-supported operations for whole-resource replacement, additions and patches. An add requires a free ID. A patch requires an existing target and preserves omitted fields. Later valid changes win for the same field. Lists replace as a whole unless their domain supports merging. Deletion requires an explicitly supported operation.
4. Resolve and validate a candidate before publication. Reject an invalid contribution as a whole. Show its source and reason. Allow explicit omission only when rebuilding the remaining setup passes dependency and content validation. Main-menu entry locks the validated configuration for the run.
5. Provide an on-demand **Content Diagnostics** view in the pre-menu configuration stage. Show contributing and winning sources for the candidate being diagnosed, including field-level winners where patches contribute to the same record. Ordinary valid overlaps do not trigger blocking prompts. Invalid contributions retain the recovery flow above.

See MOD-007-D01 and D02 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md) and the approved [DATA-003 specification](../DATA/DATA-003.md).

## Parameters, data, inputs and outputs

Required data includes the selected root, candidate mod order, logical resource paths, stable record IDs, declared operations, applicable schemas, source provenance and validation outcomes. Inputs include supplied text and patch files, candidate edits and explicit recovery choices. Outputs include resolved resources or records, their contributing and winning sources, and diagnosed validation failures. No gameplay formulas apply. Content domains own balance values and operation constraints. Concrete API and event names remain open.

## Interactions and save/load

- [CORE-001](../CORE/CORE-001.md) selects the root. [MOD-002](MOD-002.md) manages profile edits. [MOD-003](MOD-003.md) validates dependencies and order.
- [DATA-003](../DATA/DATA-003.md) governs resolution, rejection and the configuration lock. Consumers such as ITEM, MAGIC and QUEST own their schemas and validate references.
- Loose content is part of the application definition plan. Character loads use the locked plan and follow applicable SAVE compatibility and domain rules. Diagnostics expose the plan without changing character state.

## Edge cases and technical constraints

- Resources with equal basenames in different logical paths remain distinct.
- When two valid patches touch different fields, show a winner for each field. When they touch the same field, show the contributors and the final winner.
- An invalid patch leaves no partial edits. Explicit omission can expose an earlier value or break references. Rebuild and validate before publishing.
- Keep diagnostic results consistent with the candidate they describe. Regenerate them when a changed pending configuration is resolved.

## Acceptance criteria

1. Two profiles in the same root both use its loose overrides after their own enabled mods. Standard and portable roots use their respective loose sources.
2. An external loose-file edit is adopted only after restart. Pre-menu reordering can change the mod result while preserving loose-source precedence.
3. The diagnostics view identifies sources and field winners for both overlapping and disjoint valid patches without a blocking prompt.
4. An invalid patch is reported with its source and reason. No partial changes survive rejection. Continuing after an explicit omission succeeds only with a valid remaining setup.
