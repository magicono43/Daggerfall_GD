# MOD-011 — Custom items, effects and spell offers

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-18.

## Purpose and intended player experience

Authors can add items and effects, attach supported custom behavior, and make spells available through specific services. Players can combine content packs without accidental ID collisions and receive actionable recovery when required definitions are unavailable.

## Daggerfall Unity reference

DFU 1.1.1 registers custom items by numeric template index and attaches use handlers by index. The effect broker registers effect templates with an explicit replacement option and registers custom spell offers by key and usage, rejecting duplicate offer keys. See [ItemHelper.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/Items/ItemHelper.cs#L113) and [EntityEffectBroker.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/MagicAndEffects/EntityEffectBroker.cs#L262).

## Confirmed rules

1. Identify each new item, effect and offer by content type, creator package ID and stable local key. Different packages can use the same local key. Display names, registration order and implementation class names carry no identity. Preserve an existing definition's identity when an authorized contribution patches or replaces it.
2. Admit additions, patches and replacements under DATA-003 and the owning domain's rules. Cross-package targets are explicit. Reject duplicate additions to the same identity and validate references, provider eligibility and domain contracts before publishing the resolved registries.
3. Custom item-use and effect behavior follow the owning gameplay contracts and MOD-004/005 execution and registration rules. Registration makes eligible definitions available for supported use. Each service still evaluates its own offer and crafting rules.
4. A mod can add a specific service offer for another package's spell through a declared dependency. Validate the spell and service eligibility. If the spell is unavailable, a required offer fails validation and an explicitly optional offer stays inactive. Required package dependency failures still follow MOD-003. Show why an offer is inactive or invalid.
5. Keep resolved definitions locked with the validated mod plan. Each item instance and applied effect owns its mutable state under ITEM and MAGIC. Inspecting definitions or offers follows the owner rules for side-effect-free browsing.

See MOD-011-D01 and D02 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Parameters, required data, inputs and outputs

Inputs include package identity, local definition keys, declared operations, domain schemas, dependency and provider information, behavior registrations, and offer-to-spell and service references. Outputs include resolved definitions, available or inactive offers, source provenance and validation diagnostics. ITEM, MAGIC and service owners define numerical effects, prices and eligibility. Concrete API and event names remain open.

## Interactions and save/load

- [ITEM-002](../ITEM/ITEM-002.md) supplies item definition rules. [MAGIC-001](../MAGIC/MAGIC-001.md) supplies effect registration and eligibility. [MAGIC-011](../MAGIC/MAGIC-011.md) governs offer visibility, learning and purchase.
- [DATA-003](../DATA/DATA-003.md) governs contribution order and recovery. [MOD-003](MOD-003.md) governs dependency validation. [MOD-004](MOD-004.md) and [MOD-005](MOD-005.md) govern executable eligibility and registration.
- Resolve required definitions before dependent save reconstruction. Persist stable references and owner-defined mutable state. Apply [SAVE-017](../SAVE/SAVE-017.md) and domain compatibility and migration rules when required providers or definitions change.

## Edge cases and technical constraints

- Matching local keys from different creator packages resolve independently. An authorized replacement tracks its contributing provider separately from the target identity.
- An optional offer stays inactive when its integration is unavailable. The same missing spell can still block a separate required offer or a required save reference.
- Changing an offer list changes future availability. Learned spells and committed purchases follow existing owner and save rules.

## Acceptance criteria

1. Two packages can register items with the same local key. Each reference resolves to its own definition. A duplicate addition to the same identity fails validation.
2. An explicit compatible cross-package patch or replacement follows the approved order and retains provenance and target identity.
3. One mod can offer another mod's spell through an eligible service. If the spell is unavailable, a required offer blocks validation and an explicitly optional offer is inactive.
4. Save reconstruction resolves required definitions before dependent item and effect state. Missing required definitions enter approved recovery.
