# MOD-015 — Mod save interface

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-18.

## Purpose and intended experience

Mods can persist character state and provide upgrade paths across mod releases. Players can update a mod and load compatible saves without installing intermediate releases.

## Daggerfall Unity reference

DFU 1.1.1 exposes a payload type and callbacks for default state, capture and restore. It stores separate files keyed by mod filename and calls the default-state callback when the file is absent. See [ModTypes.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/ModTypes.cs#L260) and [SaveLoadManager.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/Serialization/SaveLoadManager.cs#L1528).

## Confirmed rules

1. At initial release, each eligible package can register one save interface. It may organize its payload into internal sections. Keep the limit extensible so a future interface revision can support additional registrations and retain a path to read existing single-registration payloads.
2. Identify saved mod payloads by stable package ID and independent payload version. Register capture, initialization, restore, version compatibility and any supported migration or recovery policy under SAVE-017. A package filename change preserves payload identity.
3. Support a direct migration or a chain of registered steps from the saved version to a supported reader version. Prepare and validate the complete result during preflight before session replacement. An invalid step, invalid result or unsupported version follows SAVE recovery. Preserve the source generation.
4. Distinguish new-character initialization from joining an existing character. For an existing character, initialize only where no prior payload exists and the owner permits it. Incompatible or corrupt prior data follows migration, explicit recovery or failure.
5. Capture mod state at the shared save snapshot boundary and publish it with the base-game generation. A required capture or write failure fails the save. Optional handling follows declared owner policy and SAVE-017. Restore required state before session readiness.
6. Disclose eligible optional omission before load proceeds. Subsequent successful saves from that session omit the unavailable payload. Loading and failed publication preserve the source generation. Required dependencies and gameplay references retain their approved blocking recovery.

See MOD-015-D01 and D02 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Parameters, inputs and outputs

Inputs include package ID, payload version, active provider, operation and session identity, saved record, migration and initialization policies, required references and the owner's captured state. Outputs include prepared or restored state, validation and readiness results, a payload for coherent publication, or an actionable failure or omission outcome. There are no gameplay formulas. Concrete callback names and payload encoding remain open.

## Interactions and technical constraints

- [SAVE-006](../SAVE/SAVE-006.md), [SAVE-007](../SAVE/SAVE-007.md) and [SAVE-017](../SAVE/SAVE-017.md) own snapshot publication, migration and mod compatibility. [SAVE-005](../SAVE/SAVE-005.md) governs recovery disclosure.
- [MOD-004](MOD-004.md) and [MOD-005](MOD-005.md) govern provider eligibility, registration and session lifetimes. Migrations prepare data without replaying committed gameplay effects. Restore targets the incoming session.
- Resolve migration paths reproducibly where multiple routes exist. Preserve required identities and references across migration. A failed attempt cannot publish a partial generation or carry a stale callback into a later session.

## Acceptance criteria

1. A package can register one save interface and retain internally structured data. A second registration is rejected under the initial contract.
2. A renamed package restores compatible data by stable ID. A working direct migration and a working chained migration each prepare valid state without intermediate installs.
3. A failed migration leaves the source generation and active session intact during preflight. A corrupt prior payload cannot trigger new-mod initialization.
4. Required state restores before readiness. Required capture failure preserves the previously committed generation. An eligible, disclosed omission is reflected only in newly committed saves from that session.

## Outstanding questions and approval

Exact callback signatures, payload encoding, migration path selection, and the future multi-registration format remain technical design. The specification follows the approved save compatibility, generation publication and mod lifecycle rules. See MOD-015-A01 in the gameplay decision log for approval.
