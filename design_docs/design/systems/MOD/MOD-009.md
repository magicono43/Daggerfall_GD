# MOD-009 — World replacements and variants

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-18.

## Purpose and intended player experience

Mods can provide alternate locations, blocks and buildings. An overhaul can set a reusable layout default and a quest can select an alternate layout for a single placement. Players retain compatible layout changes across saves and receive actionable diagnostics when two changes cannot coexist.

## Daggerfall Unity reference

DFU 1.1.1 supports location, new-location, block and building variants. Some lookups use the last queried location as context. Save loading restores variant data before player position. See [WorldDataVariants.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Utility/AssetInjection/WorldDataVariants.cs#L51) and [SaveLoadManager.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/Serialization/SaveLoadManager.cs#L1465).

## Confirmed rules

1. Support reusable defaults and explicit placement-specific selections. A valid specific selection overrides the applicable default at that placement. Other placements retain their own applicable defaults. Keep variant identity, target placement identity and per-session selection distinct. Supply location, block or building context explicitly when resolving a target.
2. Resolve installed variant definitions using DATA-003 precedence and validation. Definitions and mod order lock at main-menu entry. WORLD and LOC can change session selections among installed validated definitions through the DATA-024 transition contract.
3. If a broader replacement removes a narrower target, identify the affected record or placement and both sources. Use an author-supplied mapping only after verifying target identity, layout compatibility and required references. If no compatible mapping exists, block the affected operation and route to the applicable configuration, world transition or save recovery. Configuration changes that affect installed definitions follow DATA-003's lock and recovery rules.
4. Validate proposed geometry, player placement, quest bindings and persistent object state before committing a variant transition. Return to baseline only through an explicit validated transition. Keep stale work from earlier operations or sessions from applying to the current world.
5. Restore required saved selections before dependent geometry construction, quest binding and player placement. If a required variant cannot be resolved compatibly, use a supported migration or fail through save recovery. Validate a mapping separately for restoration where saved state and references are involved.

See MOD-009-D01 and D02 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md) and approved [DATA-024](../DATA/DATA-024.md).

## Parameters, required data, inputs and outputs

Inputs include stable IDs for variants and placements, source and package provenance, declared scopes and defaults, author-supplied mappings, saved selections and current transition identity. Outputs include a resolved layout definition, a validated selection or transition, and diagnostics naming affected targets and sources. No fixed numeric parameters or gameplay formulas apply. The world owners define supported scopes and transition constraints.

## Interactions and save/load

- [DATA-003](../DATA/DATA-003.md) owns definition precedence and publication. [DATA-005](../DATA/DATA-005.md) governs stable world records and explicit mappings. [DATA-024](../DATA/DATA-024.md), WORLD and LOC govern variant resolution and transition readiness.
- QUEST, placement and persistent object owners validate required references before a changed layout becomes usable. [SAVE-015](../SAVE/SAVE-015.md) restores required variant facts before their consumers. [SAVE-017](../SAVE/SAVE-017.md) governs relevant provider compatibility.
- Keep session-selected variants separate from the installed definition plan. Character replacement starts with the incoming session's state.

## Edge cases and technical constraints

- Repeated instances of a block can resolve different valid selections. Query order cannot change the result.
- A moved building may still be incompatible with a narrower patch if required interior records or persistent references no longer exist.
- A baseline selection is an explicit outcome. Missing required content follows compatibility recovery.
- Context-dependent layout caches must reflect the selected variant and relevant placement. Invalidate affected results during transitions and retain unrelated resources where safe.

## Acceptance criteria

1. A reusable default affects two eligible placements. A specific selection overrides it at only one. Reversing query order preserves both results.
2. An incompatible overlapping replacement identifies the removed target and both contributing sources. A valid explicit mapping can resolve it. An invalid mapping keeps the affected operation blocked.
3. A valid runtime variant change uses the locked definitions and completes only after required placement and state checks. A stale completion cannot alter a newer session or transition.
4. A saved required variant is available before dependent reconstruction. An unavailable or incompatible variant follows explicit migration or load failure.

## Outstanding questions and approval

Exact schemas, precedence among broader defaults, mapping representation, and per-domain recovery and cache mechanics remain owner contracts. The specification follows approved DATA-003, DATA-024 and SAVE-015 behavior. See MOD-009-A01 in the gameplay decision log for approval.
