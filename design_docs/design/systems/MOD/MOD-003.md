# MOD-003 — Dependency validation and auto-sort

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-17.

## Gameplay purpose and intended player experience

Players can see which prerequisites a mod needs and repair invalid setups before playing. Auto-sort helps resolve required ordering while preserving the player's preferred precedence where possible. Optional integrations can fall back to standalone behavior.

## Daggerfall Unity reference

DFU 1.1.1 reports missing, disabled, misordered and version-incompatible providers. It checks minimum versions and excludes presence-only relationships from sorting. Its validator skips missing or disabled optional providers, while its sorter can still include a disabled optional provider. The launcher accepts dismissal of dependency warnings and can offer auto-sort. See [ModManager.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/ModManager.cs#L1059) and [ModLoaderInterfaceWindow.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/ModLoaderInterfaceWindow.cs#L437).

## Confirmed rules

1. Resolve dependencies by stable package ID against the enabled candidates after MOD-001 duplicate resolution. A required provider that is missing, disabled or incompatible blocks **Continue**. Show the dependent, provider and reason. Offer an explicit enable action for an eligible, compatible disabled provider. The player can also fix the installation or disable the dependent. Revalidate after changes.
2. An optional provider that is missing or disabled leaves the integration inactive. An enabled incompatible optional provider leaves the integration inactive and produces a warning. Both cases permit Continue if the remaining configuration validates. A compatible enabled optional provider participates in its declared order unless explicitly suppressed for the run to resolve a cycle.
3. Active dependencies default to provider-first order. Authors can declare presence-only dependencies, which still undergo availability and version checks and have no ordering edge.
4. Validation and auto-sort use the same active ordering constraints. If the pending order violates them, block Continue until the player fixes it. Preview the proposed order and apply it only on explicit acceptance. Preserve the player's relative order where feasible, with deterministic results for identical inputs. Revalidate the proposed order after application. Applying auto-sort edits the pending configuration under MOD-002.
5. An ordering cycle blocks Continue. Show the full loop with the affected mods. If an optional ordering edge participates, let the player explicitly turn off that integration for the run and revalidate. Further cycles or unresolved dependencies keep Continue blocked. The run-only choice preserves the saved profile and the dependency declaration.
6. Author-declared version bounds use an inclusive minimum and an optional exclusive maximum. For example, a range from `2.1.0` up to `3.0.0` accepts `2.1.0` and excludes `3.0.0`.

See MOD-003-D01 through D06 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Required data, parameters and balancing

Inputs include package IDs and installed versions, the pending enabled set and preferred order, dependency declarations, and explicit run-only suppressions. Each declaration identifies the provider, required or optional status, order requirement and any version bounds. No gameplay formulas apply. Reordering can change which valid content override wins under DATA-003.

## Inputs, outputs and events

Player actions include enabling or disabling a mod, editing order, requesting or accepting a sort preview, suppressing a cycle-forming integration and continuing. Outputs include blocking diagnostics, warnings, active and inactive integrations, cycle paths, a proposed order and the validated result. Concrete API and event names remain open.

## Cross-system interactions and save/load

- [MOD-001](MOD-001.md) supplies eligible packages and stable identities. Required asset exports still need content validation before activation.
- [MOD-002](MOD-002.md) supplies profile edits and lets invalid plans be saved. Only validated configurations enter the main menu. [DATA-003](../DATA/DATA-003.md) applies resolved contributions and locks the active plan on entry.
- A save load uses the locked active configuration under [SAVE-017](../SAVE/SAVE-017.md). A warning or optional suppression in the launcher does not make a missing gameplay reference eligible for omission in a particular save.

## Edge cases and technical constraints

- A disabled mod's own declarations do not constrain the active order. Enabling a prerequisite may expose prerequisites of its own.
- Presence-only relationships do not create ordering cycles. A self-ordering declaration is a one-package cycle.
- A preview depends on the candidates, order and integrations used to build it. Recompute or revalidate if the player changes those inputs before applying it.
- Turning off an optional integration must also keep its dependent content and hooks inactive. The integration and export APIs need to expose the validated outcome to their consumers.

## Acceptance criteria

1. A missing, disabled or incompatible required provider blocks entry with an actionable diagnostic. Explicit enablement of a compatible provider reruns validation.
2. Missing and disabled optional providers leave integrations inactive. An incompatible enabled optional provider also warns. A compatible active ordered provider constrains the order. Presence-only does not.
3. An invalid manual order yields a deterministic preview when an order exists. Dismissing it preserves the pending order. Applying it changes only the pending configuration and revalidates.
4. A cycle displays the loop and blocks entry. Suppressing a participating optional integration can resolve it for the run. A remaining cycle still blocks.
5. Compatibility tests cover the inclusive lower and exclusive upper boundaries.
