# MOD-004 — Compiled and source script loading

**Approved — finalized v1.** The user approved Draft v1 on 2026-11-17.

## Gameplay purpose and intended experience

Authors can add custom gameplay logic and replace substantial system behaviors. Players can see which mods need trusted execution, decide whether to permit it, and choose which provider controls a system when replacements conflict.

## Daggerfall Unity reference

DFU 1.1.1 loads packaged assembly bytes and forwards packaged source to its C# compiler. It discovers types and attributed entry points from mod assemblies. Mod code runs in the game process. See [Mod.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/Mod.cs#L946) and [ModManager.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Game/Addons/ModSupport/ModManager.cs#L700).

## Confirmed rules

1. Target both restricted scripting against documented, replaceable gameplay interfaces and an explicitly opt-in trusted code path at initial release. Design replacement interfaces alongside the base systems so an author can replace a whole behavior without needing a separate hook for every operation. The trusted path must support substantial gameplay changes.
2. Accept readable, multi-file source scripts in ZIP and unpacked packages for restricted scripting. Measure startup and first-use cost with representative large mods. Revisit precompiled distribution if profiling shows a meaningful benefit.
3. Obtain explicit player approval before trusted executable content runs. Ask again when the executable content changes, even under the same package ID and release version. Preserve approval across non-executable edits when the executable content is identical.
4. When approval is declined, keep the package installed and inactive for the run, show affected dependents and allow configuration changes before continuing. If the author declares a usable data-only mode, offer it as an explicit choice. Validate that mode and the resulting configuration before activation.
5. If multiple enabled mods claim the same gameplay system replacement, show the conflict before main-menu entry and require the player to choose its provider. Apply the choice to the pending configuration and validate that every enabled mod can run with it. Let the player revise the selection when validation fails. DATA-003 still governs ordinary data precedence.
6. Evaluate a trusted scripting candidate in an exported build using a substantial gameplay overhaul. Native-library support remains an open format choice. A concrete SDK requirement or measured performance need can justify evaluating it.

See MOD-004-D01 through D06 in the [gameplay decision log](../../GAMEPLAY_DECISIONS.md).

## Required data, configuration and events

Inputs include MOD-001 package identity, declared execution mode, script and plugin content, executable identity for approval, any declared data-only mode, replacement targets and candidate providers, and explicit player choices. Outputs include validation diagnostics, trusted approval or decline, selected providers and an eligible execution plan for MOD-005. API and event names remain open. There are no gameplay formulas or balance parameters. Replacement behavior can change game balance within the owning system.

## Cross-system interactions and save/load

- [MOD-001](MOD-001.md) discovers packages. [MOD-002](MOD-002.md) manages pending configurations. [MOD-003](MOD-003.md) validates required providers and order after execution mode or provider changes.
- [DATA-003](../DATA/DATA-003.md) governs pre-menu publication and the configuration lock. [DATA-012](../DATA/DATA-012.md) requires supported custom commands before quest validation succeeds. MOD-005 owns registration timing, cleanup and activation failure recovery.
- Approval and provider selection are application configuration. Character loading follows [SAVE-017](../SAVE/SAVE-017.md) and cannot grant code approval or override the locked configuration. Requiring trusted content or a particular provider may affect save compatibility.

## Edge cases and technical constraints

- Discovery and approval checks must be able to inspect executable identity without executing unapproved code. Bind approval to the executable inputs actually used at activation, including changes detected after discovery.
- Restricted scripts need an enforceable boundary around direct filesystem, network and OS access. Trusted code can act with the game process's permissions. Explain that access when asking for approval.
- Code load failures, missing required registrations and a data-only mode that cannot satisfy dependents must surface before the affected configuration becomes usable.
- A replacement choice applies to the named system. It does not silently change profile order or settle unrelated data overrides.

## Acceptance criteria

1. An exported build validates and runs a representative multi-file restricted mod from either package form. Measure its startup and first-use cost.
2. A trusted mod demonstrates a substantial system replacement in an exported build. Trusted code cannot run before approval. An executable edit prompts again and a data-only edit with identical executable content preserves approval.
3. Declining leaves the package installed and shows affected dependents. An author-declared data-only mode runs only after explicit selection and successful validation.
4. Two competing system replacements prompt for a provider before main-menu entry. The selected provider controls the system. A configuration with unmet requirements stays in recovery.

## Outstanding questions and approval

The scripting language and isolation mechanism, trusted delivery format, exact executable identity inputs, persistence scope for replacement choices, and system-specific replacement contracts remain open. MOD-005 must settle execution timing, error recovery and registration lifecycle. The specification preserves the approved discovery, pending profile, dependency, data activation and save compatibility rules. See MOD-004-A01 in the gameplay decision log for approval.
