# LOC-011 — Start and enter marker resolution

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-14 with “I approve”.

## Gameplay purpose and intended player experience

Land at the intended place when entering a dungeon. Different entrances may lead to different landings, and Privateer's Hold retains its distinct deep-cave opening. A blocked or missing landing produces a clear outcome and preserves the route's intended destination.

## Confirmed requirements

- **LOC-011-D01.** Use stable marker IDs scoped to the placed dungeon block, with explicit bindings for doorway arrivals, general dungeon arrivals and the special opening spawn. Entrances may share an explicitly linked landing or have distinct landings.
- **LOC-011-D02.** Verify classic marker roles and placement during import. An unresolved required route needs a validated mapping override or explicit preparation failure. Verify Privateer's Hold's original deep-cave pose and facing against source layout data.
- **LOC-011-D03.** Permit ordered authored backups only for general routes under WORLD-003. Named doorway and new-game placements retain their target and use only permitted bounded local corrections. Native load restores the saved pose under its placement rules. Failures use approved recovery.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#loc-011-interview-decisions).

## Existing Daggerfall Unity behavior

Static inspection of DFU 1.1.1. `Assets/Scripts/Internal/DaggerfallDungeon.cs#FindMarkers` takes the first available Start and Enter markers from a designated starting block and logs multiple matches within a block. It also reads water and castle metadata from the first Start marker where present. `Game/PlayerEnterExit.cs#TransitionDungeonInterior` requires Start for ordinary dungeon entry. `StartDungeonInterior` can prefer Enter and falls back to Start when Enter is unavailable. Those source labels alone do not verify the original deep-cave pose and facing.

## Detailed rules and behaviors

1. Resolve a marker from the stable dungeon, block placement and local marker identity in the effective layout. Bind each route to its declared landing or marker selection policy. Two entrances can explicitly share one landing while retaining their own doorway identity and return links under MOVE-026.
2. Map supported classic Start and Enter records to route roles during content preparation using verified source layout and placement evidence. Preserve source identity and placement context. Require a validated override or fail affected preparation when a required binding remains missing or ambiguous. Keep environmental metadata interpretation under its owner independent of arrival selection.
3. Resolve the standard new-game opening against CORE-011's verified deep-cave marker and original facing. Use the exterior start only when selected through CORE-011's explicit option. Required opening failures follow approved opening recovery.
4. For a general dungeon route, apply its authored default, optional selection policy and ordered eligible backups under WORLD-003. Check the destination, access and placement for each eligible candidate. Named doorway and opening requests retain their mapped target. MOVE-027 validates clearance, support and any bounded correction within the intended space. If permitted placement fails, return explicit failure through the applicable route or recovery flow.
5. Hand resolved marker identity, pose, facing and route context to the placement owner. Marker resolution alone does not commit entry. Ignore obsolete results after a request, activation or layout change.

## Formulas, parameters and configuration

Validated content defines marker roles, poses, facing, route bindings and ordered general-route backups. MOVE-027 supplies placement correction bounds. Exact classic conversion, marker coverage and any general-route approach metrics remain open. No new numeric defaults are selected.

## Required data

Stable dungeon, block placement, marker and applicable doorway IDs. Resolved layout version, source provenance, role, local pose and facing, destination or route binding, ordered backups where applicable, active frame and request context.

## Inputs, outputs and events

- **Inputs** — Resolved layout and marker definitions, validated classic mappings or overrides, route or opening intent, and readiness and placement context.
- **Outputs** — Scoped marker and resolved pose with provenance, ordered eligible candidates for general routes, or explicit missing, ambiguous or failed result.
- **Events** — Identify affected route and marker context in preparation failures. CORE, WORLD and MOVE publish their respective committed outcomes.

## Cross-system interactions

- **DATA-003/005 and MOD** validate source markers and overrides. **LOC-009** provides the resolved dungeon and required readiness. **LOC-012** owns dungeon water and special-block behavior.
- **CORE-011** owns the opening choice. **WORLD-003 and MOVE-026/027** own arrival, traversal and placement. **SAVE** coordinates native restoration and compatibility. Quest placement follows its own role and binding rules.

## Edge cases and failure conditions

- Check multiple starting blocks, repeated block templates, missing markers and reordered source records. Validate the intended binding with placement scope.
- Check a named doorway with a blocked marker, and a general route whose backup would bypass restricted access. Bounded correction stays within the intended space. An ineligible backup cannot be used.
- Check a missing deep-cave binding and an unavailable general route. Apply the recovery for the actual request.
- Check invalidated layouts and obsolete placement work before commitment.

## Save/load considerations

Restore the saved authoritative pose and context through SAVE and MOVE-027. Preserve stable doorway or marker references where durable owner data requires them. Validate compatibility and apply explicit migration or recovery for required missing or changed references. Load does not choose a fresh arrival marker or replay dungeon entry.

## Technical constraints

Target Godot 4.7.2. Keep stable marker identity independent of source enumeration and live scene handles. Resolve poses in the active dungeon frame and keep readiness distinct from committed placement. Import tooling and schema remain open.

## Acceptance criteria

1. Distinct doorway routes can resolve distinct landings, and explicitly linked entrances can share one. Repeated blocks retain distinct marker scope.
2. Classic fixtures verify required bindings independently of enumeration order, including the original deep-cave opening pose and facing. Missing or ambiguous required links use a validated override or fail explicitly.
3. General routes can use eligible authored backups. Named and opening routes retain the selected target and use only bounded local correction. Exhausted placement follows approved recovery.
4. Native load restores the saved pose under its placement rules without fresh marker selection or entry replay.
