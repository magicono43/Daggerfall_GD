# LOC-002 — Building identity and directory

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-14 with “I approve”.

## Gameplay purpose and intended player experience

Keep discoveries, personal map labels, quest destinations and service references attached to the intended building across visits, reloads and compatible content edits. Let gameplay systems find buildings before the relevant exterior is active.

## Confirmed requirements

- **LOC-002-D01.** Give a building a persistent ID scoped to its location. Moving, rotating, renaming or reskinning the same building within its location can preserve the ID. Check compatibility of entrances, quest bindings and saved poses independently. A replacement building or a move to another location gets a new scoped identity. Use explicit migration where continuity is intended.
- **LOC-002-D02.** Return validated building records and candidate sets by type or faction in stable order for the same content. Requesting systems own eligibility and selection.
- **LOC-002-D03.** Reject ambiguous duplicate building IDs within a location through approved content recovery, identifying both contributing records. Allow intentional replacement through a validated override.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#loc-002-interview-decisions).

## Existing Daggerfall Unity behavior

In the local DFU 1.1.1 snapshot, `Assets/Scripts/Game/BuildingDirectory.cs#SetLocation` indexes building summaries from exterior blocks. `MakeBuildingKey` packs the block grid coordinates and record index and remaps zero. `GetBuildingSummary`, `GetBuildingsOfType` and `GetBuildingsOfFaction` provide lookup and filtering. `Assets/Scripts/Internal/DaggerfallInterior.cs#GetSceneName` uses map ID and building key for interior scene names. The packed key can change when layout coordinates or record order change. This is a static source trace.

## Detailed rules and behaviors

1. Resolve building identity with the stable location ID and persistent local building ID. Use validated layout data to bind it to the current placement and building record. Keep classic packed keys usable as import mappings for their source context. Names, geographic pixels, coordinates and live scene handles serve their own lookup or presentation purposes.
2. Resolve validated building definitions independently of live area activation. Exact lookup returns a matching record or an explicit lookup outcome. Type and faction queries return matching records in a deterministic order for the same resolved content. Owners apply access, reachability, availability, disclosure and quest eligibility where relevant.
3. Permit local ID reuse in separate locations. Repeated block placements in one location resolve distinct building identities. Validate uniqueness after resolving content overrides. Reject unresolved duplicates with location, building ID and contributing record provenance. Resolve explicit overrides through DATA-003 before publishing the effective directory.
4. A validated override can edit the same building under its existing ID. An override that introduces a successor building follows the replacement and migration rule. Migration must identify the source and destination and be validated for the affected reference. Owner-specific state remains subject to owner compatibility checks.

## Formulas, parameters and configuration

The DFU reference formula is `(layoutX << 16) + (layoutY << 8) + recordIndex`, with zero remapped. The target directory uses a scoped persistent ID. Mod content may define IDs, classifications, faction associations and supported overrides through validated content. ID encoding, import mapping representation, sort keys and index structure remain open.

## Required data

Stable location and local building IDs, placement and scoped record references, supported type and faction metadata, layout and content versions, classic import mappings where applicable, and source provenance for overrides and diagnostics.

## Inputs, outputs and events

- **Inputs** — Validated active building definitions, scoped lookup references, and type or faction filters.
- **Outputs** — A validated building record, an ordered candidate set, or an explicit missing or failed lookup outcome as applicable. An empty candidate set is valid.
- **Events** — Content validation reports ambiguous definitions. WORLD and gameplay owners publish readiness, access, discovery and quest events through their established contracts.

## Cross-system interactions

- **LOC-001 and DATA-005** supply placement and scoped record context. **DATA-003/004** govern overrides, recovery and location identity.
- **WORLD-006** coordinates activation and live readiness. **WORLD-015/016/018** use stable references for authorized discovery, maps and restore.
- **MOVE and LOC entrance features** resolve applicable entrance bindings. **QUEST, ECON, NPC and FACT** own eligibility and selection for their requests. **SAVE** coordinates durable restore and migrations.

## Edge cases and failure conditions

- Two towns in one pixel may reuse a local ID. Lookups still resolve by location scope.
- Same-name buildings and repeated blocks can appear in one town. Each retains its own identity and state.
- Renaming or reskinning preserves identity when the definition still represents the same building. A missing door or incompatible quest binding still requires owner validation.
- A valid directory record may have an unready live entrance. An eligible query may return several candidates or none.
- A split, merge or cross-location move needs explicit compatibility handling for each affected reference. A missing required target follows approved recovery.

## Save/load considerations

Persist scoped building references with the compatibility context needed by their owners. Rebuild the directory from validated active content. Validate saved pose, quest bindings and other required references independently before restoring them. Use explicit validated migration or approved recovery for missing or incompatible targets. Apply WORLD-018 to eligible map-only references. Loading does not replay discovery or entry.

## Technical constraints

Target Godot 4.7.2. Keep definition lookup independent of live node creation and stable across world rebases. Reject ambiguous identities before publishing records as usable. Engine representation, public APIs and cache policy remain open.

## Acceptance criteria

1. Exact lookup distinguishes identical local IDs in two towns in one pixel and repeated building placements in the same town. Lookups work before live doors are ready.
2. An edit preserving building identity retains the same scoped reference. An incompatible entrance, quest binding or saved pose is handled through its owner.
3. Type and faction queries return deterministic candidate sets. Consumers apply their own eligibility and selection rules.
4. An ambiguous duplicate within one town fails validation and reports both records. A validated override produces one coherent effective record.
5. Replacements and cross-location moves use new scoped identities. Existing references follow validated migration or the applicable recovery flow.
