# LOC-005 — Interior reconstruction from a door

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-14 with “I approve”.

## Gameplay purpose and intended player experience

Enter the space that the selected door serves. Front and back doors into the same shop lead to the same rooms, occupants and durable changes. Independent suites can reuse a layout and retain their own state. The automap reflects the interior the player can actually explore.

## Confirmed requirements

- **LOC-005-D01.** Use explicit building-scoped interior IDs. Entrances linked to the same interior share its owner-held state. Support multiple authored interiors in one building and independent instances of a shared layout template.
- **LOC-005-D02.** Prepare the resolved layout, required collision, entrance binding, gameplay-critical records and owner state before handing the destination to MOVE. Optional decoration may finish later where safe. Discard failed partial preparation and follow MOVE-026 recovery, retaining the valid exterior when available.
- **LOC-005-D03.** Derive automap geometry and spatial references from the same resolved layout and variant as gameplay. Allow simplification for readability and apply established discovery rules.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#loc-005-interview-decisions).

## Existing Daggerfall Unity behavior

Static inspection of the local DFU 1.1.1 snapshot. `Assets/Scripts/Internal/DaggerfallInterior.cs#AssignBlockData` finds the door's block index in the current location's RMB data and selects its subrecord by the door's record index. It throws for a missing or wrong-type block or a record with no interior 3D models. `DoLayout` adds models, flats, occupants, action doors and spawn points. `DoLayoutAutomap` reads the same record and calls the models-only path. `GetSceneName` uses map ID and building key. `Assets/Scripts/Game/PlayerEnterExit.cs#TransitionInterior` catches assembly exceptions, discards the partial interior and reports transition failure.

## Detailed rules and behaviors

1. Resolve the selected stable entrance to a location, building and interior ID through the validated LOC-003 link. Resolve the effective layout and variant and the specific arrival and return bindings. Keep the selected entrance identity through staging and handoff. Classic imports map supported RMB records into the same identity and binding model.
2. Scope durable state by interior instance and the relevant local record. Entrances to the same interior resolve the same owner state. Separate interior IDs retain independent state when they use a common layout or asset. Coordinate reconstruction with owner restore and lifecycle rules so repeated entry cannot duplicate occupants or loot or reset state solely because a different door was used.
3. Prepare the required layout, collision, entrance binding and gameplay dependencies for the destination. Restore required owner state before declaring the interior ready. Once ready, hand the resolved destination and placement context to MOVE. MOVE retains access and final placement validation and commits the transition. Optional presentation can finish later where safe.
4. If a required definition, link, layout or owner restore fails, discard partial preparation and report the affected entrance or interior and cause where available. Use MOVE-026 recovery and retain valid exterior context where available. Reject obsolete preparation results after their request or content context changes.
5. Derive automap geometry, connections and marker references from the effective interior layout and variant. Simplified geometry may improve legibility while preserving the spatial relationships used by the map. Apply map disclosure rules and saved discovery under their owners. Building the automap does not activate the interior or instantiate its gameplay state.

## Formulas, parameters and configuration

Authoring defines interior IDs, entrance links, layout templates and supported variants and overrides. Required dependencies follow the destination's gameplay requirements. No new balance formulas, geometry tolerances or readiness timeouts are selected.

## Required data

Stable location, building, interior and entrance IDs. Resolved layout and variant identity with version and provenance. Scoped local record IDs, entrance and return bindings, geometry, collision and map references, required owner dependencies, and request and activation identity.

## Inputs, outputs and events

- **Inputs** — Validated entrance or restore context, active content, environment inputs, and required owner state.
- **Outputs** — Prepared interior identity and layout, current placement binding, derived map data, or explicit pending or failed preparation.
- **Events** — Distinguish assembly readiness and failure from committed entry. MOVE publishes the committed transition under its approved contract.

## Cross-system interactions

- **LOC-001/002/003 and DATA-003/005/021** provide layout context, scoped identity, entrance links and validated content. **LOC-006** defines detailed marker and exit matching.
- **MOVE-026/027, CORE and WORLD** own entry commitment, pose validation, readiness and recovery.
- **NPC, ITEM, QUEST, SAVE and local action owners** provide and restore durable state. **LOC-018 and UI** use the resolved layout under applicable map discovery and presentation rules.

## Edge cases and failure conditions

- Check two entrances into one shop and two independent suites reusing one template. Verify shared or independent state according to the authored interior IDs and preserve each entrance's binding.
- Check missing classic records, incompatible overrides, invalid links, and required owner restore failures. Discard partial preparation and apply explicit recovery.
- Check duplicate requests and obsolete completions. Optional decoration and map generation cannot commit entry or duplicate gameplay.
- Check a changed layout variant against both the live interior and automap, including marker positions and discovery compatibility.

## Save/load considerations

Persist committed interior and entrance context with stable references and required compatibility data. Reconstruct the effective compatible layout and restore durable state through its owners. Validate saved pose, required links and changed records with MOVE and SAVE. Use explicit migration or recovery for incompatible required references. Loading restores committed context without replaying doorway activation or entry outcomes.

## Technical constraints

Target Godot 4.7.2. Keep interior instance identity independent of layout template, entrance, and live scene handle. Use a consistent resolved layout and variant across gameplay and automap preparation. Scene staging, caching and map geometry generation remain open.

## Acceptance criteria

1. Front and back entrances linked to one interior resolve the same interior ID and durable state and retain their respective arrival and return bindings.
2. Two interiors reusing a layout preserve independent state through repeated entry and save/load.
3. Required dependencies are ready before MOVE can commit entry. A required failure discards partial preparation and follows the approved transition recovery.
4. The automap matches the resolved gameplay layout and variant, applies authorized discovery, and creates no occupants, loot or entry outcomes.
5. Native restoration reconstructs the committed interior and validates required references without replaying entry.
