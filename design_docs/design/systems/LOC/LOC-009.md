# LOC-009 — Dungeon block assembly

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-14 with “I approve”.

## Gameplay purpose and intended player experience

Enter a coherent dungeon whose intended passages, stairs, doors and mechanisms work across block boundaries. Preserve supported classic layouts and allow irregular native layouts. Revisiting or restoring a dungeon reconstructs the intended spaces and owner-held state.

## Confirmed requirements

- **LOC-009-D01.** Preserve classic grid placements on import. Support snapped and freely positioned, rotated pieces in native layouts. Validate intended traversable connections, including stairs and passages between levels.
- **LOC-009-D02.** Preserve intentional door pairs. Suppress a duplicate only through a verified classic import rule or explicit authored relationship. Validate the retained door and affected action, quest and save references. An unresolved conflict that blocks a required passage fails preparation.
- **LOC-009-D03.** For initial dungeon support, prepare the full gameplay-critical layout, including collision, required links and required owner state, before entry commits. Assembly may proceed block by block. Safe optional decoration may finish afterward.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#loc-009-interview-decisions).

## Existing Daggerfall Unity behavior

Static inspection of DFU 1.1.1. `Assets/Scripts/Internal/DaggerfallDungeon.cs#LayoutDungeon` instantiates the declared RDB blocks at X/Z grid offsets, resolves markers from designated starting blocks, and applies per-block water and special-block metadata. `RemoveOverlappingDoors` registers static exits and disables action doors whose origins are less than 1.4 Unity units from a registered exit centre or a previously retained action door. The retained action door can therefore depend on enumeration order. `Assets/Scripts/Utility/RDBLayout.cs` supplies block geometry, action doors, action links and population construction.

## Detailed rules and behaviors

1. Resolve the dungeon's active layout and its placed block definitions. Preserve supported source placements and references through classic coordinate conversion. Native content can combine snapped and free transforms. Scope records to their dungeon and block placement so repeated templates have independent live objects and durable state.
2. Validate connections intended for traversal against the effective geometry and collision, including elevation changes and inter-block stairs. Check the intended access and traversal conditions, including doors or mechanisms that deliberately constrain a route. Preserve deliberate separation where the layout declares it.
3. Detect candidate door conflicts after applying resolved transforms. Preserve intentional pairs. Suppression requires a verified classic import rule or explicit authored relationship with a defined retained door. Validate affected action, quest and durable references under their owners. A required reference needs a valid binding, explicit compatible migration or the applicable failure outcome. If an unresolved conflict blocks a required passage, fail dungeon preparation.
4. Stage assembly by block if useful. Before declaring the destination ready for MOVE, validate the entire gameplay-critical dungeon layout, collision and required links and restore required owner state. Optional decoration may complete afterward where safe. MOVE retains final placement validation and transition commitment.
5. A missing, malformed or unsupported required block, a required link failure or an unreconciled required owner-state failure discards partial preparation and follows DATA-005 and MOVE-026 recovery. Preserve the valid source context when available. Stale preparation results cannot publish readiness for a newer request.

## Formulas, parameters and configuration

DFU places a block at `(X × RDBSide, 0, Z × RDBSide)`, where `RDBSide` is 2,048 classic units converted by DFU's global scale. The 1.4 Unity-unit door test is a source reference. Native layout content declares placement transforms, intended connections and supported duplicate relationships. Godot units, snapping, tolerances and validation algorithms remain open. This feature introduces no population, loot or reset formula.

## Required data

Stable dungeon, block definition, block placement and scoped record IDs. Resolved layout version and provenance, placement transforms and coordinate frame, intended connections, collision geometry, marker and action references, door relationships, required owner state and preparation identity.

## Inputs, outputs and events

- **Inputs** — Validated layout and block definitions, destination request or restore context, content overrides and required owner data.
- **Outputs** — Scoped assembled layout and bindings, readiness for MOVE, or an explicit pending or failed result with affected records where available.
- **Events** — Assembly reports readiness and failure. MOVE and other gameplay owners publish committed transition and gameplay outcomes.

## Cross-system interactions

- **DATA-003/005/021 and MOD** supply verified block records, assets and validated overrides.
- **LOC-010 through LOC-017** supply variant, marker, environment, population, loot and action requirements as applicable. **LOC-018** consumes the effective layout for mapping.
- **WORLD, CORE and MOVE-026/027** coordinate readiness, final placement and failure recovery. **NPC, ITEM, QUEST and SAVE** own restoration and compatibility for their durable records. **AV** consumes layout and presentation data.

## Edge cases and failure conditions

- Test rotated block seams, vertical passages and repeated templates. Check that a required connection works under its authored traversal conditions.
- Test a verified duplicate, two intentionally adjacent doors and an overlap that leaves a required passage blocked. Validate action and quest targets after suppression.
- A late required failure after several blocks assemble invalidates preparation. Safe optional work cannot publish entry or mutate required state through an obsolete request.
- A layout edit with unchanged IDs can still invalidate a saved pose, link or quest target. Validate compatibility under the applicable owner rules.

## Save/load considerations

Reconstruct the compatible resolved layout using stable dungeon, placement and record references. Restore durable owner data before releasing the readiness gate. Validate pose, action links and quest references independently where the layout changes. Apply validated migration or explicit recovery for incompatible required data. Native restoration produces no repeated entry or gameplay outcome.

## Technical constraints

Target Godot 4.7.2. Keep definition, placement and live instance identity distinct. Publish a coherent gameplay-critical layout before allowing play. Scene assembly order, caching and optional presentation scheduling remain open.

## Acceptance criteria

1. A representative classic dungeon preserves supported placements and links. A native layout can connect snapped and rotated pieces, including passages between levels. Repeated placements resolve independent records and state.
2. Verified duplicate suppression preserves the intended surviving door and validated references. Intentional pairs remain usable. An unresolved conflict blocking a required passage fails preparation.
3. Block-by-block preparation exposes no playable partial dungeon. Entry commits after all required collision, links and owner state are ready. A late required failure discards the partial destination and follows approved recovery.
4. Restoration reconstructs the applicable layout and durable state without replaying entry. Incompatible required references follow validated migration or recovery.
