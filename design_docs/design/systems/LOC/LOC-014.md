# LOC-014 — Treasure and quest placement surfaces

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-14 with “I approve”.

## Gameplay purpose and intended player experience

Place treasure and quest resources where players can reach them through the intended dungeon routes. A fresh visit restores ordinary treasure while preserving outstanding quest items and prior acquisitions.

## Confirmed requirements

- **LOC-014-D01.** Scope stable placement IDs to placed dungeon blocks. Import verified classic treasure, quest-item and quest-spawn roles. Support explicitly declared shared roles and capacity in validated native and modded content.
- **LOC-014-D02.** Restore ordinary treasure at authored placements on the LOC-013 reset. Generate fresh ordinary contents once per successful reset and restore explicitly fixed ordinary contents as authored. Carry forward the exact outstanding quest item and its custody. Acquired quest items remain acquired.
- **LOC-014-D03.** For blocked placements, use only eligible authored alternatives or an explicitly authorized QUEST-013 fallback. Preserve settled contents and resource identity on retries. A required placement fails through its owner when candidates are exhausted. Optional treasure remains absent.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#loc-014-interview-decisions).

## Existing Daggerfall Unity behavior

Static inspection of DFU 1.1.1. `Assets/Scripts/Utility/RDBLayout.cs#AddFlats` handles random treasure records. `AssignFixedTreasure` can supply the placement and appearance while still calling `AddRandomTreasure`, which generates contents through the dungeon-type loot table. `Assets/Scripts/Game/Questing/Place.cs#EnumerateDungeonQuestMarkers` enumerates spawn and item markers separately from treasure construction. Quest code binds resources to the selected markers.

## Detailed rules and behaviors

1. Resolve each placement using the dungeon, block placement and local record ID. Use the effective layout transform and declare supported roles, pose and capacity. Reused blocks resolve separate placements. A multi-role placement can host both ordinary treasure and a quest item when its authored capacity and owner rules permit that combination.
2. Validate quest claims, compatibility and capacity through QUEST-013. A single-capacity marker rejects competing claims. Reconstruct existing logical bindings before admitting ordinary placement where the roles compete. Markerless quests can use the authorized QUEST-013 modes.
3. Stage fresh ordinary treasure for a new visit under LOC-013. Resolve authored fixed contents and ITEM-020 generation for generated contents. Retain each settled result, including an empty result, across retries. Commit the reset and new treasure with successful reentry. Preserve exact outstanding quest item identities and their custody, including a quest item in a shared chest. Already acquired quest items stay acquired. Apply ordinary drop cleanup and protected custody through LOC-013 and ITEM-022.
4. Validate pose, usable support and access within the intended gameplay context. A locked route or other authored barrier retains its intended rules. Try eligible authored alternatives or an authorized quest fallback under its owner policy. Keep settled contents and resource identity when placement changes. Exhausted required placement follows owner recovery. Optional treasure remains absent.
5. Within a visit, reattachment, inspection and native load reuse the current contents and custody. Use approved migrations or recovery for incompatible changes to required placements.

## Formulas, parameters and configuration

Content defines roles, capacity, authorized alternatives, fixed contents and loot profile references. ITEM-020 owns generation and probability. LOC-013 owns reset timing and moddable reset policy. Exact placement tolerances and role schema remain open.

## Required data

Stable dungeon, block, placement, container and resource IDs, resolved transforms and content version, roles and capacity, valid alternatives, loot profile or fixed contents, visit and generation identity, applicable quest claims, custody and provenance.

## Inputs, outputs and events

- **Inputs** — Validated layout and placement definitions, visit or reentry context, quest claims, owner custody, loot results and placement checks.
- **Outputs** — Resolved treasure placements and quest candidates, retained bindings, or classified unavailable or failed results.
- **Events** — Publish reset and placement outcomes through their owners. Preparing or attaching a container produces no acquisition or quest credit.

## Cross-system interactions

- **LOC-009/013 and DATA-003/005** supply the resolved layout, placement scope, reset boundary and validated overrides.
- **ITEM-020/022 and RULE-003** govern generation, retained results and custody. **QUEST-013** governs resource claims and fallback modes. **MOVE and SAVE** coordinate entry, compatible restoration and recovery.

## Edge cases and failure conditions

- A shared chest can contain ordinary loot and an outstanding quest item. Reset refreshes the ordinary contents while retaining quest custody.
- Competing claims against one exclusive placement follow QUEST-013. A nearby marker with another role is ineligible unless explicitly authorized.
- A blocked placement retry keeps settled contents, including an empty roll. Required failure follows owner recovery without publishing a partial reset.
- A moved, replaced or removed block requires compatibility checks for its claimed markers and durable items.

## Save/load considerations

Restore the visit, settled generation results, container custody and quest claims using stable scoped references. Loading inside preserves current contents and acquired state. If a reset is due, apply it on successful reentry. Incompatible required references use approved migration or recovery.

## Technical constraints

Target Godot 4.7.2. Keep authored placement identity, per-visit generation and durable resource custody independently resolvable. Validate the active layout and request before publishing. Scene representation and spatial checks remain open.

## Acceptance criteria

1. Repeated blocks produce independently scoped placements. Declared shared roles honor capacity, and conflicting exclusive claims follow QUEST-013.
2. Successful stock reset refreshes generated ordinary contents and restores fixed ordinary contents. Outstanding quest custody persists and acquired quest items do not reappear.
3. A blocked placement uses only an eligible alternative or authorized fallback and retains its settled result. Exhausted required and optional placements follow their respective outcomes.
4. Reopening or loading within the same visit preserves contents, claims and acquisitions. A failed reentry leaves the reset due.
