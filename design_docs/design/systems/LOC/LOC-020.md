# LOC-020 — Local scene reconstruction and state

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-14 with “I approve”.

## Gameplay purpose and intended player experience

Resume in the saved interior or dungeon with the same established state. A moving lift resumes from supported saved progress, a looted container stays looted, and quest actors retain their assignments and outcomes. A changed layout produces a clear recovery outcome when a required saved binding cannot be restored.

## Confirmed requirements

- **LOC-020-D01.** Save the resolved layout and visit identity and durable owner state using stable scoped IDs. Rebuild scene objects and derived views from those records.
- **LOC-020-D02.** Check layout compatibility and required bindings before replacing the current session wherever detectable. Use validated migration for changed references. Unresolved required bindings use explicit recovery. Eligible map-only records can remain inactive with disclosure.
- **LOC-020-D03.** Gate play until the selected layout, required local state and restored pose agree. Restore supporting mechanisms before dependent pose validation and quest claims before ordinary population. Resume supported pending actions from recorded progress and preserve committed effects. Loading inside preserves the visit. A reset due after departure takes effect on successful reentry.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#loc-020-interview-decisions).

## Existing Daggerfall Unity behavior

Static inspection of DFU 1.1.1. `Assets/Scripts/Game/Serialization/SaveLoadManager.cs` restores position, waits for respawning and object registration, applies door, action, enemy and loot state, then loads automap data separately. `SerializableActionDoor` and `SerializableActionObject` restore motion progress and restart tweens. `SerializableActionDoor` increments colliding load IDs at registration, which can make the resulting identity depend on registration order. `SerializableLootContainer` restores container records.

## Detailed rules and behaviors

1. Capture one coherent committed save generation at an admitted boundary. Record the selected layout and variant, content compatibility context, location and visit identity, and durable records through their owners. Include applicable door and mechanism state, supported pending work and committed effects, enemy and quest bindings, item custody, map knowledge and reset eligibility.
2. Preflight saved layout, variants and required references against validated active content. Resolve explicitly supported migrations and validate owner-specific compatibility. Treat a reference as required when placement, an active quest, persistent custody or another gameplay obligation depends on it. Reject detectable unresolved required failures before replacing the current session. Where approved, disclose and retain eligible map-only records inactive, with their original identity and provenance. Reactivate them only after compatibility and disclosure validate.
3. Prepare validated layout and geometry, then bind saved state to stable scoped records. Rebuild supporting mechanism state before validating dependent positions or attachments. Restore quest claims before resolving ordinary occupants in competing slots. Reconcile custody, locks, occupancy and other required owner facts before releasing play. Apply MOVE-027 to the saved pose and frame. Rebuild map and other derived views from restored authoritative records.
4. Resume supported pending actions from recorded milestones and timers. Preserve already committed effects and suppress duplicate dispatch. Unsupported in-flight conditions follow the relevant save admission restrictions. Late required failures stay behind CORE and SAVE recovery gates. Obsolete work cannot publish into a newer session or activation.
5. Native load restores the saved visit and its settled state. It creates no new entry, reset, discovery, acquisition or quest credit. Restore any reset due after departure and apply it only on successful reentry under LOC-013.

## Formulas, parameters and configuration

No gameplay formula is introduced. Validate layout versions, variant selections, supported mutation and pending-state schemas, and explicit migration mappings. Exact serialization, restore scheduling and save admission details remain with SAVE and the relevant owners.

## Required data

Stable location, layout, variant, placement, record and visit references, version and provenance, saved pose and support context, durable owner records, committed outcomes and supported pending progress, reset eligibility and compatible migration or inactive-record data.

## Inputs, outputs and events

- **Inputs** — Eligible save or restore request, coherent save generation, active validated content, owner data and compatibility results.
- **Outputs** — Committed snapshot, staged reconstructed location, explicit preflight or late failure, or validated ready context.
- **Events** — Distinguish preparation and restoration from fresh gameplay entry. Release readiness through CORE and SAVE after applicable checks.

## Cross-system interactions

LOC-005/009 provide the resolved layout. LOC-013 through LOC-019 define visit reset, local mutations and map state. DATA-005/024 and MOD govern validation and migration. CORE-013, SAVE and MOVE-027 govern admission, recovery and placement. QUEST, NPC, ITEM, COMBAT and MAGIC restore their authoritative facts through their owner contracts.

## Edge cases and failure conditions

- Test repeated block definitions and different object registration orders. Each durable record must bind to the intended placed instance.
- Test a missing quest target, a changed lift supporting the saved player, a removed container with persistent items, and an optional unresolved map pin. Required dependencies use explicit recovery. An eligible map-only pin may remain inactive with disclosure.
- Test a partially moved mechanism with already committed effects and an ordinary enemy slot claimed by a quest. Restore progress and claims without replay or duplication.
- Test loading inside a visit and loading outside with a reset due. Neither load commits a reentry reset.

## Save/load considerations

Persist authoritative records by stable scope and rebuild live representations. Capture and restore one consistent generation. Check required mappings and pose compatibility before control is released. Preserve eligible inactive history and outstanding obligations under their owners. Restore supported pending progress without replaying completed effects.

## Technical constraints

Target Godot 4.7.2. Keep runtime handles and registration order independent of durable identity. Stage results against the active session, layout and visit. Coordinate dependencies with SAVE without prescribing the global restore order or storage format.

## Acceptance criteria

1. The same save restores the intended scoped objects regardless of registration order and reconstructs derived views.
2. Detectable unresolved required references fail preflight with the current session intact. Eligible unresolved map-only records may be retained inactive with disclosure. Late required failures use approved recovery.
3. A supported mid-motion save restores mechanism state before dependent pose validation. Completed effects are preserved and quest claims resolve before competing ordinary occupants.
4. Native load inside restores the current visit. Load outside retains a due reset, which commits only on successful reentry.
