# DEV-002 — Environment report

**Approval status — Approved, finalized v1.** Updated 2026-11-18. See DEV-002-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Purpose and intended player experience

Give players a readable report they can review and share to help diagnose installation, startup and configuration problems. A player in startup recovery can inspect the information available at that point. A player in normal settings can inspect the current environment. Export is a deliberate local action after preview.

## Confirmed rules

1. Generate the report on demand from startup recovery and normal settings. Show a preview before local export.
2. Use an explicit field list covering game build, OS, CPU/GPU and graphics backend, language, storage mode, selected troubleshooting settings, classic-data validation results, and discovered mod IDs, versions and order. Mark unavailable sections when setup is incomplete.
3. Exclude absolute paths, usernames, device identifiers, credentials, save contents and recursive file listings. Apply the same field and privacy rules to preview and export.

See DEV-002-D01 and D02 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Approved export and failure behavior

- Export the sanitized text shown in the preview to a local destination the player chooses. If setup changes while a preview is open, export the displayed report and let the player generate a fresh one. Ask before replacing an existing file.
- If a section is unavailable or fails to collect, show its status and keep the remaining report available. Distinguish a failed check from a check that has yet to run. If a write fails, show an export error and keep the preview available for another attempt.

## Required data, inputs, outputs and events

Inputs are the player's report, export and cancel actions and the approved fields available from the running application. Use the status of required classic-data checks and the available mod discovery and order state. Identify pending or incomplete results as such. Outputs are the sanitized preview, a local text file upon successful export, and an export success or failure result. Event and API names remain technical design.

## Cross-system interactions and save/load

- [CORE-001](../CORE/CORE-001.md) supplies storage mode when established. Report viewing is available through recovery UI even when application storage is unavailable. [CORE-004](../CORE/CORE-004.md) owns startup routing and recovery access, and [CORE-003](../CORE/CORE-003.md) supplies available settings.
- [DATA-001](../DATA/DATA-001.md) supplies existing validation outcomes. Report generation reuses those results. It does not trigger a new scan or change whether setup can continue.
- [MOD-003](../MOD/MOD-003.md) supplies dependency and order results when available. [MOD-007](../MOD/MOD-007.md) provides detailed content provenance in its own UI.
- [CORE-002](../CORE/CORE-002.md) governs launch logs. Viewing or exporting the report works independently of the logger, and the preview payload stays out of launch logs.
- Report state belongs to the application. Generating or exporting it does not affect character saves, load compatibility, or the active configuration.

## Parameters, configuration and technical constraints

There are no gameplay formulas, balance parameters or player-selectable collection levels. Define the troubleshooting settings by explicit field before implementation. Use safe validation labels or reasons where raw paths or error strings would disclose excluded data. In Godot 4.7.2, recovery access must work with bundled UI and incomplete application initialization. The text layout, filename, file picker integration and field adapters remain open.

## Daggerfall Unity reference

DFU generates `DFTFU_Environment.log` after successful validation on its runtime setup path. It reflects settings, collects system and locale information, and recursively enumerates directory and file paths. Many collected values also go into runtime logging. The writer opens the report with `OpenOrCreate` and does not truncate it, so a shorter write can leave previous text at the end. ## Acceptance criteria

1. Both startup recovery and normal settings can open a preview on request. A failed content check appears as a failure, and an unfinished check or mod discovery is explicitly marked as incomplete.
2. A fully initialized report shows the approved fields. Excluded values do not appear in the preview or export, including through validation messages or settings values.
3. Cancel leaves the filesystem untouched. Export writes the previewed report to the chosen local destination. Replacing a longer report with a shorter one leaves the new report complete and free of old trailing text.
4. An unavailable section leaves the remaining report usable. An export failure is visible, leaves the preview usable, and does not affect startup eligibility.
5. Report generation works with launch logging disabled and does not rerun classic-data validation, change mod ordering or write to character saves.
