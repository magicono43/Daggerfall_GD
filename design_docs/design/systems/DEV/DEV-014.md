# DEV-014 — Automated verification

**Approval status — Approved, finalized v1.** Updated 2026-11-18. See DEV-014-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Purpose and intended experience

Give developers repeatable checks for gameplay and lifecycle regressions. Run fast headless checks on proposed changes. Run a separate rendered suite when a scenario depends on rendered output, visual presentation or frame timing.

## Confirmed behavior

1. Start with three integration scenarios. Verify that a failed restore preserves the active session, an enemy encounter exercises placement and combat, and a quest fault and retry preserves previously committed effects.
2. Add focused formula and classic-record conversion checks as their owners implement the relevant behavior.
3. Use separate test storage. Control the random seed, clock and input where relevant so a failure can be reproduced without touching ordinary player saves.
4. Run headless checks on proposed changes. Run rendered checks separately from the routine gate.

See DEV-014-D01 and D02 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Approved execution and reporting rules

- Make both suites callable independently from a local development environment. Expose a separate rendered run for changes whose acceptance depends on a render or frame boundary. Exact runner, CI provider and invocation remain open.
- Drive integration checks through production entry points, using bounded fixture data and controlled inputs. Reset test session state and storage between independent scenarios. Use explicit assertions for relevant committed outcomes.
- Report the scenario, failed assertion, expected and actual outcome, and available reproduction inputs such as seed, fixture identity and engine/build. Mark unavailable prerequisites or skipped scenarios explicitly. A required headless scenario that could not run leaves the routine gate incomplete.
- Use owner-approved outcomes as the reference. Choose a rendered check for behavior observable only with rendering or real frame boundaries, such as validating a matching save thumbnail. A rendered test can attach diagnostic evidence for failed assertions.

## Required data, inputs, outputs and events

Inputs include the selected suite, fixture definitions and source samples, initial session and storage state, owner-defined expected results, injected failure conditions and reproducibility controls. Outputs include per-scenario pass, fail or unavailable results, suite status and available reproduction details. Rendered runs may provide a frame capture. Exact report and artifact formats remain technical design.

## Interactions, parameters and save/load

- [CORE-013](../CORE/CORE-013.md) and SAVE govern restore eligibility and preservation of the outgoing session on preflight failure. Model the failure using an isolated test save and verify the active session through normal owner outcomes.
- NPC, LOC and COMBAT define valid placement and encounter behavior. [QUEST-023](../QUEST/QUEST-023.md) and its recovery owners define preserved effects and retry eligibility.
- RULE and DATA supply formula expectations and representative format fixtures. AV and UI govern render-dependent evidence. [DEV-005](DEV-005.md) and [SAVE-002](../SAVE/SAVE-002.md) provide distinct examples of capture contracts.
- Test seeds, clocks and input sequences are fixture parameters. Test controls leave live gameplay formulas and defaults intact. Fixture saves and outputs stay in isolated storage and are outside the ordinary player catalog.

## Edge cases and technical constraints

Target Godot 4.7.2. Handle missing fixture inputs, unavailable graphics and incomplete operations with explicit outcomes. Protect production user roots and earlier test results where concurrent runs are supported. Avoid relying on incidental random state or advancing the real game clock to drive a test. Exact fixture assets, runner and timeouts, graphics targets and evidence retention remain technical design.

## Acceptance criteria

1. Proposed changes run the headless suite independently of rendered checks. A failed assertion or missing required scenario produces a visible gate failure or incomplete result.
2. Rendered checks can run separately with their own results. An unavailable renderer produces an explicit outcome.
3. A failed restore preflight retains the current test session and its relevant state. An enemy scenario verifies valid placement and a defined combat outcome. A quest fault and retry preserves committed effects and applies supported outstanding work once.
4. Repeating a controlled fixture with the same supplied inputs reproduces its asserted outcomes. Test runs and failures preserve ordinary player saves.
5. Formula and format checks use owner-approved expectations, and a failed check identifies enough fixture context to reproduce it.
