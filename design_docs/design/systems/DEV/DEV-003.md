# DEV-003 — Runtime console and command registry

**Approval status — Approved, finalized v1.** Updated 2026-11-18. See DEV-003-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Purpose and intended player experience

Give players and developers a keyboard console for inspecting the game, reproducing issues and deliberately changing game state. Players can discover commands and their usage in the console. The console is available in player builds and enabled by default.

## Confirmed rules

1. Provide an application-wide saved setting to disable console access and reenable it through Settings.
2. Give the open console exclusive input focus. By default, it requests a pause under the approved UI policy. Provide a setting to use it live. In live mode, time advances only when the other lifecycle and suspension rules allow it.
3. Make inspection and state-changing commands available to players. Changes to ordinarily saved state persist through the normal save system. Saves carry no command-use badge or other identifying marker. Temporary debug modes end with the session.
4. Allow enabled mods to add commands. Qualify mod command names by mod ID and reject conflicting registrations with useful diagnostics.
5. Include help, session inspection, player inspection, automap reveal, teleport to a validated destination, item addition, stat changes and guild-rank changes in the initial built-in command set.

## Approved operational rules

- Help lists commands and shows usage for an individual command. A command declares whether it inspects or changes state, which scope it needs, and which arguments it accepts. Keep case-insensitive lookup. Report unknown names, invalid arguments, unavailable context and command failures in the console.
- Validate arguments and check current scope before dispatch. Send mutations through the owning system. For example, validate teleport destinations and use the existing transition flow, and route item grants through inventory operations. Command requests cannot bypass lifecycle, transition, save or recovery gates. Individual command contracts must define any intentional bypass of normal gameplay prerequisites.
- Capture console text, submit, history and dismiss input while focused. Hand focus back through the approved UI rules and release only the console's own pause request. Live mode can leave the character exposed to normal world activity.
- Use a configurable toggle binding and bounded, application-run command history. Keep history out of character saves. When the console is disabled, its shortcut cannot open it.
- Register commands from the validated enabled mod configuration. A conflicting command registration fails with command and provider diagnostics. Built-in names remain reserved, and mod load order cannot silently select a different handler. Apply the established mod recovery policy where a conflict makes the candidate configuration invalid.

## Required data, inputs, outputs and events

Required data includes the console settings and binding, current focus and session context, and a registry with command ID, provider, usage, description, argument rules, required scope and handler. Inputs are toggle, dismiss, navigation, text submission, settings changes and validated mod contributions. Outputs are help, command results, errors, and focus or pause changes. Successful mutations use their owning systems' normal outcomes and events. Console results must distinguish success, rejection and failure. Exact API and signal names are deferred.

## Parameters and configuration

There are no console-wide gameplay formulas. The application enable setting defaults to on and console pause defaults to on. Command argument limits follow each owner and the command's approved behavior. The history limit, exact key default and text grammar remain technical choices. Supported stats, amounts, destinations and guild-rank semantics need command-level definitions.

## Cross-system interactions and save/load

- [UI-001](../UI/UI-001.md) governs layer navigation, focus and ordinary UI pause, including applicable mod overrides. [CORE-016](../CORE/CORE-016.md) governs suspension, cursor ownership and text input. Loading or leaving a session invalidates its console context.
- [DATA-003](../DATA/DATA-003.md) governs the validated mod configuration and its lock. Use the approved provider configuration for command registration and recovery.
- LOC and MOVE govern map state and destination movement. ITEM, CHAR and FACT govern item, stat and guild mutations. SAVE continues to govern which resulting state is serialized and when writes are eligible. An ordinary save neither identifies command use nor stores console UI state.
- [CORE-002](../CORE/CORE-002.md) governs privacy for any diagnostic written to launch logs. Command feedback remains available in the console if file logging is disabled.

## Edge cases and technical constraints

An unready or replaced session makes old targets ineligible. Validate live targets against current owner state. A handler failure must be visible, and the console should remain usable. For operations that can fail after effects begin, use the owner's outcome and recovery rules instead of reporting success or replaying the request automatically. The Godot 4.7.2 design uses the normal input, lifecycle and gameplay owner boundaries. Exact command grammar, scopes, command signatures and mod registration interfaces remain open.

## Daggerfall Unity reference

DFU splits submitted text on spaces, dispatches via a process-wide case-insensitive registry and keeps a 20-entry input history. Duplicate command names silently replace the earlier handler. The registry handles unknown commands, while other handler exceptions can escape it. DFU registers commands for guild and automap actions. ## Acceptance criteria

1. A default player installation can open the console. Disabling it persists across launches and characters, and Settings can reenable it.
2. Console input does not trigger gameplay actions. The default requests UI pause, and live mode leaves eligible simulation running. Closing the console preserves other suspension reasons and restores eligible focus.
3. Help documents the initial built-in command set. An invalid or unknown command provides useful feedback. A mutation against an invalid destination or stale session is rejected before dispatch.
4. Valid built-in mutations route through their respective owners. Ordinarily saved effects survive a save/load round trip with no command-use marker. Console history and temporary debug modes are excluded from character saves.
5. A command from an enabled mod appears under its qualified name. Conflicting registrations produce provider diagnostics and cannot silently replace an existing handler.
6. Command results and failures remain visible without a file logger. Closing or replacing a session releases stale console focus and its pause request.
