# DEV-004 — Quest debugger and exception records

**Approval status — Approved, finalized v1.** Updated 2026-11-18. See DEV-004-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Purpose and intended experience

Let quest authors inspect what a quest evaluated, which resources it bound, and what it committed. Give authors a way to exercise a specific quest in the game world and export recent diagnostic evidence. During ordinary play the journal continues to surface actionable recovery status under [QUEST-023](../QUEST/QUEST-023.md).

## Confirmed requirements

1. Open a searchable in-game inspector through the developer console. Inspect the current session read-only. Quest launches and other state-changing test controls operate only in an isolated in-world test context under [QUEST-005](../QUEST/QUEST-005.md).
2. Retain a bounded detailed trace for the current application run. Export a local copy only when the author explicitly requests it in the debugger.
3. Apply the approved QUEST-023 rules for visibility, grouping repeated faults, player notices, journal recovery and durable recovery data. See DEV-004-D01 and D02 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Inspector rules, data and events

- Search resolved quest definitions and live instances. Show task state, timers, flags, resource bindings, command and provider identity, recent condition results and owner outcomes, including pending and committed work. Show source spans when available. Filter the trace by quest, fault phase and outcome.
- Display previously recorded condition and operation results. Inspection does not rerun conditions, draw randomness or apply effects. Launch a quest by stable ID and exercise it using normal validation, generation and runtime paths in isolation.
- Inputs include console open and close actions, search and selection, explicit export requests, isolated test actions, and quest or owner diagnostic events. Required data includes stable quest and instance IDs, task, action and operation IDs, fault phase and reason, provenance, source spans, outcome and occurrence count where applicable.
- Outputs include the inspector view, trace updates, local export and visible export outcome. Ordinary fault notices and recovery actions remain governed by QUEST-023 and the responsible quest or operation owner.

## Approved retention and export rules

- Start with a limit of **1,000 trace entries and 4 MiB of retained diagnostic payload** per application run. Apply whichever bound is reached first. Aggregate repeated faults by the QUEST-023 grouping fields, retaining the occurrence count and recent context. Evict least recently updated entries as needed, and indicate when earlier trace detail has been evicted.
- Export the selected quest's available trace as readable text to a local destination the author chooses. Include available source, provider version, failed operation, relevant outcomes and any trace-loss indication. Exclude credentials, save contents and absolute personal paths. Confirm replacement of an existing file. A canceled or failed export leaves the trace available.
- Show missing source or provider information as unavailable. When a selected instance is no longer active, retain its available historical trace with its original instance identity and clear the live selection and stale controls.

## Interactions, configuration and persistence

- [DEV-003](DEV-003.md) provides the console entry and eligibility. Follow [UI-001](../UI/UI-001.md) and [CORE-016](../CORE/CORE-016.md) for focus and suspension. Opening the inspector must respect the current session and UI scope.
- QUEST-005 owns isolated tests, QUEST-011 owns suspension and cleanup, and QUEST-022 and SAVE own durable recovery. A character load restores supported fault and recovery state. The detailed trace is application-run data outside saves. Inspection, export failure and trace eviction cannot modify recovery state or invalidate saves.
- Diagnostic retention adds no gameplay formulas or balance settings. Use the approved limits without player-facing retention tuning. Godot 4.7.2 implementation details include the console command name, inspector layout, payload accounting representation and export formatting.

## Acceptance criteria

1. An eligible console command opens a searchable inspector. Selecting a live quest shows recorded task, binding, timer and operation state without altering the game or consuming randomness.
2. State-changing test controls require an isolated context. An author can launch a selected quest by stable ID in that context without affecting ordinary character history.
3. Repeat faults aggregate, both trace bounds hold, and the view indicates evicted history. A normal recovery summary remains usable after eviction, loading or an application restart.
4. Explicit export writes the selected quest's available sanitized evidence locally. Canceling or encountering an export failure leaves the trace available. Closing the game ends run-scoped trace retention.
5. Switching sessions or losing the selected instance removes stale live controls. An unavailable file logger does not prevent use of the inspector or a local export.
