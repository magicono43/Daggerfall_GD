# DEV-005 — Screenshots and debug evidence

**Approval status — Approved, finalized v1.** Updated 2026-11-18. See DEV-005-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Purpose and intended player experience

Let players save the game view as displayed, including its visible interface, for sharing or diagnosing visual problems. Players can hide the gameplay HUD before capturing a less obstructed view and restore it afterward.

## Confirmed behavior

1. Provide a rebindable screenshot action for gameplay and menus. Capture the rendered game view at its current size, including all visible game HUD, menus and overlays.
2. Let the player toggle the gameplay HUD. Apply the effective visibility rules in [CORE-016](../CORE/CORE-016.md) so another active hide request still takes effect.
3. Save lossless PNGs in `Screenshots` under the active storage root by default. Use timestamped names with collision handling that preserves existing files. Show a brief filename confirmation on success or an actionable reason on failure. Render feedback for the current capture after its image is taken.

See DEV-005-D01 and D02 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Approved settings and failure behavior

- Provide a separate rebindable gameplay HUD toggle that changes the existing player visibility preference. It affects gameplay HUD elements, while menu navigation, required dialogs and other independently owned UI follow their existing rules.
- Offer a saved screenshot destination override in Settings, with an explicit return to the default. Permit a user-selected existing local folder, including one outside the active root. This choice applies to manual screenshot output. If the chosen folder becomes unavailable or unwritable, report the failure and let the player choose another folder or restore the default.
- Bind each accepted request to its rendered game view and intended destination. If no valid frame can be captured for that request, report the failure. Collisions during bursts or between installations using the same override must preserve existing files. Report success only for a complete published PNG. Encoding and write failure leave gameplay and menu state usable.

## Parameters, data, inputs and outputs

Required data includes the active binding and input context, current rendered frame and pixel dimensions, effective HUD visibility, active storage root and configured destination, and timestamp and collision-safe file identity. Inputs include the screenshot action, HUD toggle, destination changes and capture, encoding and write results. Outputs are a local PNG and a success or failure notification. There are no gameplay formulas or balancing values. Filename syntax, exact default keys and PNG encoding settings remain technical design.

## Cross-system interactions and save/load

- [MOVE-002](../MOVE/MOVE-002.md) supplies rebinding and conflict rules. [UI-001](../UI/UI-001.md) and CORE-016 govern focus, HUD visibility and suspension. Screenshot input must respect text entry, rebinding and other exclusive input contexts.
- [CORE-001](../CORE/CORE-001.md) supplies the active storage root, including portable and development modes. [CORE-003](../CORE/CORE-003.md) supplies settings persistence. AV supplies the composited game frame. Capture leaves the existing simulation and input state in place.
- [SAVE-002](../SAVE/SAVE-002.md) governs save thumbnails, which use a matching world-only view. Manual captures have their own output files and outcomes. A manual capture failure cannot affect save or load. Character saves carry no manual capture state.

## Daggerfall Unity reference

DFU listens for the bound screenshot key release when its hotkey gate permits it. At the end of the frame it reads the full game screen, encodes JPEG, saves a timestamped file with a suffix for collisions and posts a HUD confirmation. It checks for an existing configured folder and otherwise uses `Screenshots` under the persistent root. [PrintScreenManager.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/Game/Serialization/PrintScreenManager.cs)

## Technical constraints and edge cases

Target Godot 4.7.2. Capture the game frame through its render lifecycle, including the presentation already composited into the requested view. Account for resizing, view replacement, rapid requests, directory removal, denied access and disk-full failures. Choose a capture, encoding and publication strategy that avoids incomplete files being presented as successful captures. Keep notifications usable when the gameplay HUD is hidden. Capture provides local output for manual sharing.

## Acceptance criteria

1. The configured action produces a lossless PNG of the displayed game frame during eligible gameplay and menu contexts, including the visible UI and excluding the current capture's own result notice.
2. A player can hide the HUD, capture the changed view and restore the HUD. Restoring the preference respects any other active hide request.
3. Default captures go to `Screenshots` under the active root. A configured override is used when selected. Reset restores the root-relative default. When an override becomes unavailable, the player sees a failure and can change it.
4. Repeated captures preserve all existing files, including when timestamps coincide. A failed frame, encode or write produces visible failure feedback. A success notification identifies the resulting file.
5. Manual captures and HUD preference changes leave SAVE-002 thumbnail eligibility and world-only composition intact.
