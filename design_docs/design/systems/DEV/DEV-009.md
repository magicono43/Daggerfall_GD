# DEV-009 — Text, definition and asset inspection/export

**Approval status — Approved, finalized v1.** Updated 2026-11-18. See DEV-009-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Purpose and intended experience

Help authors locate source records and visually identify game models, including assets whose appearance cannot be determined from a texture filename. Authors can inspect available content and export supported artifacts for editing in a chosen workspace.

## Confirmed scope and behavior

1. Start with classic text records, careers, items and spells, plus a 3D model viewer. Use existing readers and asset resolution. Make classic and enabled-mod models searchable by stable ID and name when available. Show the model with its resolved materials when available, with rotation and zoom.
2. Support mesh and texture export where feasible. A model that can render remains inspectable when a faithful export is unavailable. Explain which selected assets can be exported.
3. Export supported editable records to a chosen workspace. Validate them through the game's loaders. An unedited export and reimport must preserve the fields and behavior represented by the supported schema. Label simplified displays as inspection previews when they omit details.
4. Initial record exports are editable representations. Byte-exact classic record export is deferred. Font and location tools are outside this initial scope.

See DEV-009-D01 through D04 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Approved export details

- Start with supported static meshes and material assignments, plus PNG textures where supported. Report unsupported features, missing dependencies and meaningful conversion losses before writing. The exact mesh format and supported conversion matrix remain technical design.
- Label records and models with their source and stable identity. Show the proposed output files before writing and ask before replacing existing files. Keep the selected source and active game configuration intact.
- For supported editable records, report loader validation success or a specific rejection. If validation or a write fails, identify the affected artifact and any outputs already written. Inspection remains available.

## Required data, inputs, outputs and events

Inputs include the selected source and resolved mod context, source record or model ID, search and preview actions, explicit export selection, destination and replacement choice. Required data includes schema identity, source/provider provenance, model geometry, material slots and resolved textures where available, and loader validation results. Outputs include records or rendered previews, editable exports, supported mesh and texture files, and per-artifact export outcomes. API and event names remain open.

## Cross-system interactions, configuration and persistence

- DATA owns source reading and schema validation. CHAR, ITEM and MAGIC define their supported fields and behavior. AV supplies rendering and asset dependencies.
- [MOD-007](../MOD/MOD-007.md) provides content provenance. [MOD-016](../MOD/MOD-016.md) owns package validation, workspace inclusion and packaging. An export takes effect in play through the normal content and mod workflows.
- No gameplay formulas or balance parameters apply. The workspace and output choices are authoring inputs. Character saves carry no inspection or export state. Inspecting or exporting preserves character state.

## Edge cases and technical constraints

Target Godot 4.7.2. Preserve stable identity when source packages have identical display names. Handle malformed records, absent names, missing mesh dependencies, unsupported materials and unwritable destinations with source-specific feedback. Preview controls change only the preview camera. Exact UI integration, record schemas, portable mesh format and handling for animated or specialized materials remain technical design.

## Acceptance criteria

1. Authors can find supported text and definition records by stable identity and inspect their source and available fields.
2. Authors can find classic and enabled-mod models, rotate and zoom them, and see available resolved materials. A missing material or unsupported export has a visible explanation.
3. A supported editable record exports to the chosen workspace and reimports through the loader with supported fields and behavior intact. Rejected output has actionable diagnostics.
4. Supported static mesh exports retain geometry and material assignments within the documented format contract. Supported textures export as PNGs. Unsupported data or meaningful conversion losses are reported before writing.
5. The tool asks before replacing existing output. Canceling the export leaves the destination untouched. Inspecting and exporting preserve source files, active content and character state.

## Consistency review and outstanding questions

Reviewed against the approved DATA text structure rules, MOD-007 provenance and MOD-016 packaging. This feature reuses their readers and validation without changing active content resolution. Exact mesh format, detailed schema coverage and the supported conversion matrix remain open.
