# DEV-011 — Exterior block editing

**Approval status — Approved, finalized v1.** Updated 2026-11-18. See DEV-011-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Purpose and intended experience

Let authors build reusable exterior blocks or adapt supported classic blocks for a mod. Authors can save an unfinished draft, preview edits, reuse object groups and identify broken references before publishing playable content.

## Confirmed behavior

1. Create a native exterior block or start from an editable copy of a supported classic block. Add, move and remove buildings and scenery, edit ground tiles and import or export reusable object groups. Interior and whole-settlement editing have separate workflows.
2. Allow work-in-progress drafts to be saved. Before playable export, check required assets, stable IDs, and door and building links. With settlement and terrain context, run the applicable required-route and entrance checks. Identify missing context and unresolved checks. Runtime readiness remains governed by the normal validators.

See DEV-011-D01 and D02 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Approved authoring and export rules

- Use an explicit authoring workspace. Keep imported source records intact. Save drafts and export playable definitions as distinct actions. Ask before replacing an existing workspace file and before discarding unsaved edits.
- Preserve stable record IDs for retained records. Give added or pasted records fresh IDs within the destination definition. Remap links within the pasted group and report unresolved links to outside records. When a deleted record has known dependents, identify them and require resolution before playable export.
- Reject playable export on known validation failures. When only placement-specific checks lack context, allow a block definition export with those checks explicitly marked pending. Such an export can be packaged as a reusable block. The final placement still must satisfy the owning validation and readiness rules before play.
- Preserve supported untouched source content within the output schema, including gameplay metadata and automap data. When an edit requires derived data or bindings to be refreshed, use the owning rules or identify the unresolved requirement. Reopen the exported definition through the runtime reader as part of verification.

## Required data, inputs, outputs and events

Inputs include a new block request or supported source definition, workspace destination, editing and preview actions, selected object groups and available placement context. Required data includes stable definition and record IDs, block-local transforms, asset references, ground tiles, building and door bindings, scenery, automap data and validation outcomes. Outputs include an editable draft, group artifact, exported block definition and diagnostics scoped to the affected record or check. Exact commands and event names remain technical design.

## Interactions, parameters and save/load

- [DATA-005](../DATA/DATA-005.md) governs block and record identity, reference validation and replacement compatibility. [LOC-001](../LOC/LOC-001.md) owns placement, required routes and entrances. WORLD owns terrain context and area readiness.
- [DEV-010](DEV-010.md) provides read-only inspection and overlays. Reuse preview capabilities where they can display the draft in isolation. [MOD-016](../MOD/MOD-016.md) governs validation and packaging of mod workspaces.
- No new gameplay formulas apply. The block schema and owners define valid transforms, coordinates, tile ranges and record limits. Exact snapping controls and output representation remain open.
- Authoring state belongs to the workspace. An export enters play through normal content selection and validation. Changes to references used by saves or quests require the owners' compatibility or recovery process.

## Edge cases and technical constraints

Target Godot 4.7.2. Treat malformed drafts, missing assets, ambiguous IDs, broken links and invalid placement as explicit diagnostics. Avoid partial acceptance of an invalid group import. Keep live scene activation and authoring preview state independent. A write failure must leave the draft available and report whether the destination was published. Exact UI, file schema, reference migration tools and derivation algorithms remain technical design.

## Acceptance criteria

1. Create a native block and edit a copy of a supported classic block. Save and reopen each draft with changes intact while preserving the input files.
2. Add, move and remove buildings and scenery, edit ground tiles, and reuse a selected object group. Reusing a group assigns new destination IDs and preserves its supported internal links.
3. Missing required assets, duplicate IDs or broken required bindings block playable export and identify the affected record. Invalid drafts remain savable for later repair.
4. In a supplied terrain and settlement context, required route and entrance checks run and failures block export. Without context, those checks are visibly pending and final placement still goes through normal readiness validation.
5. A valid exported definition reopens through the runtime reader with its supported records and references intact. Canceling an overwrite preserves existing output.

## Consistency review and outstanding questions

Reviewed against DATA-005, LOC-001, DEV-010 and MOD-016. The approved workspace, group identity and export rules follow existing identity, validation, readiness and packaging requirements. Output schema, editor surface and derivation mechanisms remain open.
