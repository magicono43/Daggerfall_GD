# DEV-012 — World data editing

**Approval status — Approved, finalized v1.** Updated 2026-11-18. See DEV-012-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Purpose and intended experience

Let authors build new locations and adapt existing settlements, interiors and dungeons. Authors can preview terrain and layout together, inspect broken links before export, and understand whether a change can be used with affected saves.

## Confirmed behavior

1. Arrange exterior blocks within existing settlements. Edit objects, entrances, markers and action links in existing interiors and dungeons. Support reusable variants and explicit placement-specific edits.
2. Create entirely new locations and author terrain shaping for those locations and their approaches. Use the location owner's terrain and route validation.
3. Preserve stable IDs for retained records and show affected links and known save or quest dependencies before export. Broken required links block export.
4. To claim save compatibility after changing persistent records, supply a mapping that passes the owning compatibility checks. Authors may publish an otherwise valid variant as incompatible with affected saves. Those saves follow the approved recovery flow.

See DEV-012-D01 through D03 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Approved workspace and validation rules

- Work in an isolated workspace with a preview of the candidate layout. Save unfinished drafts. Require explicit export and confirmation before replacing existing output. Source definitions and the active game remain intact during editing.
- Assign stable IDs to new definitions and placements. Distinguish the variant ID, the target placement or reusable definition, and the individual records within it. Show source provenance and the declared scope so authors can tell which other placements would be affected.
- Reopen exported definitions through the normal readers. Run applicable checks for geometry, terrain seams, access routes, entrances, markers and action links. Identify both sources when a broader replacement removes a narrower target. Report unavailable checks and require the owning runtime gates before any affected location becomes playable.
- Report the scope and context of each save compatibility result. A valid content export can still be incompatible with affected saves. Unresolved checks cannot establish a compatibility claim.

## Required data, inputs, outputs and events

Inputs include workspace content, classic or native source definitions, edit and preview actions, a new-location or variant declaration, explicit target scope, terrain and placement context, and optional author-supplied mappings. Required data includes stable location, variant, placement and record IDs, source provenance, transforms, terrain shapes, entrances, marker roles, action links and owner validation results. Outputs include drafts, preview data, validated mod-ready definitions and diagnostics naming affected records, required checks and compatibility outcomes. API and event names remain technical design.

## Edge cases and technical constraints

Target Godot 4.7.2. Detect ambiguous scopes, overlapping layouts, broken links, incompatible record replacements and unusable terrain approaches through owning validators. Validate mappings by stable identity and supported layout, never by visual similarity or proximity. Report failed writes and keep the draft usable. Previewing a change preserves the live session and saves.

## Acceptance criteria

1. An author can arrange an existing settlement and edit supported objects, entrances, markers and action links in interiors and dungeons.
2. An author can create a new location, shape its terrain and approaches, and preview the resolved layout. A blocked required route is reported before the location becomes playable.
3. A reusable variant and a placement-specific variant declare distinct targets. An incompatible broader replacement identifies the narrower affected source and target.
4. Retained records preserve their IDs. Invalid required links block export. A changed persistent record requires a validated mapping for a save compatibility claim. An otherwise valid incompatible export follows existing recovery when used with an affected save.
5. Exported definitions reopen through the normal readers. Editing, cancellation and preview preserve source files, active state and save data.
