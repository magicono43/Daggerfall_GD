# DEV-001 — Startup log retention

**Approval status — Approved, finalized v1.** Updated 2026-11-18. See DEV-001-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Purpose and intended player experience

Keep recent local diagnostics available when a player restarts after a startup failure or crash. Logging runs during normal play. If file logging is unavailable or stops, a single non-blocking warning tells the player while play remains available, subject to the usual startup requirements.

## Governing specification

The user confirmed on 2026-11-18 that DEV-001 should reference [CORE-002, approved v1](../CORE/CORE-002.md). CORE-002 governs startup log behavior and supplies the full acceptance criteria. See DEV-001-D01 and CORE-002-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

| Area | Approved behavior |
| --- | --- |
| Rules, parameters and configuration | Keep the current and previous launches as `Player.log` and `Player-prev.log`, each capped at 200 MiB (209,715,200 encoded bytes). Flush each message. Default release output is informational and higher. The initial retention and size policy is fixed. |
| Required data and inputs | Use the selected storage root after exclusive-use protection is acquired. Record build, launch time, operating system and storage mode. Record mod IDs and versions after discovery, with an explicit pending status before then. Accept severity-tagged diagnostics and filesystem outcomes. |
| Outputs and events | Write local readable text with timestamps, severities and exception traces. Apply CORE-002 privacy filtering before byte accounting. Report logging availability and present the cap or failure warning independently of the file logger. |
| Cross-system interactions | [CORE-001](../CORE/CORE-001.md) governs root selection, exclusive use and development isolation. CORE starts file logging once storage is ready, DEV and other subsystems supply diagnostics, MOD supplies discovery results, and UI presents warnings. |
| Edge cases and failures | Follow CORE-002 for first launch, failed preservation or creation, oversized messages, the cap and write or flush failure. Protect existing diagnostics during failed rotation. Failures before the logger starts may leave no file record. Per-message flushing leaves power-loss durability unguaranteed. |
| Save/load | File logs are scoped to the application launch. Save/load and scene changes neither rotate the logs nor reset their state. Save outcomes are independent of logging availability. |
| Technical constraints | Apply the CORE-002 contract in Godot 4.7.2. CORE-002 defers encoding, timestamp format, warning wording, API details and the rotation mechanism. |

## Daggerfall Unity reference

At subsystem registration, DFU initializes the persistent path and installs its handler under a play/install-mode guard. The handler replaces the previous log with the old current log, creates a fresh current log and enables automatic flushing. It catches rotation failures but attempts to create the current log afterward, which can truncate a surviving current file. Creation itself is outside the rotation catch. [DaggerfallUnityApplication.cs](../../../../reference_material/daggerfall-unity-1.1.1-cve-2025/Assets/Scripts/DaggerfallUnityApplication.cs), `SubsystemInit`, `InitLog` and `LogHandler`.
