# DEV-013 — Localization and mod packaging tools

**Approval status — Approved, finalized v1.** Updated 2026-11-18. See DEV-013-A01 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Purpose and intended experience

Let translators review an import before changing their workspace and catch invalid localization before publishing a mod. Authors can keep existing translations, apply selected updates and package an incomplete language collection when the runtime has an approved fallback.

## Confirmed behavior

1. Present a graphical import preview grouped by locale and collection. Show new keys, changed source text, conflicts with existing translations and validation errors. Let authors select changes to apply and keep existing translations by default.
2. Automate localization checks as part of mod validation and packaging. Identify invalid entries by key, locale and source file when available. Block packaging for errors that would make the contribution fail the runtime loader. Report missing translations as warnings where approved fallback makes them usable.
3. [DATA-020](../DATA/DATA-020.md) governs safe, reviewable imports and supported round trips. [MOD-016](../MOD/MOD-016.md) governs package validation and ZIP creation, including graphical and command-line targets subject to feasibility.

See DEV-013-D01 and D02 in the [decision log](../../GAMEPLAY_DECISIONS.md).

## Approved workflow details

- Show source and existing translation together for a changed key, with its proposed result and applicable diagnostics. Unselected translations and source files stay intact. Source removals flag existing translations for review under DATA-020.
- If the workspace or source changes after preview, refresh the preview before applying affected edits. Publish the approved import as a validated operation under DATA-020. A failed import leaves the existing translation workspace usable.
- Reuse the same localization validation rules across graphical and command-line package workflows. Distinguish a loader error, a fallback warning and a check that could not run in the supplied context. Report the actual packaged result through MOD-016.

## Data, inputs, outputs and events

Inputs include classic or authored source records, workspace catalogs, locale and collection mappings, selected changes, validation context and package requests. Required data includes stable keys, source provenance and versions, supported token and placeholder contracts, expected fallback, differences and per-entry validation results. Outputs include the import preview, committed catalog changes, packaging diagnostics and the MOD-016 package result. Exact event names and diagnostic representation remain technical design.

## Interactions, parameters and save/load

- DATA-013 and DATA-014 govern key scope, fallback and translation validity. DATA-015 and DATA-016 govern text structure and substitutions. DATA-020 owns supported import fidelity and safe publication. [QUEST-007](../QUEST/QUEST-007.md) covers quest-specific preview and reveal diagnostics.
- DEV-009 covers source inspection and supported editable exports. MOD-016 owns manifests, package file inclusion and packaging. DATA-003 owns runtime activation of validated contributions.
- No gameplay formulas or balance settings apply. Authors choose locales, mappings and approved replacements. The workspace holds review metadata. Imports and package operations preserve character saves and the active runtime configuration.

## Edge cases and technical constraints

Target Godot 4.7.2. Handle duplicate keys, stale previews, removed source entries, missing translations, invalid required controls, unsupported tokens and failed workspace writes. Diagnose invalid required placeholders and markup through the owning contracts. Preserve translator work during canceled or failed imports. Packaging checks rely on the same runtime validity and fallback rules for the supplied context. Exact workspace format, GUI layout, CLI output and supported fixture inventory remain open.

## Acceptance criteria

1. The graphical preview groups changes by locale and collection and exposes new keys, source changes, conflicts and errors. Existing translations remain selected for preservation by default. Applying selected valid changes preserves unselected translations.
2. A source or workspace change invalidates affected preview decisions until refreshed. Failed or canceled publication preserves the previous usable catalogs.
3. Packaging diagnoses loader-rejected text by key, locale and source where available and blocks publication. An incomplete locale with an approved fallback yields a warning and can package successfully.
4. Equivalent graphical and command-line checks agree wherever both workflows are supplied. Unavailable checks are disclosed. The final ZIP follows MOD-016 verification.
5. Import and packaging preserve original sources, character saves and the active content configuration.
