# UI-008 — Setup, title and cinematic transitions

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-16 with “I approve”. Updated 2026-11-16.

## Gameplay purpose and intended experience

Reach a usable title menu after setup or session return. Let players watch the opening presentation or skip it with a fresh button press, then use the menu normally.

## Confirmed requirements

- **UI-008-D01.** Play the startup video once during the first successful title entry per app launch, after required setup and validation. Provide a setting to disable the startup clip. If it is missing or unplayable, proceed to the title. Later title returns follow their CORE flows.
- **UI-008-D02.** Use DFU-style broad any-key skipping for the startup and death clips.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#ui-008-interview-decisions).

## Existing Daggerfall Unity behavior

In the local DFU 1.1.1 snapshot, `Assets/Scripts/Game/DaggerfallUI.cs#ProcessMessages` dispatches setup, startup and death return. `#InitGame` checks validated data, pushes the start window and conditionally pushes the video window above it. The startup clip is `ANIM0001.VID` and the death clip is `ANIM0012.VID`. `Game/UserInterfaceWindows/DaggerfallVidPlayerWindow.cs#Update` checks any-key input when enabled, Back and end of playback, then releases playback and closes. Its any-key check ignores axis bindings. Findings are from static inspection.

## Detailed rules and behaviors

1. CORE-004 governs mandatory and optional setup, accepted content paths and menu failure recovery. Required validation and pre-menu configuration must complete before startup video presentation or normal title entry. Continue and Retry follow the current transition's admission rules. Startup presentation has no character start or load effect.
2. Default the startup clip on and use original `ANIM0001.VID`. Play it on the initial entry flow after required validation, keeping the title input inactive through playback. Natural completion, skip, disabled preference or playback failure satisfies the startup presentation step. Prepare the menu behind the clip if useful, and publish readiness only when the menu is usable. Return directly to title presentation on later ordinary returns, subject to the approved death exception.
3. Record startup presentation completion, skip or bypass across menu retry. If the menu fails after the clip has resolved, retry only menu entry through CORE-004's independent recovery. An attempt that fails before reaching presentation does not consume the startup clip. The startup preference applies only to the startup clip and changing it does not trigger playback.
4. Starting as soon as the video context owns input, accept a fresh keyboard key, mouse button or digital controller button as skip. The mapping includes ordinary unbound buttons as well as Back. Axis movement, stick drift, pointer motion, held input and auto-repeat do not skip. Consume the entire triggering activation so it cannot activate a title control. Focus restoration and device changes cannot synthesize skip or menu input.
5. CORE-008 owns death return. Play original `ANIM0012.VID` once for a completed death return, allow early skip and bypass missing or failed playback silently without substitute death text. Voluntary return does not play it. Death presentation uses application-scoped video, audio and input ownership independent of the ended gameplay session. Retry after resolved presentation does not replay it. Neither playback nor skip resumes the ended session.
6. AV reports a terminal playback outcome for each attempt. Scope the completion to the active flow and ignore duplicates and late callbacks. Release video-owned resources and input during handoff. Keep CORE-004 recovery available without original media assets. Playback failure may be logged and routes directly toward the title under the applicable startup/death policy.

## Parameters, data and configuration

No gameplay formulas or balance values apply. Required data includes launch and flow identity, return reason, validation and menu readiness, media identity, startup preference, presentation status, and active input scope. Startup and death clips each resolve once in their applicable scope. No generic playback timeout, skip delay or key count is selected. The startup-video preference is application-wide and follows CORE settings application and persistence rules.

## Inputs, outputs and events

Inputs include startup, setup Continue or Retry, return reason, validation and menu preparation outcomes, fresh skip input, AV completion/failure, and scope teardown. Outputs include setup, playback, skipped/bypassed status, usable title or independent recovery. Menu readiness and CORE session outcomes remain distinct from AV completion. Exact event names are implementation choices.

## Cross-system interactions and consistency

Reviewed against CORE-004 setup and recovery, CORE-005/007 scope and operation identity, CORE-008 original death clip and skip, CORE-015 readiness, CORE-016 input handoff, UI-001/002 context ownership and routing, and UI-004 and MOVE-001 device behavior. CORE-012 opening gameplay popups are a separate entry flow. DATA resolves media and AV owns decoding/playback and audio scope.

## Edge cases and failure conditions

- A held button from setup, controller drift, or a pointer moved over title cannot skip or activate the title. A fresh skip press can end a video immediately.
- A missing, unplayable or interrupted clip follows its declared completion/failure path. A late or duplicate callback cannot end a newer presentation or publish a second menu-ready result.
- Menu failure after presentation retains its terminal state across retries. Death return still follows CORE-008 cleanup failure precedence.
- Disabling startup video leaves death presentation under the approved death-return contract. Existing saves are untouched by title presentation.

## Save/load considerations

The startup preference is application configuration. Presentation status, consumed input and retry state belong to live application or return scopes. They are not character save data. Loading a save does not trigger startup presentation or implicitly load another save after death.

## Technical constraints

Target Godot 4.7.2. Coordinate independent startup/recovery UI and AV lifetimes. Verify the supported decoder and source-media access against actual content before implementation is complete. Exact playback backend and transition APIs are open implementation choices.

## Acceptance criteria

1. Required setup and validation finish before first title presentation. Startup playback defaults on and is attempted once per launch when eligible. Disabling or losing the clip reaches the usable title directly.
2. A fresh digital press can skip from the start. Motion, held input and repeats cannot skip. The skip press cannot activate the title.
3. Death return plays its original clip once with early skip and silent failure bypass. Voluntary return skips death presentation and the startup setting applies only to startup.
4. Menu failure uses independent recovery and retry does not replay resolved presentation or repeat completed teardown.
5. Duplicate or stale AV callbacks cannot affect a newer scope. Readiness is published only for a usable title.
