# UI-002 — Message routing and shortcut dispatch

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-16 with “I approve”. Updated 2026-11-16.

## Purpose and intended experience

Route deliberate input to the expected screen or gameplay owner. A simultaneous press has a predictable result, and a confirmation can affect only the prompt that asked for it. A burst of visual updates cannot erase a navigation request.

## Confirmed requirements

- **UI-002-D01.** Navigation and confirmation requests receive explicit outcomes. Reject requests that cannot be admitted as busy and requests whose target is no longer valid as stale. Repeated visual refreshes may merge.
- **UI-002-D02.** Escape/options retains first priority. Ordinary screen shortcuts outrank quicksave and quickload. CORE-018 retains the quicksave/quickload conflict rule.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#ui-002-interview-decisions).

## Existing Daggerfall Unity behavior

In the local DFU 1.1.1 snapshot, `Assets/Scripts/Game/DaggerfallUI.cs#Update` lets the top window process the string queue before global `ProcessMessages` dequeues an entry. `UserInterfaceWindows/DaggerfallStartWindow.cs#ProcessMessages` itself dequeues an entry and switches on it. `UserInterface/UserInterfaceManager.cs#PostMessage` caps the queue at ten and discards all pending entries on overflow before enqueuing the newest. `GameManager.cs#Update` checks ordinary window shortcuts on action completion and quick actions on action start. Options, status and automap are independent of the main window shortcut chain, so a single update can issue multiple requests. These findings are based on static inspection.

## Detailed rules and behaviors

1. Resolve discrete actions in the active input context. A focused control can handle its local bindings within that context. Unhandled input in a modal, menu, text-entry or loading context does not activate gameplay shortcuts. Global shell operations use explicit routes and retain their own eligibility checks. An unhandled request receives an outcome without being rerouted to an unrelated view.
2. Use one shortcut dispatch per processed input update. Consider newly eligible deliberate activations collected since the prior dispatch across keyboard and controller together. Resolve against one context before applying the winning action. The dispatch boundary is independent of physics catch-up, and a brief tap remains eligible even if released before dispatch. Discrete shortcuts do not auto-repeat, and suppressed actions expire at the end of the dispatch.
3. Remove both quicksave and quickload candidates when both appear in one gameplay dispatch, and give brief conflict feedback. Other candidates can still compete. For the remaining candidates, use the priority below and submit at most one. A rejection of the winner produces its own outcome. It does not promote another candidate from that dispatch.
4. Bind navigation and confirmation requests to their intended destination or target and relevant context/session identity. Validate on admission and revalidate before applying. A duplicate or delayed response cannot resolve a replacement prompt. Consume opening, closing and confirmation input so it cannot pass through at the handoff. UI-001 owns navigation and CORE-016/MOVE-001 own input resumption.
5. Requests may resolve immediately. If a command needs to defer, keep its identity and accepted order relative to other deferred commands for the same destination. Every command receives an outcome, including busy rejection when capacity or conflicting work prevents admission and stale rejection when its context expires. An admitted request can report pending before its terminal outcome. Visual refreshes may merge for the same target using its latest state. Visual refresh traffic cannot evict admitted commands. Commands posted during a transition run only at a safe boundary after the active handoff commits.
6. The dispatcher submits requests to UI or the gameplay owner. Owners validate gameplay eligibility, perform effects and determine success. A navigation or confirmation event cannot skip save/load preflight, incur a charge twice or report successful persistence at submission. CORE-018 governs user feedback for quick actions. Routine visual refreshes need no player feedback.

## Priority, parameters and configuration

Highest to lowest priority follows. The ordinary shortcut order follows DFU's source check order where that code supplies one, with independently checked status and automap placed after the main chain.

1. Escape/options
2. Character sheet
3. Inventory
4. Travel map
5. Rest
6. Transport
7. Quest journal
8. Notebook
9. Spellbook
10. Magic-item selection
11. Status
12. Automap
13. Quicksave
14. Quickload

The pair conflict check occurs before ranking, so rows 13 and 14 never resolve a simultaneous save/load tie. No balance formula or numeric queue capacity applies. Keyboard/controller bindings are configurable. CORE-018 requires resolving conflicts before applying overlapping bindings and permits reuse across mutually exclusive contexts. Binding defaults and detailed control-specific actions remain with the controls and screen specifications. The priority is a behavior rule for the stock action family.

## Data, inputs, outputs and events

Inputs include eligible action edges, action and binding identities, target and context/session identities, navigation or confirmation requests, refresh targets, and owner completion. Outputs include applied, busy, stale, declined or other owner-defined outcomes and pending status where appropriate. Emit committed effects through their owning system. Use owner reasons for applicable notices and correlate completions with their originating requests. Exact data representation and event names remain implementation details.

## Cross-system interactions and consistency

Reviewed against CORE-018 shortcut arbitration, binding validation and feedback, CORE-016 pause/input context, MOVE-001 input retention and disconnect handling, UI-001 coherent handoffs, and CORE-007/013 session replacement. Separate deliberate presses remain ordered at input capture. Shortcut arbitration intentionally selects at most one eligible action per dispatch under CORE-018. General gameplay inputs continue under MOVE-001. Covered views receive no gameplay shortcut fallthrough even with a no-UI-pause mod profile. SAVE owns quick-target validation and durable completion. UI-AR-01 remains proposed beyond this specification.

## Edge cases and failure conditions

- Escape and inventory in one dispatch open options only. Inventory and quicksave open inventory only. Quicksave plus quickload give conflict feedback even if a third action wins.
- A rejected winner cannot silently trigger a lower-priority action. A key held across a modal close cannot reopen the window. A lost controller follows the approved MOVE recovery path.
- A queued confirmation from a retired prompt or session is stale even if a new prompt has the same content. Duplicate responses cannot repeat the owner operation.
- When refreshes, navigation commands and callbacks arrive in a burst, preserve admitted command outcomes and committed transition order. Busy or stale outcomes require no deferred action replay.

## Save/load considerations

Dispatch batches, pending UI commands and refreshes are runtime state. Session replacement invalidates requests from the retired session. Supported restored activities reconstruct their own approved UI context under UI-001 and CORE-013. Quick actions use CORE-018 and SAVE/CORE identity, completion and recovery rules. Binding persistence follows the applicable settings contract.

## Technical constraints

Target Godot 4.7.2. Route by action and owning context and preserve explicit request identity across deferred callbacks. A queue is optional. Any deferred mechanism must preserve admission, ordering and outcome guarantees before it accepts a command. Exact input callback and queue mechanics remain implementation choices.

## Acceptance criteria

1. Each supported gameplay shortcut routes to its intended owner only while eligible. Focused text and active modals prevent gameplay fallthrough.
2. Simultaneous shortcuts follow the full priority order. Quicksave/quickload conflict is detected independently of that order. A losing candidate or rejected winner cannot generate deferred fallback.
3. Brief taps survive input capture. A held key and extra physics steps do not repeat a discrete shortcut or pass input into a new context.
4. Under saturation, admitted navigation and confirmation requests retain outcomes. New unadmittable commands report busy, and duplicate refreshes can merge.
5. A late, duplicate or stale prompt response cannot resolve a different prompt or repeat an owner effect.
6. Quick actions preserve owner validation and show success only after authoritative completion. Results from a retired session cannot appear as success for its replacement.
