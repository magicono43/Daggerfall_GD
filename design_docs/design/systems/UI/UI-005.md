# UI-005 — Modal messages and text entry

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-16 with “I approve”. Updated 2026-11-16.

## Gameplay purpose and intended experience

Read an important message, make a deliberate choice or enter text with clear feedback. The input that opened a prompt cannot accept it. A rejected text entry stays available to correct, and cancellation has an explicit meaning.

## Confirmed requirements

- **UI-005-D01.** Informational modals accept fresh Confirm or Back. Click-anywhere dismissal is enabled per message. Consequential choices start on a safe option when available. Back cancels only when the owner permits cancellation. A required choice without a safe default requires explicit selection.
- **UI-005-D02.** Enter used to accept active IME composition is consumed. A separate press submits single-line text. Owner rejection keeps the entered text and shows what needs fixing. Cancellation has a distinct outcome from acceptance of empty text.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#ui-005-interview-decisions).

## Existing Daggerfall Unity behavior

Static inspection of the local DFU 1.1.1 snapshot shows that `Assets/Scripts/Game/UserInterfaceWindows/DaggerfallMessageBox.cs#AddCommonButtons` marks No as the default on standard Yes/No prompts. `ParentPanel_OnMouseClick` checks minimum presentation time and weapon input before advancing or dismissing eligible messages. `ActivateButton` raises a callback with the chosen button. `DaggerfallInputMessageBox.cs#OnPush` and `#OnPop` save and restore IME mode where applicable. `#Update` accepts Return and keypad Enter, and `#ReturnPlayerInputEvent` closes the window before notifying listeners with the entered string.

## Detailed rules and behaviors

1. A prompt declares whether it is informational, a choice, or text entry. Give each offered response a stable identity independent of visible text. A prompt owner declares permitted cancellation, initial safe response if applicable, validation, and any screen-specific time or pause behavior. UI presents the prompt and routes requests to the owner.
2. Dismiss an informational prompt with a fresh Confirm or Back. When enabled, click-anywhere dismissal applies within the prompt's declared area. A click that activates a prompt control, scrolls text or opens the prompt cannot also dismiss it. Multi-page prompts advance one page per eligible action and dismiss on the last page. Preserve access to required reading and choices across UI sizes.
3. Initially focus the declared safe response on a consequential choice when available. For a required choice with no safe default, start without an armed response. Navigation may move focus to a response, and then a distinct Confirm activates it. A deliberate click on a response may activate it directly. Back, including Escape where mapped to Back, requests cancellation only when allowed. Return to Game follows the same owner constraints under UI-001.
4. Give the active text field ownership of editing input and IME composition. Preserve uncommitted text in the active prompt when the owner rejects submission. Enter that ends composition cannot also submit. For single-line fields, a later deliberate Enter or explicit Submit validates the current text. If an owner permits multiline input, Enter inserts a line break when composition is inactive and an explicit Submit control sends the value. Back or Escape consumed by the IME must not also cancel the prompt.
5. Use prompt and request identity for validation and resolution. Reject duplicate and stale submissions. If validation or resolution remains pending, block duplicate submission and respect the owner's cancellation policy for that phase. On rejection, show the reason in the prompt while preserving the draft. Accepted text and accepted choices close or advance the prompt according to the owner's committed outcome. Close once, release prompt ownership and consume the triggering input before a follow-up prompt can receive new input.
6. A cancelled prompt reports cancellation to the owner once. An explicitly submitted empty value goes through normal validation. Session teardown or scope invalidation retires the prompt and invalidates pending UI responses through UI-001/002. Cleanup releases the ending field's text and composition ownership without altering another active text context.

## Parameters, data and configuration

No gameplay formula or global text length applies. Required data includes prompt and session identity, localized message or formatted text, stable choices, safe response and cancel policy, text field constraints, draft input, validation state, and applicable scope and presentation policy. Owners define valid text, including empty input, whitespace, length and allowed characters. The shared UI supports per-prompt dismissal and field configuration. Feature-specific deadlines, including CORE-006 display confirmation, follow their owning clock and outcome rules.

## Inputs, outputs and events

Inputs include open, Confirm, Back, click, focus navigation, composition and edit events, submit, owner validation outcome, and scope teardown. Outcomes include dismissed, selected response, accepted text, cancelled, validation rejection, busy or stale. Terminal player outcomes occur once for the intended prompt. Use localized owner reasons for recoverable validation feedback.

## Edge cases and failure conditions

- Held Confirm, click-through and repeated Enter cannot dismiss a follow-up prompt or replay an accepted action.
- A cancelled input and a successfully submitted blank remain distinct. Invalid input preserves the draft through correction and retry.
- Text composition acceptance, cancellation and context handoff require distinct activation from prompt submission or cancellation.
- A timed or stale prompt can expire while a player is interacting. Resolve by the owner's rules and prevent late input or callbacks from applying the expired action.
- A required prompt with no safe default remains navigable by keyboard and controller even without an initially armed response.

## Save/load considerations

Draft text, composition, focus and transient response tokens are runtime state. A feature with an approved restorable prompt reconstructs it from authoritative state with a current-scope identity. An old response cannot apply on load. Saving or restoring an active prompt follows its owning feature and CORE/SAVE contracts.

## Technical constraints

Target Godot 4.7.2. Verify IME event consumption, focus handoffs and callback ordering on supported platforms. Keep prompt content and response IDs separate and preserve owner validation before committing outcomes. Exact text controls, token representation and event API remain implementation choices.

## Acceptance criteria

1. Informational prompts dismiss through fresh Confirm or Back, and click-anywhere works only when enabled. Opening input cannot dismiss the prompt.
2. A consequential choice starts on an available safe response. A required choice with no safe default accepts only deliberate response selection and activation. Back cancels only when permitted.
3. Enter accepts active composition without submitting the prompt. A fresh submission validates the final text. A rejected submission retains text and displays an actionable reason.
4. Cancellation is reported separately from an accepted blank. Each prompt resolves at most once, and stale or duplicate responses have no owner effect.
5. Nested prompts and focus changes preserve active text ownership, consume handoff input and keep required controls reachable.
6. Save/load, screen expiry and display timeout follow owner-specific behavior. A late response cannot commit after invalidation.
