# UI-004 — Frame rendering and input ownership

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-16 with “I approve”. Updated 2026-11-16.

## Gameplay purpose and intended experience

Keep game screens readable and operable across supported displays and devices. The player can enlarge controls and text independently of world rendering resolution, see which control will respond to keyboard or controller input, and point freely where a screen benefits from it.

## Confirmed requirements

- **UI-004-D01.** Adapt the layout to the available space while preserving the aspect ratio of retro artwork. Provide a separate UI size setting that enlarges text and controls independently of world resolution.
- **UI-004-D02.** Use visible focus and direct control navigation for keyboard and controller. Mouse hover highlights the pointed control without taking navigation focus. A deliberate click may move focus. Screens suited to free pointing, such as maps, may provide a controller cursor.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#ui-004-interview-decisions).

## Existing Daggerfall Unity behavior

In the local DFU 1.1.1 snapshot, `Assets/Scripts/Game/DaggerfallUI.cs#Update` supplies a custom pointer position to the top window, updates it and clears frame key state. `OnGUI` draws the top window on repaint and can draw the large HUD beneath it. `ProcessHotKeySequences` checks whether the focused control suppresses panel hotkeys. `Game/UserInterface/Panel.cs#Update` passes custom pointer coordinates to child components, and `Draw` renders child components. Findings are from static inspection.

## Detailed rules and behaviors

1. Use the available UI area to lay out each screen. Preserve artwork proportions and allow text wrapping, reflow or scrolling where necessary. At supported viewport sizes and UI scales, required controls and their focus indicators remain reachable. Decorative backgrounds may use screen-specific cropping, subject to preserving relevant visual information.
2. A UI size change affects text, controls, layout spacing and associated hit regions coherently. Pointer hit tests use the same layout and coordinate mapping as rendering. Changing aspect ratio, display mode or UI size recomputes both before subsequent interaction. Preserve valid focus through reflow and use the screen's safe focus target if necessary.
3. Keep presentation updated through ordinary gameplay pause. The active view owns interaction. Covered views and the HUD may remain visible according to UI-001 and the relevant presentation rules. Visible background layers receive no interaction through the active view. Respect HUD preference and independent hide requests.
4. Give each interactive screen a predictable initial focus and navigation order. Skip unavailable elements and scroll the focused element into view where necessary. Keep focused and hovered states distinguishable. A deliberate click on a focusable control may establish focus and perform that control's applicable action once. Moving the mouse or idle controller drift cannot move navigation focus or activate controls.
5. In sections that declare controller pointing, route intentional controller pointer movement and activation through the screen's hit regions. Provide a clear route to continue ordinary focus navigation or leave the pointing section. Each activation targets either a pointed control or a focused control. Mode and device changes alone cannot activate either.
6. Focused text fields receive applicable edit input. UI-005 owns detailed text entry and composition. UI-001/002 and CORE-016 govern layer and context handoffs, including input consumption, cursor capture and valid focus restoration. MOVE-001 governs device disconnect and deliberate input.

## Parameters, data and configuration

No gameplay formula or balancing value applies. Required data includes available viewport bounds, UI size preference, artwork dimensions, layout and hit regions, eligible focus targets and order, focused and hovered controls, supported pointer modes and active context identity. UI scale defaults, range and options, minimum supported viewport, and screen-specific pointing surfaces are pending owner specifications or display verification. Preference application and persistence follow applicable CORE settings rules.

## Inputs, outputs and events

Inputs include viewport and UI size changes, active view changes, eligible pointer and navigation input, device changes, confirm, and focus invalidation. Outputs include updated visual layout and hit regions, focus and hover feedback, pointer mode and eligible control actions. Submit control actions through UI-002 and any applicable owner contract. Rendering or focus changes alone produce no command.

## Cross-system interactions and consistency

Reviewed against UI-001 for modal input and focus restoration, UI-002 for context routing, UI-003 for modded layout and required controls, CORE-006 for display testing, CORE-016 for pause, HUD and input ownership, and MOVE-001 for input and disconnect. Display confirmation retains its 15-second real-time deadline. AV owns world rendering and detailed image sampling. UI-005 owns modal text entry. UI-AR-02 remains proposed beyond this specification.

## Edge cases and failure conditions

- Narrow displays, enlarged UI and long localized strings can move controls off-screen. Approved layouts keep required actions reachable by scrolling or reflow.
- On a resize or scale change, cursor coordinates and visual layout can temporarily disagree. Apply the new mapping before accepting actions in the changed layout.
- Hiding, disabling or removing a focused target selects a valid fallback without triggering it. A modded screen must preserve required navigation under UI-003.
- Moving from screen navigation to map pointing or changing devices cannot double-fire Confirm. Controller disconnection follows the approved MOVE recovery flow.
- A visible control beneath a modal cannot receive clicks or navigation. Failure to restore an invalid display mode follows existing CORE recovery.

## Save/load considerations

The UI size setting is an application preference. Live focus, hover, hit regions and controller pointer positions are runtime presentation state. Reconstruct supported restored views under UI-001 and screen-owner contracts. A view may retain specific navigation state only where its specification permits it.

## Technical constraints

Target Godot 4.7.2. Maintain consistent coordinate transforms for rendering and hit testing, and restrict input routing to the active context even when several layers render. Exact layout nodes, renderer composition, pointer API and focus styling are implementation choices.

## Acceptance criteria

1. Across supported aspect ratios and scale settings, retro artwork retains its proportions, and required text and controls remain reachable.
2. Enlarging UI changes rendered text, controls and matching hit regions independently of world resolution.
3. Keyboard and controller can reach required controls with visible focus. Hover does not steal navigation focus. A deliberate click applies at most one action.
4. A screen that opts into controller pointing can operate supported targets and return to ordinary navigation without duplicate activation.
5. Covered views remain input-inactive. Reflow or modal return restores eligible focus or a safe fallback without activation.
6. While gameplay is paused, UI remains responsive. Display confirmation and device disconnect follow approved CORE and MOVE rules.
