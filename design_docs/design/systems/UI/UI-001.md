# UI-001 — Window stack and modal lifecycle

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-16 with “I approve”. Updated 2026-11-16.

## Gameplay purpose and intended experience

Open a screen, make a choice and return to the expected place. A confirmation can cover inventory without losing the selected item. Returning to play feels deliberate, especially when the world continues to run under a modded menu.

## Confirmed requirements

- **UI-001-D01.** Full-screen gameplay menus such as inventory, character sheet, journal and maps pause by default. Passive HUD overlays leave gameplay running. A screen can request live simulation. Mods can override UI pause behavior, including a profile in which no gameplay UI requests a pause. An interactive live overlay owns its input while focused.
- **UI-001-D02.** Back or Cancel dismisses one eligible layer at a time and restores valid prior selection and focus. Required decisions use explicit options. Offer a separate Return to Game action for closing multiple eligible layers. Required decisions and screen-owned draft rules govern whether it can proceed.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#ui-001-interview-decisions).

## Existing Daggerfall Unity behavior

In the local DFU 1.1.1 snapshot, `Game/UserInterface/UserInterfaceManager.cs` under `Assets/Scripts` owns the stack. `PushWindow` calls `AddWindow`, which invokes `OnPush` and checks `PauseWhileOpen`. Push then clears gameplay actions and any active fade before notifying. `RemoveWindow` protects the HUD, calls `OnPop` and `OnReturn` when removal occurs, and uses stack depth and HUD setting to decide whether to resume and delay activation clicks. `ChangeWindow` repeatedly removes windows and adds a replacement through lower-level paths. A protected HUD can prevent that removal loop from finishing. `Game/DaggerfallUI.cs` updates and draws the top window and its `PopToHUD` assumes the HUD can be reached. Evidence is from static inspection.

## Detailed rules and behaviors

1. A navigation scope has a valid base destination tied to the current application or session context. In a ready gameplay session, the base destination is gameplay whether or not the player displays the HUD. Pause, HUD visibility, and active input context are distinct.
2. Opening a modal covers the previous view and suspends its input. Keep the covered view's draft and selection while its scope remains valid. On normal close, restore the previous view and any still-eligible focus target or selection. Use a screen-defined safe focus target if the old control is absent or disabled. Focus restoration never activates that control.
3. Back targets the active eligible layer. If it requires an explicit response or has an unresolved draft rule, let that screen handle Back. A close request identifies its intended layer so duplicate or delayed requests cannot close the next layer. Closing a layer releases its owned resources once.
4. Return to Game is offered in a gameplay session for a valid return path. Check the layers to be closed. Honor any owner-required confirmation or commit/cancel flow before completing the return. If a required decision blocks it, leave the path in place and identify the blocking decision. The action closes eligible UI and returns to the gameplay destination. CORE still determines whether the player can act or the world can advance.
5. Each applicable window owns its UI pause request for the lifetime of the layer, including while covered. Under a no-UI-pause mod profile those ordinary window requests are suppressed. Independently owned focus-loss, load, recovery and device-disconnect suspension retain their approved rules. Live interactive windows block ordinary gameplay input while focused, while the world may still advance and affect the player. A child layer can have a different pause policy from its parent.
6. Commit replacement and teardown coherently across navigation, pause, HUD and input. Session end and successful session replacement retire old UI scopes and route to the valid new destination. Delayed callbacks from an ended scope cannot act on the replacement. Each visibility change respects the player's HUD preference and other hide requests.
7. Consume input that opens, dismisses or changes active context. Restore cursor and text ownership under CORE-016. Discrete gameplay actions require a fresh press after return, and held movement can resume once eligible.

## Parameters, data and configuration

No numerical balance parameters apply. Use a stable view and layer identity, owning scope, base destination, return target, focus and selection references, dismissibility, effective pause mode, applicable HUD and input policies, and owner-reported close constraints. Simulation advances only when CORE readiness and applicable suspension reasons permit it.

Support per-view pause policy overrides and a mod profile that suppresses all ordinary UI pause requests. DATA-003 governs content activation. MOD/DATA can specify validation, conflict resolution and data format. Live simulation under menus exposes the player to ordinary world hazards and lets some choices become stale. Screen owners revalidate targets and eligibility when the player commits an action.

## Inputs, outputs and events

Inputs include open, dismiss, Back, Return to Game, replace, owner confirmation outcomes, and scope invalidation. Outcomes include the committed active view or base destination, focus/input handoff, ownership changes, or a rejected or pending transition with a reason. Notify observers of committed navigation once. Exact interfaces and notification timing within the committed handoff are implementation details. UI-002 owns general message routing.

## Cross-system interactions and consistency

Reviewed against CORE-005, CORE-013 and CORE-015–016 for scope cleanup, restore and owner-scoped gating, MOVE-001 for input and device disconnect, NPC-017 for dialogue policy, DATA-003 for mod activation, and TIME-002 for ordinary world time. Dialogue pauses by default and can run live through a mod. A navigation action does not replace the session lifecycle or advance TIME directly. Rest, travel, court, quest prompts, transactions and drafts retain their owning feature rules. UI-AR-01 remains proposed beyond this specification.

## Edge cases and failure conditions

- A hidden HUD, missing destination or stale return target cannot create an endless unwind. Use the valid scope destination when available. Otherwise reject the navigation request and let CORE supply its existing recovery route.
- Live menus can be interrupted by death or a session-ending event. Retire the invalid scope and prevent stale confirmation callbacks from committing an action.
- A modal closing above another pausing window, or a transition between two pausing windows, cannot expose an input or simulation frame between owners.
- A held button or duplicate close request cannot confirm a second prompt or attack after dismissal. A required choice cannot be skipped by repeating Back or Return to Game.

## Save/load considerations

The general navigation stack, focus handles and ownership tokens are runtime state. A feature with an approved restorable activity reconstructs its supported view and current-scope requests through CORE/SAVE before load suspension ends. Ordinary dialogue follows NPC-017's approved return-to-gameplay behavior on load. Save eligibility remains governed by the relevant owner. The mod profile follows applicable configuration rules.

## Technical constraints

Target Godot 4.7.2. Navigation must report finite outcomes and commit through the same lifecycle boundary for push, pop, replacement and multi-layer return. Keep simulation gating with CORE, input delivery with MOVE/UI, and authoritative gameplay commits with the appropriate owner. Exact scene structure, focus APIs and mod schemas remain open implementation choices.

## Acceptance criteria

1. Stock inventory, character sheet, journal and maps suspend ordinary gameplay. Passive HUD presentation adds no pause reason.
2. A no-UI-pause mod profile keeps the world advancing under gameplay menus when other gates allow. Focused live UI receives eligible input exclusively. Focus-loss, device-disconnect, load and recovery gates still apply.
3. Closing a confirmation returns to its parent with an intact draft and valid focus. Removed targets fall back to safe focus without activation.
4. Back removes at most one eligible layer per action. Return to Game handles eligible layers even with the HUD hidden, and respects required choices and draft confirmation.
5. Closing or replacing one paused layer releases only its ownership. No world step, gameplay input or HUD flash leaks through the handoff.
6. Open and close input cannot activate another context. Held discrete actions require fresh presses after return, while held movement can resume when eligible.
7. A stale or duplicate close is harmless. Death or successful load invalidates the old navigation scope, and supported restored activity reasons are in place before load releases its own gate.

## Outstanding questions and approval

Individual required responses, dirty-draft behavior and supported restorable activities remain screen-owner decisions. Mod schema and override conflict precedence remain MOD/DATA dependencies.
