# UI-003 — Window creation and replacement

**Approval status — Approved, finalized v1.** The user approved Draft v1 on 2026-11-16 with “I approve”. Updated 2026-11-16.

## Gameplay purpose and intended player experience

Open a screen with predictable state and working controls. Mod authors can make a small edit without supplying a custom screen, or replace a supported screen through a documented contract. Compatible edits can follow a replacement. If a custom view fails, the player can understand the failure and recover safely.

## Confirmed requirements

- **UI-003-D01.** Open screens fresh by default. A screen retains state between visits only where its own specification says so.
- **UI-003-D02.** Support targeted edits and straightforward whole-window replacement at declared points. Validate before main-menu entry. Keep startup and recovery UI available independently. If a replacement fails during play, preserve the current view where valid and offer an explicit built-in fallback where it can safely continue the same flow.
- **UI-003-D03.** Apply targeted edits to custom views that expose compatible named targets. Report missing or incompatible targets and allow correction at pre-menu mod configuration.
- **UI-003-D04.** Support button label, icon, placement and optional visibility edits, plus added text and buttons invoking supported actions. Changing an existing button's behavior requires a declared action hook. Required actions must remain reachable.

See the [gameplay decision log](../../GAMEPLAY_DECISIONS.md#ui-003-interview-decisions).

## Existing Daggerfall Unity behavior

In the local DFU 1.1.1 snapshot, `Assets/Scripts/Game/UserInterfaceWindows/UIWindowFactory.cs#RegisterCustomUIWindow` overwrites the mapping from window kind to class and asks `DaggerfallUI` to reinstantiate persistent windows. `GetInstanceWithArgs` delegates to `Activator.CreateInstance` with caller-supplied arguments. `DaggerfallUI.cs#Update` recreates the persistent window set when requested and processing messages calls for it. Some paths create windows directly, including HUD creation and several message-box helpers. Reuse policy and visible state depend on each window's lifecycle code. Findings are from static inspection.

## Detailed rules and behaviors

1. Treat a fresh open, a return to a covered view and a session restore as distinct requests. A fresh open initializes from current owner data plus any screen-approved retained state. A return preserves the same active view's eligible state under UI-001. Restore uses the owning feature's contract. Reusing a view instance is allowed if it behaves like the specified open and releases prior subscriptions, callbacks, transient focus and other opening-scope resources.
2. Publish documented IDs for supported windows, editable elements, insertion locations and action hooks. A targeted edit can change supported presentation properties or add content at a declared location without replacing the view. A replacement supplies a custom view for the same window ID through one declared registration, consuming the screen's documented opening data and fulfilling its required actions and lifecycle. Supported edit points and hooks are published per screen.
3. Resolve the whole view first, then resolve targeted edits against that view's exposed targets and capabilities. Use the resolved enabled-mod order for competing replacements and scalar edits, with the later valid contribution taking precedence. Distinct compatible edits accumulate. Validate the effective composition, identifiers, required actions and target compatibility before entering the main menu. Identify the conflicting contributions and targets if validation fails. Follow applicable DATA-003 recovery and run-long activation rules. A configuration change requires returning to the supported setup flow under those rules.
4. Validate preparation before handing off to a new view. If a replacement fails at runtime, release partially acquired resources and report the affected window and mod without committing the failed navigation or an owner action. Keep the prior view when its scope remains valid, or use existing CORE recovery if the scope is no longer safe. Offer explicit stock fallback only where it can safely receive the same request and preserve required outcomes. Fallback opens the stock view for that request without the failed replacement or targeted edits and preserves the configured mod order.
5. Preserve gameplay owner validation and UI-001/002 lifecycle and routing. Edits and action hooks cannot bypass owner prerequisites or replace required recovery actions. Protect access to startup and recovery UI independently of replaceable views. Check that required actions remain reachable through applicable keyboard, controller and pointer navigation, including after an edit hides or moves a control.

## Parameters, data and configuration

No gameplay formula or numeric balancing parameter applies. Required data includes stable screen and target IDs, view contract and required actions, typed opening context, supported edit properties, insertion points, action hooks, allowed retention fields and scope, contribution provenance and resolved order. Configurable surfaces are the supported additions, presentation edits, action hooks and replacement registrations. Exact authoring format and the list of exposed points belong to UI/MOD and the respective screen owners.

## Inputs, outputs and events

Inputs include screen open, return, close and restore requests, opening context, resolved mod contributions and explicit fallback selection. Outputs include a prepared view or a specific failure, mod validation diagnostics, committed navigation under UI-001, and supported action requests under UI-002. Rejected view creation must not emit navigation success. Screen presentation can request an action, with the gameplay owner deciding its outcome.

## Cross-system interactions and consistency

Reviewed against UI-001 for covered views and coherent transitions, UI-002 for target identity and command outcomes, CORE-004/005 for independent startup/recovery and scope lifetime, CORE-013 for supported restore, and DATA-003 for pre-menu validation, package ordering and activation lock. Targeted presentation edits and view replacement do not give UI authority over an inventory transfer, quest choice, purchase or save operation. UI-AR-02 remains proposed beyond this specification.

## Edge cases and failure conditions

- A replacement omits a control targeted by another enabled mod, or exposes the same ID with incompatible capabilities. Surface the contributor and target in pre-menu validation and allow the player to resolve the configuration.
- Two mods introduce the same control identity. Reject an ambiguous composition unless the supported schema defines an explicit override. The same scalar property follows the declared precedence when both edits are valid.
- Removing an optional button must not strand focus. A layout change must not make a required action unreachable or leave only a pointer path where controller or keyboard access is required.
- A failed open cannot leave gameplay paused, steal focus, duplicate a trade or cause a second confirmation. Existing valid owners retain their requests until a successful handoff.
- Reusing a view after close, load or character change cannot replay a callback or carry stale selections or drafts across scopes.

## Save/load considerations

UI instances, focus handles, modded view registrations and edit composition are runtime or configuration data. A feature with approved durable state saves that state through its owner and reconstructs its view from the current validated configuration. A screen-specific approved retention rule supplies scope and persistence. A runtime fallback does not migrate gameplay or change mod configuration in a save.

## Technical constraints

Target Godot 4.7.2. Expose a documented registration path for custom views and a declarative path for common targeted edits. Stable target identities must survive ordinary layout refactors. Validate the effective composition and keep failed preparation separate from committed navigation. Exact authoring tools, scene format, hook API and caching remain implementation choices.

## Acceptance criteria

1. Reopening a stock screen starts fresh unless its approved spec retains particular state. Dismissing a modal restores the same covered view under UI-001.
2. One mod changes a button label and adds text without replacing the view. Another can supply a custom view using the declared window contract.
3. Compatible targeted edits are applied to a custom replacement. A missing or incompatible target identifies the involved contribution during pre-menu validation.
4. A mod can add a button invoking a supported action, and can rebind an existing button where an action hook is declared. Required actions remain reachable after edits or replacement.
5. Competing valid edits resolve in documented order. Repeated validation of the same configuration produces the same effective composition.
6. A failed runtime replacement preserves the valid current screen, cleans up partial preparation and offers stock fallback only where the same flow can continue safely. Choosing fallback does not retry or duplicate a gameplay operation.
7. Reuse, close and session replacement cannot leak callbacks, drafts or navigation state. Startup and recovery routes remain available independently of custom views.

## Outstanding questions and approval

Individual screens still define retention, supported targets, action hooks and safe fallback context. MOD/UI still define contributor schemas and authoring ergonomics.
